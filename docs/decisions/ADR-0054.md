# ADR-0054 — Account is the tenant entity; connectors are account-scoped

Status: Proposed (owner-approved direction 2026-07-03; ADR-first before build — #392)
Relates to: auth (`cairn/core/triggers/auth.py`, single-admin today), the
workspace contract (ADR-0048/0051, `cairn/core/workspace.py`), the connection
catalog + stores (`cairn/core/connections.py`, ADR-0037 `cairn connect`), the
SecretStore (ADR-0033), the storage-unification epic (#427), and #392 (SaaS
foundation). Supersedes ADR-0048's "workspace is the tenant" stance.

## Context

Today cairn is effectively single-tenant:

- **Auth** is a single hard-coded admin (`OBS_API_USER`/`OBS_API_PASSWORD`). No
  user store, no registration, no roles. One login for the whole deployment.
- The top-level grouping is the **workspace** (ADR-0048/0051). The prior SaaS
  sketch leaned on *workspace-per-tenant*.
- **Connectors** (`connections.py`) store secrets as *references* into the
  SecretStore (never raw values — the anti-leak primitive), but the store is
  flat/global: no tenant scope.

The owner wants: an **admin panel** to create users (username/password) and
assign them; users **connect/disconnect/delete** their own LLM keys + GPU
providers with **no cross-account leakage**; and the explicit reframe that
**workspace ≠ account** — *one account holder has many workspaces, and
connectors are tied to the ACCOUNT, not the workspace.*

## Decision

**1. One tenant entity: `Account`.** An Account is the billing / credential /
isolation boundary. It **owns** workspaces and connectors and **has members**
(users) with roles. This *replaces* the workspace-as-tenant stance of ADR-0048:
the tenant boundary moves up one level.

```
Account (tenant · billing · connectors · isolation)
├── Members: User ↔ Account, role ∈ {owner, admin, member}
├── Connectors  (account-scoped; shared across the account's workspaces)
└── Workspaces  (many per account; the existing ADR-0051 entity, now child of Account)
```

**2. Do NOT build a separate `Organization` noun.** A solo user is an Account
with one member. Model **membership + roles from day one** even when most
accounts have one member — retrofitting a tenant boundary later is the worst SaaS
migration. Team sub-groups *inside* an account can come later if needed.

**3. Onboarding is admin-invite only.** An admin creates users / sets passwords
/ assigns them from the panel. No public self-serve signup in this phase.

**4. Connectors are account-scoped, credentials write-only.** Every connector row
carries an indexed `account_id`, **enforced at the query layer** — a resolver
refuses cross-account reads (extends `ScopedSecretStore`). A pasted credential
goes to the secret backend keyed by the account and is **never returned** to the
API/UI (write-only); "delete" **purges the secret value**, not just the row. The
resolved value is read worker-side only, within the account's scope.

**5. `workspace_id` stays; `account_id` is added above it.** Workspaces remain
the ADR-0051 project/env grouping; they gain an owning `account_id`. Account-owned
resources (connectors) are keyed by `account_id`; run/workspace-owned resources
keep `workspace_id` and inherit their workspace's account.

## Consequences

- **Migration:** every account-or-workspace-scoped table gets `account_id`
  (backfilled to a single `default` account for existing/OSS single-tenant
  installs). This is the reason to do it *now*, in the same touch as the
  storage-unification epic (#427), which is already adding Postgres backends to
  these stores.
- **OSS vs SaaS:** OSS = one `default` account, one admin, invite disabled — no
  behavior change for single-tenant users. SaaS = account-per-tenant + members.
- **Auth:** a real user store + password hashing (reuse the argon2 path) +
  membership/roles + session→account resolution. The middleware scopes every
  request to the authenticated user's account.
- **Isolation is testable:** a required test proves account B cannot read account
  A's connector/secret — the acceptance gate for the credential-isolation claim.

## Phasing (#392)

1. **Identity & tenancy** — `Account` + `User` + `Membership(role)` entities +
   multi-user password auth + the **admin panel** (create user, set password,
   assign to account/workspace).
2. **Account-scoped connectors** — `account_id` on connectors, write-only creds,
   connect/disconnect/**delete-purges-secret**, query-layer isolation + the
   cross-account-denial test.
3. **GPU connectors + lifecycle** — the new providers (Lambda/JarvisLabs/Together)
   + guaranteed terminate-on-end/cancel. Rides on the connector-catalog work.

## Alternatives considered

- **Keep workspace as the tenant** (ADR-0048 original). Rejected: contradicts
  "one holder, many workspaces, shared connectors," and forces connectors to be
  re-pasted per workspace.
- **Separate `Account` and `Organization` entities.** Rejected: two entities for
  one concept; the members-list-of-one models a personal account cleanly.
- **Self-serve signup now.** Deferred: not needed for the internal/controlled
  deployment; adds email-verification/abuse surface.
