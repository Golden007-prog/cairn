### 24.23 Decision: RAG indexing lifecycle — harvest `docs/rag-index.md`, idempotency-first, durability deferred

**Status: backlog (decisions locked 2026-06-11, build not started).** Source:
the untracked design note `docs/rag-index.md` (AgentOps RAG Index Job
Guidelines). This section records what we adopt, what we reject, and the
open forks — so the doc itself can be treated as harvested, not as a plan
to execute wholesale.

#### 24.23.1 Reframe — most of the pipeline already exists

The doc reads greenfield, but ~70% of what it proposes to build already
ships in `cairn/services/rag/`:

| Doc proposes (operator) | Already in repo |
|---|---|
| LlamaIndex Workflow `rag/llamaindex_index` | `services/rag/ingest.py` — LlamaIndex Workflow: router → parse → chunk → dense+sparse embed → upsert |
| Multi-format parsing | `services/rag/readers.py` — PDF/HTML/MD/RST/OpenAPI/JSON/YAML/CSV/notebooks |
| `embedding/*` operators | `services/rag/embeddings.py` — pluggable `EmbeddingProvider` (gemini/openai + BM25 sparse) |
| `vector/*` operators | `services/rag/stores/` — pgvector, qdrant, pinecone, sqlite_vec over `base` |
| Query runtime + evidence/citations | `services/rag/query.py` — hybrid RRF + rerank + cited synthesis; `operator-rag-local` wraps it per `[requires.rag.<corpus>]` |

So the doc's pipeline / vector / embedding operators are **redundant** —
do not rebuild. The genuine gap is the **lifecycle layer** around the
existing pipeline.

#### 24.23.2 DECISION — drop durability for the index job (idempotency-first)

No Temporal / Restate / Prefect for RAG indexing now.

- **Why it's safe:** content-hash idempotency at chunk granularity makes
  "resume" ≡ "re-run + skip-done" via manifest comparison. A crashed job
  re-runs cheaply and skips completed chunks by hash — durability's main
  payoff (don't redo completed work) comes free from idempotency + a
  catalog, even for a half-embedded large document.
- **Failure handling without an engine:** per-document try/except →
  `partial_completed` + `failed_documents[]`; embedding rate-limit /
  transient vector error → simple per-step retry/backoff. No workflow
  engine required.
- **Scheduling is separate:** periodic / on-change re-index is a *trigger*
  concern (k8s CronJob / APScheduler / system cron), not durable
  execution — consistent with §3.4 ("no separate Prefect needed").
- **When to revisit:** add durability ONLY when a single run crosses the
  size/cost line (thousands of docs, material embedding $ where
  re-scanning on crash wastes real money). At that point it slots in
  behind the doc's generic `WorkflowExecutor` interface, fired by a
  scheduled-skill trigger — implementation upgrades, interface stays.
- **Net effect:** the doc's three layers (Core + Prefect + LlamaIndex)
  collapse to **two** — control logic (plan + catalog + incremental) over
  the existing `services/rag` pipeline. Prefect drops out entirely
  (re-affirms §3.4 / §24.22).

#### 24.23.3 Adopt as-is (the real prize)

- **Content-hash idempotency scheme** (doc §Idempotency): `document_id`,
  `document_hash`, `chunk_id`, `embedding_id`, `index_job_id` as
  deterministic sha256s. Backend-agnostic; take roughly verbatim.
- **Incremental rules** (doc §Incremental Indexing): re-index when file
  hash / chunking config / embedding model / parser / metadata-policy
  changed, or doc added/deleted; skip when all unchanged. Tombstone
  deleted files; upsert-by-chunk-ID.
- **Normalized status model** (doc §RAG Job Status): pending / running /
  completed / failed / cancelled / partially_completed / requires_attention.
- **Structured partial result** (doc §Failure Handling): explicit
  `documents_indexed` / `chunks_indexed` / `failed_documents[]`.
- **Indexing-vs-query separation:** indexing at install/update/schedule
  lifecycle; query at template runtime (query path already exists).

#### 24.23.4 Constraints to respect (LOCKED surfaces this must not violate)

- **No `type: rag` template node** — not in the §24.20.8 10-node vocab.
  Model query as an `operation` calling a `rag.query` operator (exists);
  model indexing as a skill, not a new node type. New node type ⇒ §24.x.
- **No Jinja in bindings** — the doc's `query: "{{ incident.summary }}"`
  violates §24.20.6. Use `$input.*` / `$state.*`.
- **`rag index` is not in the locked 10 CLI verbs** (§24.20.14). Either
  open a §24.x to add it, or drive indexing via an existing surface
  (skill trigger / `run`). Decide at build time.
- **MarkItDown deferred** — `readers.py` + LlamaParse already cover the
  runbook/service-doc formats that matter. MarkItDown (DOCX/PPTX/XLSX
  breadth) is a later optional `document/markitdown_convert` operator
  (`core_safe=False`, `convert_local` only), not MVP.

#### 24.23.5 Open forks — RESOLVED 2026-06-12

- **Fork B — declaration split → PROFILE-owned build config (thin pack).**
  Build config (parser / chunk size / embedding model+dim / vector store) is a
  *tech choice* and therefore a **PROFILE** concern per the three-layer model
  (ADR-0026: PACK = semantic intent, PROFILE = how). The pack's
  `[requires.rag.<name>]` stays **consumption-only** (corpus/access/freshness) —
  **no production-side manifest section is added**, so packs stay portable
  across embedding/vector backends. The indexer resolves build config from the
  active profile + provider settings; the catalog records the *resolved*
  `build_fingerprint` so a model/chunk/parser change triggers re-index.
  (Rejected: a `[provides.rag.<name>.build]` manifest spec — couples packs to
  tech and adds a lockable surface for no portability gain.)
- **Fork C — catalog + incremental → core/storage catalog, file-granularity,
  skill-driven.**
  - *Catalog home:* a new `RagCatalogStore` in `core/storage`, mirroring
    `SqliteRunStore` (JSON blob + indexed filter columns), in-memory + SQLite
    tiers now (Postgres later), added to `StorageBackend`. Source of truth is
    the catalog DB; a `rag-plan.json` is optional dry-run *output*, not state.
  - *Comparison keys:* `content_hash` (sha256 of file bytes) + `build_fingerprint`
    (sha256 over resolved parser/chunk/embed-model/dim/store). Re-index when
    either changes; tombstone deleted sources (`delete_by_source` exists);
    skip when both unchanged. This fixes the current correctness bug —
    `ingest_document` skips any path it has already seen, so a *changed* file is
    never re-indexed today.
  - *Granularity:* **file-granularity MVP** — changed file = `delete_by_source`
    + re-ingest whole file. Chunk-level skip (per-chunk hashes + stable
    chunk-ids; the doc's "skip completed chunks" resume payoff) is a documented
    follow-on, valuable mainly for very large docs / expensive embeds. (Stores
    expose `delete_by_source`/`list_sources` but not chunk-id listing, so
    chunk-level needs the catalog to own chunk hashes — deferred.)
  - *Drive surface:* a **lifecycle skill** fired on install/update + scheduled
    freshness triggers (APScheduler/cron) — "indexing as a skill, not a node"
    (§24.23.4). **No** `rag index` CLI verb is added (keeps the 10 locked verbs
    frozen, §24.20.14).

#### 24.23.5.1 Resulting build shape (MVP)

1. `services/rag/idempotency.py` — deterministic sha256 helpers (`document_id`,
   `content_hash`, `build_fingerprint`) — adopted ~verbatim from the doc.
2. `core/storage` `RagCatalogStore` (Protocol + in-memory + SQLite) + a
   `StorageBackend.rag_catalog` field.
3. `services/rag/plan.py` — pure `RagIndexPlan` + `plan(files, catalog,
   build_config) → {to_index, to_skip, to_delete}`.
4. `services/rag/indexer.py` — orchestration over the existing
   `ingest_document`: scan corpus → plan → ingest/tombstone → update catalog;
   normalized status model + structured partial result (§24.23.3).
5. (Slice 2) the lifecycle drive surface + freshness trigger wiring.

#### 24.23.5.2 Slice 2 — DONE 2026-06-12 (drive surface)

- `services/rag/lifecycle.py` — `discover_corpora` resolves every loaded pack's
  `[requires.rag.<name>]` to a `CorpusTarget` (pack-qualified catalog id
  `{pack}/{name}`, collection `rag_{name}` to match the local query provider,
  on-disk root from `pack.rag_dir`'s parent); `index_all` runs the
  install/update pass; `autoindex_enabled()` gates on `OBS_RAG_AUTOINDEX`
  (**opt-in, off by default** — keyless local-dev pays nothing, matching
  redaction/audit); `check_backend_alignment()` warns when `RAG_VECTOR_STORE`
  diverges from the bound query provider's backend.
- `services/rag/schedule.py` — `RagIndexScheduler`, a **sibling** to
  `SkillScheduler` reusing the same Tier-1 apscheduler, firing `index_corpus`
  directly. **Deviation from the Fork-C "skill" wording, with cause:** a
  `SkillSpec` requires a template and exists to compile an agent pipeline +
  propose actions — indexing is a lifecycle side-effect, not a pipeline, so
  routing it through the skill engine would force a dummy template + a
  custom-logic hack. The ADR constraint ("indexing as a skill, *not a node*")
  is about not adding a `type: rag` node, and is satisfied: no node, no CLI
  verb. Freshness → cron: `hourly`/`daily`/`weekly`/raw-cron schedule;
  `on_change`/`manual` get no job (startup pass + cheap incremental cover them).
- Wired into `build_app` startup/shutdown (gated on `OBS_RAG_AUTOINDEX`); rag
  jobs surface on `GET /triggers/scheduled`.

**Follow-up (no core change when done):** `operator-rag-local` hardcodes
`SqliteVecStore` instead of routing through `get_vector_store()`. Fixing that so
index + query share whichever backend `RAG_VECTOR_STORE` selects makes
qdrant/pinecone swap in via config/binding with **zero core-interface change**
(backends already sit behind the `VectorStore` ABC + the `rag.search`
capability). Separate slice; until then `check_backend_alignment()` nudges.

#### 24.23.6 What this section closes

- The doc is treated as **harvested**, not as a plan: pipeline/vector/
  embedding/query layers are already shipped; Prefect + the durable index
  job are rejected for now; the catalog + idempotent-incremental lifecycle
  is the adopted core, deferred to backlog pending Forks B and C.
