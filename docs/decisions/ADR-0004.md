### 24.4 Decision: unified storage strategy

**Today's situation.** State is sprawled across five stores:

| Concern | Today's store |
|---|---|
| Runs + events | `SqliteInvestigationStore` (dispatcher) + JSONL (CLI) |
| Memory (episodic) + vectors | Qdrant |
| RAG corpus + vectors | Qdrant |
| Sessions / approvals / budgets | Not formalized |
| Temporal/Restate state | External (Restate today, Temporal post-§24.2) |

That's the sprawl to collapse. Goal: **one default store per tier**,
with optional per-concern swap-ins for power users.

#### 24.4.1 Tiers

**Tier 1 — dev (default, zero infra):**
- **SQLite** for all relational data.
- **`sqlite-vec`** extension for vector data (same DB; no separate
  process).
- JSONL stays as a human-friendly view onto runs (grep-friendly artifact).
- Configured via single env var: `OBS_STORAGE=sqlite:///./.cairn.db`
  (the default if unset).

**Tier 2 — prod (default for real deployments):**
- **Postgres** for all relational data.
- **`pgvector`** for vector data (same instance).
- Configured via single env var:
  `OBS_STORAGE=postgres://user:pass@host:5432/cairn`.

**Tier 3 — optional swap-ins:**
- Override individual concerns when a specialized store is wanted.
- `OBS_TRACES=clickhouse://...` (events stream analytics)
- `OBS_MEMORY=qdrant://...` (advanced vector ops)
- `OBS_RAG=qdrant://...` (RAG retrieval)
- (Temporal/Restate state still lives in its own backing store —
  external concern, not duplicated here.)

#### 24.4.2 Storage abstraction layout

```
cairn/core/storage/
├── __init__.py          # build_storage() factory + StorageBackend wiring
├── protocols.py         # all *Store Protocols
├── schema/
│   ├── sqlite.sql       # canonical SQLite + sqlite-vec schema
│   └── postgres.sql     # canonical Postgres + pgvector schema
├── sqlite/              # SQLite + sqlite-vec implementations
│   ├── runs.py
│   ├── events.py
│   ├── memory.py
│   ├── rag.py
│   ├── sessions.py
│   ├── checkpoints.py
│   ├── approvals.py
│   └── budgets.py
├── postgres/            # Postgres + pgvector implementations (same shape)
│   └── ...
└── backends/            # optional Tier-3 swap-ins
    ├── qdrant.py        # MemoryStore + RAGStore
    └── clickhouse.py    # EventStore
```

`StorageBackend` is one injectable object exposing every concern:

```python
class StorageBackend:
    runs: RunStore
    events: EventStore
    memory: MemoryStore
    rag: RAGStore
    sessions: SessionStore
    checkpoints: CheckpointStore
    approvals: ApprovalStore
    budgets: BudgetStore
```

Built once at engine startup from env. Injected into Dispatcher / Runner
/ CLI / chat endpoint. Every consumer reads its concern off the same
object.

#### 24.4.3 Canonical schema (the part hardest to change later)

```sql

CREATE TABLE runs (
  id              TEXT PRIMARY KEY,
```

#### 24.4.4 Decision: sqlite-vec, not Chroma, for the dev tier

Both are credible. sqlite-vec wins because:

| | sqlite-vec | Chroma |
|---|---|---|
| Process count (dev) | 0 (extension in same SQLite) | 1 separate process |
| Backup story | `cp database.db` | DB + Chroma artifacts |
| Migration consistency | one SQL file | DB + Chroma migrations diverge |
| Same mental model as prod | yes (both SQL-native, both sit in the RDBMS) | no (Chroma ↔ pgvector mental gap) |

Chroma stays a valid Tier-3 swap-in (`OBS_RAG=chroma://...`) for users
who want its features, but it isn't the default.

#### 24.4.4b Architectural note: vector backends live in `services/rag/stores/`

**Correction to the earlier P4.8 sketch.** The vector backend drivers
(qdrant, pinecone, pgvector, future sqlite-vec) are NOT in
``core/storage/`` — they live in ``cairn/services/rag/stores/`` as
:class:`VectorStore` subclasses, selected by ``RAG_VECTOR_STORE`` env.
The high-level :class:`~cairn.core.storage.HybridRagStore` (and
:class:`~cairn.core.storage.EpisodicMemoryStore`) delegate to
:func:`cairn.services.rag.stores.get_vector_store` under the hood, so
swapping the driver is a one-branch change in the factory.

To add a new vector backend:
  1. Drop a file at ``services/rag/stores/<name>.py`` subclassing
     :class:`VectorStore`.
  2. Add an ``if name == "<name>"`` branch in
     ``services/rag/stores/__init__.py``.
  3. Set ``RAG_VECTOR_STORE=<name>`` to activate.

The §24.4.7 phase plan stands — pgvector lands in this driver layer,
sqlite-vec will land here too (not under ``core/storage/sqlite/`` as the
earlier sketch implied). The ``core/storage/`` layer is the Protocol
home + the pack-facing wrappers, not the per-backend driver home.

**Status update (P4.8 done):**

- ``pgvector.py`` shipped as dense-only (sparse silently accepted,
  hybrid TBD via tsvector FTS). Optional dep group ``rag-pgvector``
  pins ``asyncpg>=0.29`` + ``pgvector>=0.3``. Lazy connection pool,
  HNSW index, JSONB-containment filters, SQL-injection-safe collection
  naming. 13 structural tests; ~270 LoC.

- ``sqlite_vec.py`` shipped as dense-only (sparse upstream-in-flight).
  Optional dep group ``rag-sqlite-vec`` pins ``sqlite-vec>=0.1``.
  Two-tables-per-collection design (vec0 virtual table for vectors,
  companion table for id/source/payload, joined by rowid). **Defaults
  to the same SQLite file as :class:`SqliteRunStore`** — the §24.4
  Tier-1 "one file for everything in dev" promise lands automatically.
  ``OBS_SQLITE_VEC_DB`` env overrides for split-file deployments.
  24 tests (3 end-to-end roundtrip with dep installed, 21 structural).

With both backends shipped, the §24.4 storage tier picture is:

  - **Tier 1 (dev default, zero infra)**: SQLite + sqlite-vec — one
    file. ✓ available today.
  - **Tier 2 (prod)**: Postgres + pgvector — same instance. ✓ vector
    side available today; ``PostgresRunStore`` for runs/events lands
    in §24.4 P5 proper.
  - **Tier 3 (optional swap-ins)**: Qdrant ✓ (default today), Pinecone
    (stub).

#### 24.4.5 Checkpoints — skip for MVP

LangGraph runs in-memory today; crash-mid-run loses state. The
`checkpoints` table above gives crash-resume, but adds write volume per
node.

**Defer.** Rely on Temporal (post-§24.2) for durability when it's
actually needed. The in-process runtime stays ephemeral. The
`checkpoints` table can be schema-defined but unimplemented — empty
until a future phase wires it.

#### 24.4.6 CLI replay — JSONL stays primary, DB mirror added later

Today CLI writes JSONL. After Phase 1 of storage, CLI ALSO writes to the
DB so `cairn ls runs` works and eval can target past runs. JSONL is
regenerable from DB at any time; it stays as the human-friendly grep
artifact.

#### 24.4.7 Phased migration

| Phase | Scope | Effort |
|---|---|---|
| **Phase 1** | Storage Protocols + SQLite/sqlite-vec impl for **runs / events / memory / RAG**. Wrap existing `SqliteInvestigationStore`; wrap Qdrant memory under `MemoryStore`. | ~3 d |
| **Phase 2** | Postgres + pgvector impl of the same four stores. | ~2 d |
| **Phase 3** | New stores: **sessions, approvals, budgets**. Required for real chat + multi-user + cost gating. | ~2 d |
| **Phase 4** | Optional Tier-3 swap-ins (Qdrant, Clickhouse). Temporal as `CheckpointStore` if we revisit §24.4.5. | ~3 d |
| **Total to "Tier 1 + Tier 2 with all 8 stores"** | | **~10 d** |

Phase 1 alone halves today's sprawl.
