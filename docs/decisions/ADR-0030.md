# Source layout — kind-first; a tier move is a metadata edit, not a code change

## Context

ADR-0027 classifies every pack on two orthogonal axes — **`kind`**
(`domain` / `operator` / `service_provider`) and **`trust_level`**
(`builtin · official · community · private · local`). The filesystem can only
make one of those axes the outer directory level. The original layout chose
**trust-level-first**:

```
cairn/
├── builtins/        # trust_level
│   ├── packs/incident/
│   ├── operators/        # 6 substrate operators
│   ├── profiles/
│   └── connectors/
└── official/        # trust_level
    ├── operators/        # 4 incident operators
    └── packs/            # empty scaffold
```

Two problems showed up once it was populated:

1. **Promotion crosses the top level.** ADR-0027's headline promise is
   "promote builtin→official is a directory move, not a rewrite." But a
   promotion only ever changes *trust_level*, never *kind* — yet trust-first
   made it a move across the **outermost** boundary
   (`builtins/operators/git` → `official/operators/git`).
2. **Operators are scattered.** "Show me every operator" spans two top-level
   trees. And `profiles/` + `connectors/` — which have no trust_level at all —
   were buried under `builtins/`, implying a trust tier they don't have.

## Decision

### 1. Invert to **kind-first**

```
cairn/
├── operators/
│   ├── builtins/    # mcp, memory_local, artifact_local, rag_local,
│   │                #   redact_regex, audit_store  (engine substrate)
│   └── official/    # clickstack, git, blast_radius, postmortem  (domain add-ons)
├── packs/
│   └── incident/    # the one domain pack — FLAT (see §3)
├── profiles/        # local-dev.toml, secure.toml   (no trust_level)
├── connectors/      # github/slack/notion specs      (no trust_level)
├── core/  services/  cli/
└── integrations/    # observability backend lib — NOT a tier (see §4)
```

The **stable** axis (`kind`) is the outer group; the axis that actually
changes on promotion (`trust_level`) is the leaf. Promotion is now a shallow
rename **inside one kind tree** (`operators/builtins/git` →
`operators/official/git`) — which is exactly what promotion *is*.

### 2. Locked invariant — **a tier move never breaks code**

This is the load-bearing guarantee, and it already holds by construction
(verified 2026-06-13). Nothing a consumer touches encodes the tier:

| Surface | What it keys off | Tier-dependent? |
|---|---|---|
| Operator wheel import path | `operator_<name>` (own `src/` package) | **no** — decoupled from filesystem tier |
| Profile bindings / `[requires]` / templates | operator **capability name** (`git/correlate`, `redact/text`) | **no** |
| Operator registry | flat `name → OperatorEntry` map | **no** — keyed by name |
| `trust_level` field | advisory metadata; `manifest.py` enforces nothing, resolves nothing by it | **no** |
| Discovery | shipped tiers → filesystem walk of `operators/{builtins,official}`; `local`/`community`/`private` → entry-point group `cairn.operators` | both merge into the **same** name-keyed registry |

So moving an operator **builtins ↔ official ↔ local** changes exactly three
things, none of them a consumer reference:

- its **directory** (`git mv`),
- its `trust_level` field (a metadata edit that *should* match the new tier),
- **how it is discovered** — in-tree tiers (builtins/official) are found by the
  filesystem walk; moving *out* to `local`/`community`/`private` means the
  operator leaves the engine wheel and registers via the `cairn.operators`
  entry-point instead. The operator's **name is identical** across that
  boundary, so every binding, `[requires]`, template, and Python import keeps
  resolving.

**Rule, locked:** no code may reference an operator (or pack) by its tier or
filesystem path — only by its stable capability name. `trust_level` stays
advisory (distribution/signing/install-policy metadata); it must never become
a resolution or routing key. A regression guard asserting the registry yields
the same names regardless of tier directory keeps this honest.

### 3. `packs/` stays **flat** until a second pack exists

There is one domain pack (`incident`, builtin) and zero official packs.
`packs/builtins/incident` would be premature structure and uglify the import
path (`cairn.packs.builtins.incident`). Decision: keep `packs/incident`
flat with import path **`cairn.packs.incident`**; the lock manifest records
all `packs/*` as `trust_level=builtin` for now. The day a second pack arrives,
`packs/` gains the same `{builtins,official}` nesting as `operators/` — same
rule, applied when it becomes load-bearing.

### 4. `integrations/` is **not** a tier — left in place

`cairn/integrations/observability/` is the shared, vendor-agnostic
`ObsBackend` protocol + vendor impls (ClickStack/OTel/mock) + telemetry query
tools that the incident pack, three official operators, and `services/mcp` all
wrap. It is neither an operator nor a pack nor a trust tier, so it does **not**
move under `operators/` or `packs/`. Its real awkwardness — observability-*domain*
code sitting as a peer of the domain-neutral `core/` — is acknowledged but
**out of scope here**: 5+ wheels import `cairn.integrations.observability.*`,
so its placement is its own future decision. This ADR leaves it untouched.

## Consequences

- Mechanical rename, history-preserving (`git mv`). Blast radius, all
  enumerated: incident entry-point + import path (`cairn.builtins.packs.incident`
  → `cairn.packs.incident`), `loader._SHIPPED_OPERATOR_PACK_DIRS`,
  `lock.py` tier table, `presets._CONNECTORS_DIR`, profiles import path,
  uv workspace members + hatch excludes, 3 `status.yaml` probes, the
  regenerated `cairn.lock`, README + ADR-0027 cross-refs.
- No operator wheel import name changes; no capability name changes; no
  binding changes. The suite + `audit_status` + `lock --check` verify green.
- ADR-0027's taxonomy is unchanged — this ADR only fixes which axis the
  *filesystem* makes outer, and locks the move-safety invariant ADR-0027
  promised but never stated as a guarantee.
