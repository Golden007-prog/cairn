# ADR-0043 — Remote compute over SSH (`remote/exec`) + the NATS remote-worker channel

Status: Accepted (2026-06-27) — Slice 1 + Slice 2 built
Relates to: ADR-0038 (long-running control loop — operator-runner + events-up/control-down), #70 (Axis-2 external compute), #115/#50 (NATS JetStream), #127 (control loop).

## Context
Users often run the workflow **locally** but have **direct access to raw CPU/GPU boxes** (a lab server, an EC2 instance, a workstation). Today the only remote-compute operators are GPU-marketplace-specific (RunPod/Vast/Modal/Kaggle APIs) — there's no way to dispatch a job to *a box you own over SSH*. The substrate to do it already exists:

- the `remote_job` executor + lifecycle (`RemoteJobOperator` submit/poll/cancel, `run_job_lifecycle`, `RemoteJobDriver`);
- `RemoteJobStore` with a `channel` field for **event/control subjects** (the NATS seam);
- a **real NATS JetStream** implementation (the #115 trigger inbox: connect/stream/publish/ack/DLQ/replay, behind the `[nats]` extra) — proof the JetStream substrate works;
- the control loop (`drive_once`/`run_control_loop`) and the connection model.

## Decision

### 1. `compute.ssh` connection
`cairn connect ssh` → a `compute.ssh` connection: `{host, user, port, known_hosts}` + the **private key held in the SecretStore** (`SSH_PRIVATE_KEY`). Resolved into `ctx.compute` like any compute target.

### 2. `remote/exec` operator (generic, not training-specific)
A `RemoteJobOperator` over **asyncssh** (cap `remote.exec`, `[ssh]` extra):
- **submit** — connect, make a workdir, SFTP-upload inputs, launch the command **detached** (`nohup`, pid recorded);
- **poll** — read the captured exit code; on success SFTP-fetch outputs + parse a `metrics.json` (so the model gate / learning gate get real metrics, same as the providers);
- **cancel** — kill the pid.

Training is a **use** of it, not a bespoke operator — matches "raw compute access." The first consumer is the `run-train-remote` binding (built): it targets `remote/exec` with command = `cairn-train-local`, maps the training inputs to `CAIRN_*` env, and fetches `metrics.json` + the adapter. On the box, `cairn-train-local` runs the **same `_train_local`** plain-LoRA trainer as `train/local` (CPU/MPS, no CUDA-only deps) — NOT `train_entry`, which is Unsloth/GPU-only. This is the escape hatch for a torch-less orchestrator (Intel-Mac/py3.13): the box does the torch training, cairn stays the governor. Prereq: a `compute.ssh` connection (`execution.compute_target`) + `operator-training[local]` installed on the box.

### 3. Safe SSH (non-negotiable)
asyncssh; **key-based** (Ed25519 recommended), key from the SecretStore; **host-key verification via `known_hosts`** — `None` falls back to the system file which *rejects* unknown hosts; **never `()`** (which disables checking → MITM). The command is the workflow author's, written to a script file and run there — not shell-interpolated from untrusted input.

### 4. Two slices
- **Slice 1 (this ADR, built):** `compute.ssh` + `remote/exec`, **poll-based** on the existing `run_job_lifecycle`. Delivers the capability immediately, no NATS needed.
- **Slice 2 (this ADR, built):** the **live NATS remote-worker channel** (`cairn/core/operator/job_channel.py`). A `RemoteJobChannel` Protocol with two impls — `InMemoryJobChannel` (tests/dev) and `NatsJobChannel` (JetStream, reusing the inbox's connect/stream pattern; last-value via `get_last_msg`). The worker-side `JobReporter` publishes heartbeat/loss/metrics **up** (`heartbeat`/`succeeded`/`failed`) and polls an abort **down** (`aborted`). The local side is just two drop-in callables — `build_channel_poll` / `build_channel_cancel` — that read the latest event → `JobStatus` (carrying `eval_losses`) and publish abort to the control subject. They feed the **existing** `drive_once`: the learning gate (ADR-0039) and the resume-via-`RunDispatcher.resume_run` are **unchanged** — so the control loop is the NATS↔orchestrator bridge and the **workflow never speaks NATS** (it pauses at `remote/exec` and resumes). Durability: state lives in Temporal+Postgres + JetStream (durable last-value), not in the worker or the loop. Subjects: `cairn.jobs.<run_id>.{events,control}` under one stream. Verified end-to-end with the in-memory channel incl. the learning-gate abort; **live NATS verify is pending** (`nats-py` isn't in the dev venv — same gap as the inbox).

## Consequences
- New: a `compute.ssh` kind + the `remote/exec` operator (Slice 1). Reuses the executor, lifecycle, control loop, connection model, and (Slice 2) the JetStream substrate — **no new durability machinery.**
- The Temporal workflow stays transport-agnostic: the same pause/resume works whether the job ran on RunPod's API or your SSH box over NATS.

## Open
- **Live NATS verify** — `nats-py` isn't in the dev venv (same gap as the #115 inbox); `NatsJobChannel` is exercised by parity with the proven inbox JetStream pattern + the in-memory channel covers the loop integration. Verify on a box with the `[nats]` extra.
- **The remote operator-runner that *runs* `JobReporter`** — Slice 2 ships the channel + the worker-side reporter; wiring it into a long-running on-box runner (so `cairn-train-local` streams loss up + obeys abort) is the next consumer. Today `remote/exec` is poll-based (Slice 1); the channel poll is opt-in via `OBS_JOB_CHANNEL=nats://…` + `build_channel_poll`.
- `cancel` has no `ctx` in the control worker (#127) — Slice 1 SSH-cancel falls back to the ambient `SSH_PRIVATE_KEY`; the Slice 2 channel-cancel needs none (it just publishes abort).
