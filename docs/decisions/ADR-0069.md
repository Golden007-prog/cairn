# ADR-0069 — Bundle execution: a declarative, trigger-driven pipeline of governed runs

Status: Proposed (2026-07-13)
Supersedes: the **execution** half of ADR-0066 §Phase-2 (bundle → one flattened
LangGraph in `compile_bundle.py`). The **contract** half of ADR-0066 (the
compile-time typed `$steps` validation in `bundle.py`) is retained.
Relates to: `bundle.py` (contract + resolvers), `compile_bundle.py` (the flatten
being replaced), the dispatcher (`RunDispatcher.submit`), the event bus (transport,
ADR-0010) + the trigger server, `subgraph_node` (intra-template composition,
unchanged), and ADR-0068 (per-operator config gating — a step's internal gates use
it). NB: `BusSkillBridge` is the *userspace* event→skill path and is **not** reused
for step transitions — those are core-owned (§2).

## Context

A **bundle** chains packs into a multi-step pipeline. Today
(`compile_bundle.py`) a `[[bundle.pipeline]]` compiles to **ONE** LangGraph: every
step's behavior-tree nodes are spliced in sequence and each step's `gate`
predicate becomes a conditional edge routing to a shared terminal fail-node. So a
three-pack pipeline collapses into a **single run** — one `run_id`, one gate/report
boundary, one durable workflow, one failure domain.

That is wrong for cross-**pack** composition. Each step is an *entire pack* (with
its own subgraphs, gates, and lifecycle); packs are independently distributable
wheels; stages run at different times, on different machines (dataset prep on CPU,
training on a GPU box, serving long-lived), and each deserves its **own** governed
run — its own gate verdict, report, HITL approval, retry/resume, and audit. The
run is cairn's unit of governance; flattening N packs into one run erases N−1
governance boundaries.

`subgraph_node` (a template embedding another template's graph inline → one run)
is the *right* model for **intra-template** composition and stays. The question is
only the **cross-pack bundle** execution model.

**Prior art (both mature systems agree).** Prefect: tight = **subflow** (one run);
loose = independent **deployments** chained by **Automations** — a
`DeploymentEventTrigger` on the upstream `flow-run.Completed` event runs the
downstream deployment with parameters templated from the event; `emit_event`
publishes custom domain events; `run_deployment` is the manual path. Dagster:
tight = one **job / asset graph**; loose = **asset sensors** returning a
`RunRequest` (carrying upstream metadata into the downstream `run_config`) across
jobs *and code locations*, or **Declarative Automation**
(`AutomationCondition.eager()`), with **blocking asset checks** +
`all_deps_blocking_checks_passed()` as the gate. Neither uses a central imperative
loop — each downstream unit *declares when it runs* (an upstream event + a gate
condition) and the runtime fires it. Auto vs manual is just the trigger *source*
on the same unit.

## Decision

**A bundle pipeline compiles to a set of declarative TRIGGER-BINDINGS on the bus,
not a graph. Each step runs as its own governed run; the chain emerges from
per-step triggers + the gate condition + the typed data contract.** This mirrors
Prefect Automations / Dagster sensors + declarative automation, using cairn's
*existing* primitives.

### 1. `plan_bundle` replaces the flatten

`plan_bundle(BundleSpec) → PipelinePlan` — an ordered/DAG plan of steps with their
bindings, gate, and trigger. It does **not** build a graph. Each step's template
still compiles to its own graph on demand (the existing single-template compiler),
so a step that is a whole pack with multiple subgraphs runs exactly as a normal
template run. `compile_bundle.py`'s flatten path is retired for bundles (kept for
`subgraph_node`).

### 2. Each step = a trigger-binding — enforced by a CORE `PipelineBridge`

**Ownership (correction, 2026-07-13).** The step-to-step transition is a **governance
boundary** and is therefore owned + enforced by **platform core**, NOT by the skill
layer. An earlier draft said "reuse `BusSkillBridge`" — that is wrong: `BusSkillBridge`
activates **pack-authored skills** (userspace, discretionary automation — "my pack wants
to run on event X"). If a pipeline's gate lived there it would be pack-authored and
bypassable, and the gate becomes theatre (the same failure the ADR-0070 config-scoping
work designs against: governance is platform-enforced, never userspace-weakenable).

So the transition is a **new core `PipelineBridge`** (platform infrastructure, a sibling
of the dispatcher). It **reuses the bus as transport** and the trigger server, but **owns
the routing + gate evaluation itself** — never the skill-matching path. The bundle config
is **declaration only** (steps, `trigger`, `depends_on`, `gate` predicate, input wiring,
`approval`, `environment`); core reads that declaration and enforces it. The `gate` is a
declarative predicate core *evaluates* over persisted output — a pack can never inject code
into the transition. Two deliberately-separate mechanisms on the one bus:

| Mechanism | Layer | Semantics |
|---|---|---|
| `BusSkillBridge` (exists) | **userspace** | pack skills react to domain events — discretionary |
| `PipelineBridge` (new, core) | **platform** | pipeline steps advance — **gated + enforced + audited by core** |

For each step, the `PipelineBridge` registers a binding on the bus (transport) + trigger server:
- **activation (`trigger`)** — `auto` (fires when `depends_on` complete), `manual`
  (a human/API/CLI advances it), `schedule:<cron>`, or `on:<domain-event>`. The
  auto/manual duality is only the trigger *source*.
- **condition (`gate`)** — `eval_gate_predicate` (bundle.py, reused) against the
  upstream run's PERSISTED output; the downstream run is submitted **iff pass**
  (= Dagster's `all_deps_blocking_checks_passed`).
- **input map (data contract)** — `resolve_step_inputs` (bundle.py, reused) from
  the upstream run's persisted output → the downstream run's input (= Prefect
  templated params / Dagster `run_config`). Big values pass as **refs**
  (`staged_dataset_uri`, `adapter_uri`) — cairn already produces these.
- **action** — `dispatcher.submit(TriggerEvent(source="pipeline"|"manual",
  payload={template: step.ref, input: resolved, pipeline_id, step_id}))` → the
  step runs as its own governed run (its own internal gates/subgraphs/report/HITL).

### 3. Completion signal = a domain event on the bus

Each step, on completion, publishes a **domain** event
(`get_bus().publish("<pipeline>/<step>.done", {refs…}, correlation_id=run_id)`).
The bus's reserved `run.*` guard (ADR-0010) already forces *domain* topics for
activation — the same discipline as Prefect custom events / Dagster
materializations. A downstream `trigger = "auto"` binding subscribes to its
`depends_on` steps' completion events.

### 4. Optional pipeline-run owner (joins + observability)

Default chaining is fully declarative (bindings + bus). An **optional** lightweight
`pipeline_id` owner record groups the child `run_id`s and provides the two things
declarative-only can't: **multi-parent joins** (`depends_on = ["a","b"]` — step C
waits for both) and **watch/cancel-the-pipeline-as-a-unit**. This is the imperative
escape hatch both Prefect (controller flow) and Dagster (multi-dep condition) also
offer — demoted from the primary mechanism to an optional layer.

**Storage — the `pipelines` table.** The owner is a durable record, one row per
pipeline execution, living alongside the runs store (`cairn.core.storage`,
memory/sqlite/postgres backends). It mirrors the `Run` record at the *pipeline*
grain — the grouping `run_id`-as-the-unit already implies (pilots/experiments are
the same pattern):

```
pipelines
  pipeline_id      PK        # the grouping id (child runs FK back to it)
  bundle_ref                 # bundle name@version the plan came from
  pipeline_name              # [[bundle.pipeline]].name
  status                     # queued | running | paused | done | failed | cancelled
  plan             json      # resolved PipelinePlan snapshot (steps + bindings + gate + trigger)
  step_state       json      # step_id → {run_id, status, verdict, started_at, ended_at}
  cursor                     # active step(s) — scalar for linear, set for DAG/joins
  inputs           json      # the pipeline-level (bundle) input
  environment                # profile/env the pipeline runs under
  trigger          json      # what started the pipeline (source + payload)
  workspace_id               # tenancy scope (mirrors Run, #223)
  created_at / updated_at / ended_at
```

And the **runs** table gains two nullable columns so a child run points back at its
pipeline (a standalone run leaves them empty):

```
runs.pipeline_id   FK → pipelines.pipeline_id   (nullable)
runs.step_id                                     (nullable)
```

`status = paused` covers both a `manual` step awaiting an explicit advance and an
`approval` step awaiting HITL. On restart the owner resumes from `step_state`
(re-attaching to an in-flight child by its `run_id`, the adopt-by-id pattern remote
jobs use). Durability tier follows ADR-0036: an in-process record (dev) or a
Temporal workflow (prod). A `PipelineStore` protocol with memory/sqlite/postgres
impls mirrors the existing runs store.

### 5. Config surface changes (`bundle.toml`)

Authoring is mostly unchanged; the shifts are semantic + a few new optional keys:

```toml
[[bundle.pipeline.step]]
id = "train"
pack = "training"
template = "finetune-remote"
trigger = "auto"          # NEW: manual | auto | schedule:<cron> | on:<event>
depends_on = ["prep"]     # NEW (optional): explicit deps → DAG + multi-parent joins
gate = "$steps.prep.verdict == 'pass'"          # SAME syntax → now a TRIGGER CONDITION
environment = "gpu-prod"  # NEW (optional): per-step run targets its own env/box
approval = true           # NEW (optional): inter-stage HITL before this run submits
emits = "model.trained"   # NEW (optional): domain event published on completion
inputs = { dataset = "$steps.prep.staged_dataset_uri" }  # SAME syntax → resolved from PERSISTED output
```

| Key | Status | Change |
|---|---|---|
| `id` / `pack` / `template` | unchanged | still `pack/template` per step |
| `inputs` / `$steps.<id>.<field>` | same syntax, **new source** | from the upstream **run's persisted output** (a ref), not an in-graph channel |
| `gate` | same syntax, **new role** | the downstream **run's trigger condition**, not a conditional edge |
| `trigger` | **NEW** | `manual` \| `auto` \| `schedule:<cron>` \| `on:<domain-event>` |
| `depends_on` | **NEW (optional)** | DAG + multi-parent joins (default: previous step) |
| `environment` | **NEW (optional)** | per-step run on its own profile/box (GPU) |
| `approval` | **NEW (optional)** | inter-stage HITL pause |
| `emits` | **NEW (optional)** | domain event other bundles can chain off |

**Back-compat:** a step with no `trigger`/`depends_on` defaults to `trigger="auto"`
+ implicit linear `depends_on` (prior step) → the current ordered behavior, now as
separate runs. A pipeline-level `mode = "graph"` pins the legacy flatten during
migration.

## Consequences

- **Per-stage governance.** Each step is a real run: own gate verdict, report,
  audit, retry/resume, and **inter-stage HITL** (the trigger pauses for approval
  before submitting the next run) — impossible in the flattened graph.
- **Decoupled durability/failure domains.** A crash, retry, or code change scopes
  to one stage, not the whole prep→train→serve span.
- **Cross-time / cross-machine.** A step fires hours later on the GPU box; the
  binding just submits when its trigger + gate are satisfied. `environment`
  per-step is now expressible.
- **Packs stay independent.** Coupling is by *data contract* (the typed `$steps`
  wire), not shared graph state / schema-version lockstep.
- **Reuses everything except the enforcer.** Contract validation, the resolvers,
  single-template compile, `subgraph_node`, dispatcher, bus (transport), trigger
  server, HITL/resume — all reused. New code = `plan_bundle` + the **core
  `PipelineBridge`** (owns + enforces the gated transition; NOT `BusSkillBridge`,
  §2) + the optional owner record.
- **Cost:** loses the single-run atomic view + adds handoff latency and a durable
  medium requirement (the ledger — already there). For a genuinely atomic,
  tightly-coupled multi-template unit, `subgraph_node` remains the right choice.

## Console impact

The theme mirrors the engine: **every per-run / per-template view is reused
verbatim — a pipeline step IS a normal governed run — and a thin pipeline tier is
layered on top.** No per-run view is rewritten.

**Unchanged** (they render a single run / template): `WorkflowGraphTab` +
`GraphCanvas` (a step's internal graph), `WorkflowRunTab` / `RunDiagnosisView`
(per-run timeline), `PilotReportView` / `PilotReview` (report + HITL — reused for
inter-stage approval), `InsightsView` / `SuggestionsView` (per step-run),
`EnvironmentsView` (a step's `environment` points at an existing env).

**Changed** (gain a `pipeline_id` dimension, not a rewrite):
- **`WorkflowGraphTab` / `GraphCanvas`** → **two-tier**: a NEW coarse **pipeline
  DAG** (nodes = steps/packs; edges = `depends_on` / `$steps` contract wires; a
  **gate badge** per edge; a **trigger-source icon** per step) → click a step →
  drill into its existing template graph. Backend `build_graph_view` (#187) gains a
  pipeline-graph builder.
- **`RunsView`** → child step-runs **grouped under `pipeline_id`**: a parent
  pipeline row (rollup status) that expands to child runs. Individual rows/detail
  unchanged.
- **Audit** (`+workflow` column + export) → each step-run keeps its own
  hash-chained audit; gains `pipeline_id` + `step_id` columns **plus a NEW audit
  event: the inter-stage gate-as-trigger decision** ("prep gate PASS → train
  triggered"; "train gate FAIL → serve NOT triggered").
- **Replay** → single-step replay unchanged; NEW **"resume pipeline from step N"**
  — re-run one stage on the *persisted* upstream outputs without re-running
  upstream (cheaper partial replay the flattened graph couldn't do).
- **Results** → per-step artifacts unchanged; NEW pipeline rollup grouped by
  `pipeline_id`.
- **Triggers surface** → NEW pipeline-step trigger management: `manual` steps get
  an **Advance step** button, `auto`/`schedule`/`on:event` are shown, and
  `approval` steps get **Approve** actions.

**New**: a **`PipelineView`** (or a mode of `WorkflowsView`) — the pipeline *as a
unit*: the live DAG with per-step run status, gate verdicts on edges, trigger
badges, Advance/Approve buttons, and links into each step's run. Reads the
`pipelines` table (§4). The analog of Dagster's job/asset lineage view or Prefect's
cross-deployment flow-run graph.

## Alternatives considered

- **Keep the flatten (bundle → one graph).** Simple single-run view, but erases
  per-pack governance, couples durability/failure, and can't do cross-machine /
  inter-stage HITL. Rejected — it's why this ADR exists.
- **Imperative central coordinator as the PRIMARY mechanism** (a saga loop that
  submits → awaits → submits). Works, but neither Prefect nor Dagster leads with
  it — declarative event+gate triggers are more decoupled and make auto/manual a
  trigger-source choice. Kept only as the **optional** join/observability owner
  (§4).
- **Adopt Dagster/Prefect wholesale.** Re-platforms off LangGraph+Temporal +
  cairn's governance model. Rejected (see the framework build-vs-buy review); we
  adopt the *pattern*, not the platform.

## Decision rule (for authors)

> Does each stage deserve its own governed run (own gate/report/approval/lifecycle)?
> **Yes** → bundle pipeline (this ADR). **No, it's one logical operation** →
> `subgraph_node` (one run). The run boundary is the governance boundary.
