### 24.15 Decision: platform self-observability — OpenTelemetry-native

> **Provenance.** Surfaced during the §24.14 review (June 2026) by the
> question: "we can't use observability packs on our own platform if it
> breaks." The §24.14 brief-rejection table addressed customer-pack
> *integration* with Prometheus/Grafana/Loki; this section addresses the
> distinct concern of the platform's own observability under failure
> conditions.

**Status before:** The platform observes customer systems well (incident
pack reads ClickStack / Prometheus / etc.) and observes its own *skill
executions* well (JSONL traces + run/event store in Postgres). It does
**not** observe its own *infrastructure code paths* — dispatcher loop,
action handler health, MCP client latency, Restate/Temporal connection
state, storage backend health. When the platform itself breaks, the
incident pack can't be relied on to debug it (chicken-and-egg: the tool
you'd use is the thing that's broken).

The gap is real:

| Layer | What we emit today | Production-debuggable? |
|---|---|---|
| Python logs | `logger = logging.getLogger(__name__)` per `docs/conventions.md` | Only with external aggregation |
| Skill executions | JSONL traces + Postgres events | Yes — but only for SKILL runs, not platform code paths |
| Platform metrics (active runs, queue depth, MCP latency) | Nothing | **No** |
| Platform traces (dispatcher → runner → MCP → executor) | Nothing | **No** |
| MCP server health | Nothing structured | **No** |

**Decision: the platform itself emits OpenTelemetry (logs + metrics +
traces) natively. Customers route OTLP to the backend of their choice.
ClickStack remains the reference deployment.**

#### 24.15.1 Why OTLP-native, not a specific backend

This is the §24.13 + §24.14 integration pattern applied to platform
self-observability:

| Approach | Customer with Prometheus? | Customer with Honeycomb / Datadog / etc.? | Platform code change per backend? | Vendor lock |
|---|---|---|---|---|
| First-class Prometheus exporter | Works | Doesn't work (need adapter) | Per backend | High |
| First-class ClickStack only | Awkward (need to bridge) | Doesn't work | Per backend | High |
| **OTLP-native (this decision)** | Works (OTLP → Prom receiver) | Works natively | **Zero** | None |
| Custom telemetry format | Works only with our tools | Doesn't work | Per backend | Total |

OTel is the W3C-track standard. The OTel Python SDK is well-supported
and stable. The backend (Prometheus + Grafana + Loki, ClickStack,
Honeycomb, Datadog, Tempo, Grafana Cloud, etc.) is the **customer's
choice**. The platform doesn't know or care what's on the receiving
end of the OTLP socket.

This is **strictly better** than baking in any specific backend.

#### 24.15.2 Three primitives

| # | Primitive | Effort | What it gives |
|---|---|---|---|
| **O1** | **Platform OTel instrumentation** — OpenTelemetry SDK wired into every long-lived code path: dispatcher loop (run counts, queue depth, lane saturation), runner (skill timing, LLM latency, cost-per-run), action handler (saga step timing, retries, compensation triggers), MCP client (per-server latency, error rate), storage backend (query timing, pool stats), trigger server (webhook ingest rate, dispatch errors) | ~3–5 d | Platform code paths visible in any OTLP backend. Same metrics the brief lists for ModelOps now also cover platform health. |
| **O2** | **OTLP endpoint configuration** — single env var `OTEL_EXPORTER_OTLP_ENDPOINT` + standard OTel SDK env vars (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, etc.). Reference deployments: dev/demo → ClickStack on localhost; prod → customer's existing OTLP receiver | ~½ d | One config knob. No per-backend code. |
| **O3** | **Doctor `[self_observability]` category** — reports OTel exporter configured + reachable, sample-trace round-trip, per-component instrumentation presence | ~½ d | Doctor catches misconfiguration before it becomes a debugging-during-an-outage problem. |

**Total: ~4–6 d. Lands in P3** alongside the §24.14 Tier 1 work; same
operational hardening theme.

#### 24.15.3 What we explicitly REJECT (anti-pattern table)

| Rejected | Why |
|---|---|
| First-class Prometheus exporter in platform code | OTel SDK + OTLP → Prometheus receiver covers it. Zero platform code per backend. |
| Grafana dashboard provisioning in platform code | Dashboards are deployment-side. Ship reference dashboard JSON in `docs/observability/` for customers to import. |
| First-class Loki integration | OTLP logs export, Loki receives. Same pattern. |
| Custom telemetry format / bespoke metrics protocol | OTel is the standard. No bespoke. |
| Separate "platform observability" data store | The same OTLP receiver that handles customer telemetry handles platform telemetry. Single ops story per backend. |
| Vendor-specific SDKs (Datadog APM, New Relic agent, Honeycomb Beeline) | All are OTLP-compatible via standard receivers. Stay vendor-neutral. |

#### 24.15.4 Dogfooding payoff

Once §24.15 lands:

- **Incident pack can investigate the platform itself** — the platform's
  metrics + traces + logs appear in the same ClickStack the incident
  pack already queries via `read_logs` / `read_traces` / `read_metrics`.
  No special-case "platform metrics" reader needed.
- **Eval baselines extend to platform health** — a regression that
  doubles MCP client latency shows up in baseline comparison the same
  way an eval-quality regression does.
- **Doctor can self-diagnose** — `cairn doctor` reports on the
  platform's own emission pipeline health, catching observability
  outages before they hide a real outage.

#### 24.15.5 What this does NOT include

- **Customer's choice of OTLP backend** — Prometheus + Grafana + Loki,
  ClickStack, Honeycomb, Datadog, Tempo, etc. All work via standard
  OTel receivers. Platform stays neutral.
- **Reference Grafana dashboards** — ship as JSON assets in `docs/`
  (separate from platform code). One-off authoring per dashboard,
  not platform engineering.
- **Custom alerting rules** — customer's existing alerting stack
  (Alertmanager, Grafana alerts, PagerDuty integrations, etc.)
  consumes the OTLP-exported metrics. Not platform-side.
- **Distributed tracing across customer code + our platform** — works
  natively via OTel context propagation if customer instruments their
  own code with OTel. Out of the box.
