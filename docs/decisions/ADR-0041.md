# ADR-0041 — The cairn SDK: a Python client to the governed runtime (no workflow-authoring DSL)

Status: Proposed (2026-06-25)
Relates to: ADR-0026 (locked architecture — declarative composition + the `invoke_operator` chokepoint), ADR-0034 (HITL), ADR-0036 (runtime tiers), ADR-0038 (long-running control loop), #145 (governed sweep — the SDK's first consumer), #167 (SDK implementation).

## Context

Recurring pressure: "should cairn let you automate workflows as Python code, with its own library?" The phrase collapses four different surfaces — (1) **author** a workflow *as* Python (a DSL), (2) **run/embed** governed workflows from Python (a client), (3) a `python_node` inside a template, (4) operators (already Python). Only #1 is contentious; #3/#4 already exist as the code seams.

cairn's moat is **governance by construction**, which holds only because:
- the **composition is declarative data** (markdown state-machine + YAML bindings) — content-addressed, so a run is replayable and lineage/audit can say exactly what produced a result;
- **code is confined to operators** — every LLM/tool/IO call passes the `invoke_operator` chokepoint and inherits gates, redaction, cost ceiling, HITL, audit;
- therefore the gates are **non-bypassable**.

cairn also **compiles to LangGraph** — it sits *above* a Python graph engine specifically to add the governance layer.

## Decision

### 1. NO Python workflow-authoring DSL
Imperative workflow code can call an LLM/tool/API **around** the chokepoint (ungoverned), and isn't cleanly content-addressable (degrading replay/lineage). It would also collapse cairn's differentiator — a "cairn Python workflow DSL" is either a thin reskin of LangGraph (then just use LangGraph) or a reintroduction of the ungoverned code paths cairn exists to remove. **Authoring stays declarative.** If authoring DX hurts, the answer is a **codegen builder that emits the declarative artifact** (demand-gated), never a runtime DSL.

### 2. YES — a run/embed SDK (a thin, typed CLIENT)
A client to the governed runtime: it **runs templates**, reads results, resumes gates, queries lineage. It builds **zero** execution machinery — a veneer over `RunDispatcher` (in-process) and the trigger server's REST+SSE (remote).

**Boundary rule:** the SDK runs *templates*; it never lets you assemble operator calls imperatively (that would bypass the chokepoint). Client to the governed runtime, like a DB client — not a way to write the workflow.

### 3. Execution model — one governed run per call
Parallel/sequential is the **caller's Python**; governed composition is a **template**.

```python
import asyncio, cairn
cx = cairn.local()                                     # embed the engine
# parallel = the caller's concurrency; each is an INDEPENDENT governed run
reports = await asyncio.gather(*[cx.arun("training/finetune", t) for t in trials])
# sequential pipeline = ordinary Python over results
ds = cx.run("dataset/eval", {"dataset": "./d.jsonl"})
if ds.verdict != "fail":
    cx.run("training/finetune", {"dataset_path": "./d.jsonl"})
```

| You want… | Belongs in | Why |
|---|---|---|
| N independent runs (sweep, batch, glue) | **SDK + Python** | each run independently governed; the orchestration isn't part of any lineage |
| A flow replayable/gated **as one unit** | **a template** (`sequence`/`parallel`/`map`) | governed composition must be content-addressed data, not imperative Python |

A dependency-chained pipeline you want replayable as a whole is a **smell** → promote it to a template.

### 4. Two transports, one API
```python
cx = cairn.local()                                     # in-process (notebook / CI / single box)
cx = cairn.connect("https://cairn.acme", token=TOKEN)  # remote: HTTP to a deployed server (== `cairn remote`)
```

### 5. submit / await / attach — durability is a runtime-tier property, not an SDK feature
```python
run_id = cx.submit("training/finetune", req)           # returns immediately
async for ev in cx.stream(run_id): ...                 # SSE lifecycle events
cx.resume(run_id, {"approved": True, "approver": "alice"})  # HITL gate
report = cx.wait(run_id)
report = cx.attach(run_id).wait()                      # reconnect later — even after this process died
```
The deployment picks the tier (`in_process` ephemeral / `temporal+pg` durable / `dbos` durable-batch). The run lives in the **durable store, not the client**, so `attach`/`wait` work across SDK restarts and crashes — that *is* what durable means. The SDK implements none of it; it submits and reconnects by id. Blocking `run()` is `submit()`+`wait()` sugar.

### 6. Triggers — submit IS a trigger; inbound hosting stays server-side
`cx.run()`/`cx.submit()` is the manual/API trigger (the run records `trigger.source="sdk"`). Inbound triggers (webhook/alert/schedule → match → dispatch) remain the server's job (TriggerSpec, the #115 inbox, apscheduler); the SDK **manages their config** (`cx.triggers.*`) and **observes the runs they fire** (`cx.stream(run_id)`), but never hosts the inbound machinery.

## Consequences
- The SDK is thin (no new engine). First consumer: the #145 sweep drivers — replace `subprocess`+parse-stdout with `cx.run("training/finetune", trial)`.
- "Governed composition" pressure pushes users to templates (the correct place), keeping arbitrary side effects out of the flow.
- cairn exposes Python as a **client** and as **constrained nodes/operators**, never as a **workflow-authoring DSL** — the first is leverage; the last would dissolve the moat.
