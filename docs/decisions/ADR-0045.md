# ADR-0045 — cairn distribution (locked, portable deployable bundle)

Status: Accepted (v1 scope) (2026-06-29) — open questions resolved; v1 cut locked below.
Relates to: #209 (epic), supersedes #208; ADR-0017 / ADR-0029 (`cairn lock` + parked registry resolver), ADR-0020 / ADR-0026 (pack contract + locked architecture), #204 (operator dependency isolation), #205 (execution sandboxing), #185 (server-side install security), #206 (console IA — surfaces the install gap).

## Context

Today "installed" is a *discovery* fact, not a *recorded* one. A pack (domain or
operator) is a Python wheel installed into the engine's environment; at startup
`load_all_packs()` reads the `cairn.packs` / `cairn.operators` entry points into
an in-memory registry (`cairn/core/pack/registry.py`), and `/packs` is a live
`candidate_templates()` walk of each pack's `templates_dir`
(`cairn/ask/resolve.py`). There is:

- **no DB record** of what was installed (only runs/events/audit/registry are persisted);
- **no dependency resolution** beyond content-integrity — `cairn lock` pins the
  shipped pack closure by content hash, but its registry resolver + cross-pack
  version solving are **explicitly parked** (ADR-0029: "one monorepo → nothing to resolve");
- **no portable combined artifact** — nothing bundles a chosen set of packs +
  operators + a profile into something reproducible elsewhere.

Consequences: the console's `Install →` can only be a no-op or a guided hint;
first-run hits "capability X has no provider"; and "runs here, breaks there" is
possible. We want a real install: **resolve dependencies, write a lockfile,
create a DB record, and produce a combined deployable that runs anywhere.**

## Decision

Introduce a **cairn distribution** — a *composition + lock layer on top of the
separately-shipped packs* (packs and operators still ship as independent wheels;
a distribution **pins a chosen set + a profile together**, the way a lockfile
pins libraries or a Helm chart pins images). It is:

> **distribution = template packs + operator packs + profile ("config"), with a
> resolved lock + a DB install-record, materializable as a reproducible install
> or an OCI image.**

We **build on what exists and buy what's commodity**, only writing the
cairn-specific glue:

- **Lock** — extend the existing `cairn.lock` / `cairn lock` from
  content-integrity to a *resolved deployable closure* (un-park the ADR-0029
  resolver). Do not invent a new lock format.
- **Python dependency resolution + pin** — delegate to **`uv`** (`uv lock` /
  `uv export`). Do not hand-roll a resolver.
- **"Run anywhere" artifact** — an **OCI image** via the already-implemented
  `docker` executor + existing image CI. Do not build a packaging runtime.
- **Net-new (cairn-specific):** (1) un-park the capability→pack resolver;
  (2) a distribution manifest (`bundle.toml` / a `[distribution]` block);
  (3) an **install-record store-layer** (mirrors the trigger/policy store via
  `build_storage()`) tracking `requested → resolving → locked →
  compiled/validated → installed | failed`; (4) a compile/validate-on-install
  gate (schema valid · subgraph refs resolve · capabilities known → verdict +
  `content_hash`); (5) materialization + console install UX.

### Two invariants the design must preserve

1. **Discovery stays the source of truth for *existence*.** The DB install-record
   tracks the *console-initiated lifecycle*, reconciled against live entry-point
   discovery — it must not become the authority for whether code is present
   (that invites drift when packages are installed/removed out of band).

2. **Operators do not always co-resolve in one env (#204).** `uv` will correctly
   fail to co-install conflicting/heavy operators (e.g. torch vs others). A
   "combined package" is therefore **a lean, uv-locked engine env + a set of
   operator execution images (`docker`/`remote_job`) + the profile binding them**
   — NOT one flat environment. A resolve failure is the *signal* to push an
   operator to its own execution image.

3. **The profile ("config") pins a *default* environment, not a frozen monolith.**
   The capability→operator indirection survives inside the distribution, so the
   same bundle rebinds when the profile changes. A distribution is a
   *reproducible snapshot* of a deployment, still swappable.

### Shape

```
bundle.toml (authored)            →  cairn build  →  cairn.lock (resolved + pinned)
  template packs: [training/finetune]                + uv python lock
  operator packs: [operator-training, operator-s3]   + per-operator execution target
  profile: prod.toml  ("config")                      + content hashes + DB install-record
materialize: (a) lock + manifest → `cairn install <bundle>` reproduces via uv
             (b) OCI image        → `docker run <bundle-image>` truly run-anywhere
```

Phased delivery (sub-issues) is tracked in the epic, #209. Server-side install is
remote-code-execution-adjacent and stays gated on auth + an allowlist (#185;
relates to sandboxing #205).

## Decision — locked (2026-06-29)

**Isolation model = shared engine env + container-for-heavy (no per-pack venv).**
A pack installs into the engine's lean shared env; a `uv` resolve failure is the
*signal* to push that operator to a `docker`/`remote_job` execution image via the
existing executor seam (#204). We do **not** add per-pack/conda venvs — the
executor boundary is the isolation boundary. This is the foundational decision the
rest hangs off.

**Sequencing: install is the primitive; a bundle is install over a resolved set.**
The registry (the AVAILABLE side — repo + catalog + `/registry/catalog`, #211/PR
#212) is done. Build order: registry → single-pack install → bundle install →
isolation tiers → OCI.

### v1 cut (each open question takes the cheap default; the rest is deferred)

| Concern | v1 | Deferred |
|---|---|---|
| Resolver | author-pinned / catalog-derived (`composes → operators`, already works) | capability version-solving |
| Materialization | lockfile + `cairn install` (extend `cairn.lock`) | OCI image export |
| Conflicting operators | **flag** for a container target (don't auto-build) | auto-container build |
| Discovery refresh | restart-to-discover (matches today) | hot-reload entry points |
| Install record | DB record; **discovery stays source-of-truth** (reconciled) | — (build it; it's the core) |
| Security | source allowlist only | signature verification |
| Abstract `requires` | skip (`composes` suffices for resolution) | cairn-loader enrichment in CI |

**v1 deliverable:** install a pack/bundle from the registry → `uv` into the engine
env → write a DB install-record → restart-to-discover → validate (compile its
templates) → console shows real status. Touches none of the deferred forks.

## Consequences

- Un-parks the ADR-0029 resolver; `cairn.lock` gains a resolved-closure mode
  (the content-integrity `--check` gate stays).
- Makes the console's one-click install honest (real status/errors), and enables
  the Extensions "kind" facet + a workflow "requirements" check (#206 follow-ups).
- Adds an install-record table to the store layer; existence still derives from
  discovery (reconciled), so the DB cannot silently diverge from the env.
- Heavy/conflicting operators are pushed to execution images by construction,
  reinforcing #204 / #205 rather than fighting them.
