# ADR-0051 — The workspace contract: path-based addressing, indexed `workspace_id`, lifecycle

Status: Accepted (2026-06-30)
Relates to: ADR-0048 (workspaces as a first-class entity), ADR-0049 (definition source-of-truth), ADR-0050 (one home for schemas + a migration runner). Triggered by the console tenancy audit (`docs/ideas/console-tenancy-perf-audit-2026-06-30.md`) and #255. Supersedes the `?ws=` query-param attempt (#257). Tracked work: the implementation issues filed against this ADR (storage / backend API / frontend / lifecycle).

## Context

Workspaces exist (ADR-0048) but tenancy is expressed three inconsistent ways:

1. **Addressing is implicit.** The active workspace travels as the `X-Cairn-Workspace`
   request header → a per-request ContextVar (`current_workspace()`,
   `server.py:197-211`). It is **not in the URL** — neither the API nor the console
   route shows it, so nothing is deep-linkable, a reload can't restore it, and a
   missing/wrong header silently scopes to `default`. A `?ws=` query-param attempt
   (#257) was rejected: tenancy belongs in the path, not a param.
2. **Storage is inconsistent.** `workspace_id` is kept **two** ways:
   - **JSON `data` blob** + `json_extract(data,'$.workspace_id')=?` for runs/events,
     triggers, remote jobs (`storage/sqlite/runs.py:194`, `triggers/store.py:186`,
     `operator/job_store.py`). Not an indexed column — list filters can't use an
     index, and there's no integrity on the dimension.
   - **A real column + composite PK** `(workspace_id, id)` only for
     `workflow_registry` (`workflow_registry.py:182`). This is the *one* store that
     did it "right" — and the column it added is exactly what an un-migrated DB
     lacked, which produced the #255 500.
3. **Scoping isn't always query-enforced.** Single-resource reads like
   `runs.get(run_id)` don't filter by workspace in SQL (`storage/sqlite/runs.py:139`);
   the workspace check is in the route handler instead (`server.py:424`). One missed
   guard = a cross-workspace read.

## Decision

### 1. Addressing is path-based, by workspace **id** (slug)
Workspace-scoped resources are addressed with the workspace id as a path segment:

- **Backend:** `/workspaces/{workspace_id}/…` — e.g. `/workspaces/acme/runs`,
  `/workspaces/acme/runs/{run_id}`, `/workspaces/acme/registry/installed-workflows`,
  `/workspaces/acme/triggers`, `/workspaces/acme/jobs`,
  `/workspaces/acme/packs/{pack}/{template}/run`.
- **Frontend:** `/console/w/{workspace_id}/…` — e.g. `/console/w/acme/workflows`.

The segment is the workspace **id** (the slug, e.g. `acme`, `ml-ops`), **never** the
display name, **never** a query param.

**Env-global resources stay flat** (no workspace dimension): packs +
`contract`/`graph`/`validate`/`slack-modal`, `registry/catalog|install|installs|uninstall`,
profiles, policies, connections, providers, connector catalog, oauth, operators,
registry, gateway, `/workspaces` itself, `healthz`.

### 2. The path is the single source of truth for the workspace
A FastAPI path-param dependency resolves `{workspace_id}` and sets
`current_workspace()` for the request (replacing the header as the primary
mechanism). The `X-Cairn-Workspace` header MAY be retained briefly as a fallback for
non-console clients during transition, then removed. On the console, the router's
`:ws` segment is the source of truth; the API client builds `/workspaces/{ws}/…`
URLs and the segment feeds the query keys.

### 3. `workspace_id` (and the workflow id) are real **indexed columns**
Every workspace-scoped table stores `workspace_id` as a **real column with an
index**, not a JSON-blob field read via `json_extract`:

- **runs / run_events**, **triggers**, **remote_jobs** migrate from blob-filtering to
  a `workspace_id` column (via the ADR-0050 migration primitive — add column +
  back-fill `default` + covering index; rebuild where a PK must change).
- The **workflow identifier** (`workflow_id` / `ref`) is likewise an **indexed
  column** on the installed-workflow + run tables, so workspace×workflow lookups are
  index-served. `workflow_registry` already has `PRIMARY KEY (workspace_id, id)` +
  `idx_wf_installed_ref(workspace_id, ref, status)`; the others gain matching
  covering indexes on `(workspace_id, …)`.
- Same definition for SQLite and Postgres, dialect type only where it differs
  (`TEXT` vs `TEXT`/`JSONB` payload) — per ADR-0050 (one definition, per-dialect
  override, never two parallel files).

### 4. Scoping is query-enforced (defense in depth)
Single-resource reads take `workspace_id` and filter in SQL
(`get(run_id, workspace_id)` → `WHERE id=? AND workspace_id=?`), so a workspace can
never read another's row even if a route guard is missed. The route guard stays as a
second layer.

### 5. Lifecycle (folds #258)
The `Workspace` entity gains a `status` (`active` / `archived`):

- **New workspace = empty.** Only `default` auto-inherits engine-discovered workflows;
  a fresh workspace starts with zero → the console shows the flagship empty-state.
- **Per-workspace enable / install.** An explicit action writes a workspace-scoped
  installed-workflow record (the store is keyed `(workspace_id, id)`), so the same
  workflow can be enabled in A but not B.
- **Delete = soft archive, never a hard delete.** `DELETE /workspaces/{id}` sets
  `status="archived"` and marks that workspace's installed-workflow records
  **inactive** (reversible) — runs, events, audit, pilot scores, artifacts are
  **never deleted**, still queryable for history/compliance. `default` can't be
  archived. Archiving is reversible (restore → `active`, records reactivated). The
  switcher hides archived workspaces.

## Alternatives considered

- **Header-only (`X-Cairn-Workspace`)** — status quo. Rejected: invisible tenancy,
  not deep-linkable, silent fallback on a missing header.
- **`?ws=` query param** — rejected by product decision: tenancy belongs in the path.
- **`workspace_id` in a JSON blob everywhere** — rejected: unindexed (list filters
  scan), no integrity, and the inconsistency that produced #255.
- **SQLAlchemy + Alembic for the column model** — deferred per ADR-0050 (raw SQL +
  the migration primitive is sufficient; no new dep).

## Consequences

- **Backend:** ~12 endpoints move under `/workspaces/{id}/…` (FastAPI `APIRouter(prefix=…)`,
  the mechanism already used for `/console/api` and `/ui/api`); a path-param
  dependency resolves the workspace. Env-global routes unchanged.
- **Storage:** column migrations on connect (ADR-0050) for runs/events, triggers,
  remote_jobs; indexed `(workspace_id, …)` predicates improve list perf at scale and
  give the dimension real integrity. Single-resource reads gain a `workspace_id`
  parameter.
- **Frontend:** router gains a `:ws` segment; the API client builds path-scoped URLs;
  the switcher navigates the segment. Supersedes the `?ws=` work (#257).
- **Migration/compat:** a transition window where the header still resolves
  (fallback) keeps non-console clients working until they adopt the path.

## Acceptance — the golden path (end-to-end)

The contract is "done" when this flow works against a **truly empty** deployment
(fresh DBs, nothing installed):

- **Cross-cutting:** with no data, **every** console page renders a graceful empty
  state — explanatory text + a call-to-action button — never a blank page, an error,
  or an infinite spinner. (Runs, Workflows, Library, Triggers, Jobs, Audit, Results,
  Policies, Environments.)
- **0. Default landing.** Workflows is the landing page. The `default` workspace is
  auto-seeded (decision A below), so the landing renders its **empty** state — which
  shows both a prominent **"New workspace"** CTA and **"Install from registry"** (no
  installed workflows yet).
- **1. Create workspace.** The user creates a workspace → the console switches to it
  (URL becomes `/console/w/{id}/…`) → its Workflows page shows the **empty** state
  ("nothing installed — install from the registry"), because a new workspace inherits
  nothing (§5).
- **2. Install a workflow from the registry into the workspace.** The user installs a
  workflow from the Library; it becomes a workspace-scoped installed-workflow record
  (§5 enable). It now appears under that workspace's Workflows (and **not** under
  other workspaces).
- **3. Run it.** The installed workflow can be **dry-run** (plan preview) and
  **full-run**; the run is scoped to the workspace (`/workspaces/{id}/…/run`) and
  shows up in that workspace's Runs.

This is the integration test that gates the epic (tracked as the E2E issue).

### Decided — keep `default` auto-seeded, prompt to create (option A)

The `default` workspace stays **auto-seeded** (ADR-0048) as the id-level fallback —
no churn to the `DEFAULT_WORKSPACE` fallbacks across runs/triggers/jobs/registry. The
first-run experience is the `default` workspace's **empty** Workflows landing, which
makes **"New workspace"** a prominent CTA alongside **"Install from registry."**
(Option B — no auto-seed, force-create-first — was rejected as too invasive for the
single-tenant OSS path.)

## Implementation (tracked as separate issues against this ADR)

1. **Storage** — `workspace_id` + workflow id as real indexed columns across
   runs/events, triggers, remote_jobs; query-enforced single-resource reads;
   migrations + tests.
2. **Backend API** — path-based `/workspaces/{id}/…` routing + path-param workspace
   resolver; env-global routes stay flat.
3. **Frontend** — `:ws` route segment + path-scoped API client + switcher/nav;
   replaces #257.
4. **Lifecycle** — `status` field + new-workspace-empty + per-workspace enable +
   soft-delete/archive (#258).
5. **E2E acceptance** — the golden-path integration test (empty → create workspace →
   install from registry → dry-run/run) + the every-page-empty-state audit.
