# ADR-0058 — Storage unification: one `OBS_STORAGE` selector + a lazy `build_storage()` resolver

Status: Proposed (owner-approved epic #427, decisions 2026-07-03; ADR-first before the fan-out)
Relates to: epic #427, ADR-0050 (migration runner, `cairn/core/storage/migrations.py`),
ADR-0046 (stateful infra capabilities — memory/RAG/vector, a *different* axis), the
registry-family stores (#429 connections, #437 the sqlite-only sweep), the `cairn_data`
volume stopgap (#426), and account-scoping #392/#223 (adds `account_id`, do it in the same touch).

## Context

Storage backend selection is **per-store, not per-deployment**. An inventory of the 18 stores:

- **12 config-family stores already honor `OBS_STORAGE`** (route to a `Postgres*Store` when
  `postgres://`): runs, policy, secrets, oauth, schedules, profiles, installs, connections,
  pilot_scores, account, workspace, workflow_registry. (#437 did this sweep.)
- **3 config-family stores are sqlite-only, no Postgres backend** — **triggers, remote_jobs,
  rag_catalog** — so they ignore `OBS_STORAGE` and can't land in the one prod Postgres.
- **3 stores are on a DIFFERENT axis and are out of scope here**: **memory** + **rag** are vector
  stores (Qdrant/pgvector via the legacy `VectorStore` driver layer — ADR-0046), and
  **trigger_inbox** uses `OBS_TRIGGER_INBOX` (sqlite | memory | **NATS JetStream**) for durability,
  not Postgres.

Two structural problems follow: (1) **inconsistency** — in one deployment some data is in Postgres,
some in ~16 scattered `~/.cairn/*.db` sqlite files; (2) **no single injection point** — every
consumer imports its own `default_*_store()`/`get_*_store()` directly; `build_storage()` only wires
the original 4 (runs/memory/rag/rag_catalog), reached in just 3 callsites. The `OBS_STORAGE` parse +
postgres/sqlite branch is **duplicated ~12 times**, one per factory.

## Decision

**1. `build_storage()` returns a lazy resolver, not an eager bundle.** Parse `OBS_STORAGE` once;
build each store on first access via `functools.cached_property`. Rationale: the worker, server, and
CLI each need *different* subsets — eagerly opening ~12 Postgres connection pools at every process
startup is wasteful. The resolver supersedes the eager 4-field `StorageBackend`, keeping the same
attribute names (`.runs`/`.memory`/`.rag`/`.rag_catalog`) so existing callsites don't churn, and adds
one accessor per config-family store (`.policy`, `.secrets`, `.oauth`, `.schedules`, `.triggers`,
`.profiles`, `.installs`, `.connections`, `.pilot_scores`, `.account`, `.workspace`,
`.workflow_registry`, `.remote_jobs`).

**2. Central routing — one place decides the backend.** The resolver owns the
`OBS_STORAGE` → {postgres DSN | sqlite path | in-memory} decision. Per-store construction becomes
"given the resolved mode, build this store's backend," deleting the ~12 duplicated
`if url.startswith("postgres://")` blocks.

**3. Dev = one `~/.cairn/cairn.db`.** In sqlite mode every config-family store shares one file with
**distinct, store-prefixed table names**. The inventory found no current collisions, but
`workflow_registry`'s bare sqlite names (`schemas`/`templates`/`installed`) are a hazard in a shared
file — it already prefixes them for Postgres (`workflow_*`). **Mandate a per-store table-prefix
convention** for the single file; rename the three `workflow_registry` sqlite tables to match its
Postgres names (one-time migration). Per-store `OBS_*_DB` knobs demote to rarely-used **overrides**.

**4. Scope boundary — config-family only; vector + inbox stay on their own axes.** memory, rag
(ADR-0046 vector drivers) and trigger_inbox (NATS) are NOT forced onto `OBS_STORAGE`. The resolver
still exposes `.memory`/`.rag`/`.trigger_inbox` accessors, but they delegate to the existing
`OBS_MEMORY`/`OBS_RAG`/`OBS_TRIGGER_INBOX` selectors. This keeps a relational selector from
pretending to own a vector/stream store.

**5. Fill the 3 Postgres-backend gaps** (proven registry-family pattern: pydantic record + JSON blob
+ indexed `workspace_id` + migration entry): **triggers**, **remote_jobs**, and **rag_catalog** get a
`Postgres*Store` so `OBS_STORAGE=postgres://` routes every config store. (triggers + remote_jobs are
already migration-registered for `workspace_id`, so they're partway there.)

**6. Register every config-store table in the ADR-0050 migration runner** so `migrations.py` manages
them in both sqlite and postgres — replacing the current mix of ad-hoc `CREATE TABLE`/
`add_missing_columns`/bespoke `_migrate_installed()`.

**7. Back-compat shims — incremental callsite migration.** Keep the `default_*_store()`/`get_*_store()`
factories as thin shims that delegate to a process-global `get_storage()` singleton, so tests
(`reset_*` helpers) and the many direct callsites keep working. New code takes the resolver via DI.
No big-bang callsite rewrite.

**8. Precedence (documented):** explicit `OBS_*_DB` override (if set) > `OBS_STORAGE` mode > default
(`~/.cairn/cairn.db` sqlite, or in-memory for runs to preserve today's non-breaking default).

**9. Remove the `cairn_data` volume stopgap (#426)** only after prod is verified with every
config-store on Postgres (round-trip test, no data loss). Last step, post-verification.

## Consequences

- One `OBS_STORAGE` selector governs the whole config-family: prod → one Postgres, dev → one
  `cairn.db` (one file to back up / wipe / inspect, vs ~16).
- The `~12×` duplicated routing collapses to one resolver; adding a store = add an accessor +
  a migration entry, no new env-parsing.
- Lazy construction means a process only opens pools for stores it touches.
- Scope stays honest: vector/stream stores keep their own backends; this ADR does not pretend to
  unify them.
- The stopgap volume goes away once prod is fully on Postgres — the durability risk it patched is
  removed at the source.

## Alternatives considered

- **Eager giant `StorageBackend` holding every store** — rejected; opens ~12 Postgres pools at every
  startup for stores a given process never uses. Lazy `cached_property` resolver instead.
- **Force memory/rag/trigger_inbox onto `OBS_STORAGE`** — rejected; they're vector/stream stores on a
  different axis (ADR-0046 / NATS). The resolver delegates to their own selectors.
- **Big-bang rewrite of all callsites to DI** — rejected; keep `default_*`/`get_*` as shims over the
  singleton and migrate callsites incrementally.
- **A separate deployment-tier flag** (e.g. `OBS_TIER=dev|prod`) — rejected; the mode is inferred
  from the `OBS_STORAGE` URL scheme (per #427 decision), no second knob.

## Fan-out plan (post-ADR)

Applying the model/effort rubric — Opus builds the spine + verifies; Sonnet fans the mechanical parts:
1. **Spine (Opus/high):** the `Storage` resolver (lazy, central routing, single-file path) + convert
   `StorageBackend` → resolver + `get_storage()` singleton + shim the existing factories to it.
2. **Mechanical (Sonnet/parallel):** the 3 new Postgres backends (triggers, remote_jobs, rag_catalog),
   table-prefix rename for workflow_registry sqlite, migration-runner registrations.
3. **Verify (Opus/high):** every config-store round-trips in single-file sqlite AND Postgres, no data
   loss; then drop the `cairn_data` volume (#426).
