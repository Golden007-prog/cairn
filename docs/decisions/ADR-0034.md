# HITL as a core feature — a non-bypassable, per-operation approval gate

## Context

Human-in-the-loop approval existed only for **actions** (ADR-0024: the durable
saga's `interrupt()` + checkpointer + `Command(resume)`), and only when a pack
proposed an `ActionCandidate` a policy gated. Template **operations** had no
gate: `OperationBinding.approval` (§24.20.16) was declared but the compiler
ignored it, and template graphs compiled with no checkpointer (one-shot, not
resumable). The durability mechanism itself is not novel — LangGraph
`interrupt()` and Temporal signals already implement durable pause/resume; the
work is making it a first-class, **non-bypassable** cairn capability.

## Decision

A per-operation approval gate, **owned by the deployment, enforced by the
engine** — mirroring ADR-0028's "optional to turn ON, not optional to ESCAPE".

1. **ApprovalResolver (`core/approval/resolver.py`)** — pure decision. The gate
   is required if ANY authority mandates it: the operator-author `requires_approval`
   / `risk` (pack.toml `OperatorEntry`, not pack-controllable), the deployment
   policy (`PolicyEngine` cross-cutting `require_hitl` on capability/mapped-risk —
   *optional/follow-up*), the `[profile.approval]` coarse switch, and the pack
   `OperationBinding.approval` which is **strictness-only** (can add/tighten,
   never relax). Policy-eval failure fails **safe** (gate on).

2. **Chokepoint enforcement (P1, `runtime.py:invoke_operator`)** — every
   operation funnels through here, so it is the topology-independent seam: a
   required gate with no recorded `ApprovalRecord` raises `NeedsApprovalError`.

3. **Durable pause/resume (P2, `compiler.py` + `runtime/inprocess.py`)** — a
   template containing a gated operation compiles **with a checkpointer**
   (`get_checkpointer()`; memory|sqlite|postgres tiers); ungated templates keep
   the bare one-shot compile (byte-identical). The gated operation-node fn
   resolves the gate and, if required, `interrupt()`s (re-run-safe: nothing
   side-effecting precedes it) — surfacing an `ApprovalRequest`; on
   `Command(resume=ApprovalRecord)` it audits the decision and, if approved,
   runs the operator (recording the approval locally so the chokepoint passes).
   Reject skips the operator. Decision delivery in v1 is the existing
   `/triggers/approve` HTTP path; the event-bus delivery (ADR-0010 `hitl.*`
   topics) is a deferred enhancement.

## Non-bypassability (the four vectors)

1. **Omission** — authority is the operator's `requires_approval` (+ deployment
   policy/profile), not the binding; the resolver runs regardless of binding.
2. **`required: false`** — strictness-only merge; `false` is a no-op vs a mandate.
3. **Route-around** — enforcement is at the `invoke_operator` chokepoint every
   operation funnels through, and the gate node is compiler-injected (not author-
   wired); the bounded `OperationContext` (§24.20.13) blocks reaching around it.
4. **Different operator** — the gate keys on declared `risk` + `capabilities`,
   so any operator of that risk/capability hits the same rule.

## Tiers

- **In-process (default) — SHIPPED + tested**: LangGraph `interrupt()` +
  `get_checkpointer()`; `InProcessRuntime.invoke` passes a `thread_id` for
  checkpointed graphs and `resume()` continues. Pause/resume/reject + ungated
  no-op are covered by tests.
- **Temporal (ADR-0022) — WIRED, unverified pending a cluster**: the gate node
  is tier-agnostic (the same `interrupt()` runs under whatever runtime), and the
  Temporal resume delivery is now in place — `TemplateWorkflow` has an `approve`
  `@workflow.signal` + a `wait_condition`/`Command(resume)` loop (a no-op when
  there's no interrupt, so non-gated workflows are unchanged), and
  `TemporalRuntime.resume` sends that signal keyed on the workflow id. It is
  **unverified**: it needs a live cluster (`OBS_RUNTIME=temporal`) and
  confirmation that the `temporalio.contrib.langgraph` plugin surfaces
  `interrupt()`/`Command(resume)`. Also, `invoke` uses blocking
  `execute_workflow` today — a non-blocking start + return-awaiting-approval is a
  refinement for long waits.

## Consequences / deferred

- v1 gate sources in the hot path = operator `requires_approval` + binding +
  (profile switch); the cross-cutting **PolicyEngine** source and the
  `[profile.approval]` schema field are follow-ups.
- **Event-bus delivery** (`hitl.requested`/`hitl.decided` + an `ApprovalBridge`)
  is deferred — HTTP `/triggers/approve` suffices for v1.
- **Timeout/expiry** (durable timer + resume claim-lock) and **MapBTNode
  fan-out** `operation_id` stability are open (see `docs/ideas/hitl-core.md`).
- `status.yaml`'s `eval-gate-node` stays `not-started` — this is operation
  approval, not the eval-gate node type.
