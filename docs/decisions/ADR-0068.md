# ADR-0068 — Operator config surface: declared knobs, projected into the profile

Status: Proposed (2026-07-12)
Tracked in: #742 (epic — phased plan + operator config sweep inventory)
Relates to: the operator contract (`Operation` in
`cairn/core/operator/protocol.py`), the binding runtime
(`cairn/core/operator/runtime.py`), the profile layer
(`cairn/core/pack/profile.py`), the doctor preflight
(`cairn/cli/commands/doctor.py`), ADR-0053 (policy scoping — the sibling
"environment is the wiring hub" decision), and the console Environments surface
(#302/#303). Supersedes the "profile-scoped overrides are a follow-up" TODO left
in `run-gate.yaml`, `schemas/gate.py` (dataset), `cost_gate.py`, and the model
gate schema.

## Context

Governance operators carry deterministic **guardrail thresholds** — the dataset
gate's `format_min_conformant_pct` (99.0), the cost gate's `max_usd`, the model
gate's `max_eval_loss` / `require_significant_improvement`. Today these are
Pydantic **field defaults** on the operator's *input* schema, nested under a
`thresholds` sub-model that the operation YAML never binds. So:

- **The defaults are the only effective values.** There is no supported way to
  change the 99% format floor, the cost cap, or the promote bar per deployment
  without editing operator source. Every threshold schema literally says
  *"profile-scoping is a follow-up; today the defaults apply."*
- **The knobs are invisible.** They live as internal field names inside an
  operator wheel. A platform owner cannot discover them, and could not author
  them safely even if we bound `$input.thresholds` — they would have to know
  `format_min_conformant_pct` by heart and hand-write raw TOML with no labels,
  bounds, or validation until the value reached the box mid-run.
- **It is not just the three gates.** A scan (issue: operator config sweep)
  finds a broad tail of operators with tunable behavior baked as input defaults
  — PII scan bounds, dedup similarity, sampling sizes, serve params, retry
  counts. Each is a per-deployment decision masquerading as a code constant.

The requirement (user, verbatim intent): *"we need a generic way to set
these/override for all future packs/operators… the user doesn't know the
internal variable. A pack or operator needs to expose them, only then does this
make sense… profile/env binds operators — if operators are bound, their config
should automatically show up in the profile."*

Three demands fall out of that: operators must **declare** a public knob surface;
the surface must be **discoverable/authorable** (not raw internal names); and the
profile must **project** the knobs of the operators it already binds, rather than
requiring hand-written config tables.

## Decision

**Operators declare a config surface; the profile projects the surface of the
operators it binds; cairn validates and injects it.** Three contract clauses.

### 1. Operators declare a `config_schema` (the published knob surface)

A new **optional** class attribute on `Operation`, parallel to the existing
required `input_schema` / `output_schema`:

```python
class Operation(Generic[I, O]):
    input_schema:  type[BaseModel]
    output_schema: type[BaseModel]
    config_schema: type[BaseModel] | None = None   # NEW — deployment-tunable knobs
```

`config_schema` is a Pydantic model whose fields are the **deployment-tunable
knobs** — severity thresholds, budgets, limits, sizes. Distinct from
`input_schema` (per-run wired data bound from `$state`/`$input`) and from
`output_schema`. Every field carries human metadata so the *schema is the
documentation*:

```python
class GateThresholds(BaseModel):           # promoted to dataset/gate.config_schema
    format_min_conformant_pct: float = Field(
        99.0, ge=0, le=100,
        title="Minimum format conformance",
        description="Rows must parse into a trainer-accepted format. Below this %, BLOCK.",
    )
```

The four existing threshold models (`GateThresholds`, `CostThresholds`,
`ModelGateThresholds`, `EvalDeltaThresholds`) are promoted to be their operators'
`config_schema` — they already have the right shape; we add `title`s and register
the attribute. Operators with no deployment knob declare nothing
(`config_schema = None`) and expose no config surface — correct for a pure
transform.

**Migration of the nested `thresholds` field (the 4 Category-A operators).**
Those four today expose `thresholds: <Model> = Field(default_factory=…)` as a
field on their *input* schema — an override is theoretically possible by binding
`$input.thresholds` (though no YAML does). The chosen migration: `config_schema`
becomes the single source of truth for those knobs; the input-schema `thresholds`
field is retained for **back-compat** and, at the injection seam, the resolved
config is written into it (i.e. config populates `inp.thresholds` unless an
explicit run input already set it). So no operator `run()` body changes — it
still reads `inp.thresholds` — and the value now flows from the profile. Once all
consumers use config, the input field can be dropped in a later cleanup.

`register_operator` captures `config_schema` into operator metadata (parallel to
how it captures `capabilities`); the registry surfaces it for introspection.

**A `config_schema` (and its nested models) MUST forbid extras**
(`model_config = ConfigDict(extra="forbid")`). Pydantic ignores unknown keys by
default, which would let a typo'd knob validate silently; forbidding extras makes
a mistyped key fail **both** doctor preflight (with the field list) and runtime
validation. Since the gate threshold models double as `input_schema` sub-models,
this also hardens the wired-input path.

### 2. The config surface is PROJECTED from the profile's bindings — not hand-authored

The profile already resolves a concrete **active operator set** — installed packs
+ `[profile.bindings]` (capability → operator-pack) + `[profile.capabilities]`
disambiguation, merged across the `extends` chain (`cairn/core/pack/profile.py`,
`loader.py`, `provisioning.py` #304). Because the bound operators are already
known, the config surface is *generated*, not typed:

```
profile bindings + installed packs
    → resolved active operators
    → for each op with a config_schema: a config section (defaults pre-filled)
    → the profile/env editor renders it; the user edits VALUES only
    → only the DELTAS from operator defaults persist to disk
```

A new `config` key is added to the closed `[profile]` schema (joining
`extends / capabilities / bindings / mcp_servers / backends / policies /
knowledge` in `_PROFILE_TOP_KEYS`), keyed by **operator name**:

```toml
# environments/prod.toml
[profile]
extends  = "local-dev.toml"

[profile.config."dataset/gate".thresholds]     # generated section — holds ONLY overrides
format_min_conformant_pct = 99.0

[profile.config."compute/cost_gate".thresholds]
max_usd  = 200.0
warn_usd = 100.0

[profile.config."model/gate".thresholds]
max_eval_loss                   = 1.5
require_significant_improvement = true
```

Keys the deployment did not override are **absent** and resolve from the
operator's declared default. Binding a new operator or upgrading a pack that adds
a knob makes the new knob appear in the editor automatically — no migration, no
hand-written table. `extends`/env override is **per-key present-wins** (matching
`backends`), so a child tightens only the keys it names.

### 3. cairn resolves precedence, validates at boot, injects at invocation, audits

- **Precedence** (highest wins): explicit run input (`$input.*` / a run's
  `config_overrides`) → env `[profile.config."op"]` → profile (+ `extends` chain)
  → operator `config_schema` default.
- **Injection** at the operator-invocation seam in `runtime.py`, *before*
  `input_schema.model_validate`: the resolved config for `op_name` is deep-merged
  **under** the explicitly-provided inputs, so a run always wins and unset knobs
  fall through to the code default. Only fields declared on `config_schema` are
  injectable — wired `$state` inputs are never config-overridable.
- **Doctor validation** (`check_operator_config`, new): every
  `[profile.config."op"]` table is `model_validate`d against that operator's
  `config_schema`. An unknown key or wrong type **fails preflight** with the
  operator's declared field list — typos surface at boot, matching the profile
  ethos, never on the box mid-run.
- **Audit / provenance:** the run records the effective config per operator AND
  which layer supplied each value (`config_provenance`), extending the existing
  pattern where `dataset/gate` already dumps `thresholds` into `audit_metadata`.
  An override is never silent.

### Discovery surfaces (how a user authors without knowing internals)

All render from `config_schema.model_json_schema()`:

- `cairn config scaffold <op>` — emits a commented TOML stub: each knob's
  `title`, `description`, bounds, and default as comments; the user edits values.
- `cairn operators show <op> --config` — the same table in the terminal.
- **Console** — the Environments surface (#303) grows a "Guardrails" section
  listing the reachable bound operators and their knobs, rendered by the existing
  schema-driven form renderer (the UIContract, #109/#221): `title` = label,
  `description` = help, `default` pre-filled, `ge/le` = min/max validation.

Only **reachable** operators (bound, or used by the profile's enabled templates)
are shown, so the editor is not cluttered with irrelevant knobs; doctor already
computes reachability.

## Exposure & enforcement — prior art: Dagster

Dagster's config system is the closest mature prior art, and the two most-used
data platforms (Dagster's `Config`/asset-checks, Prefect's Pydantic-params →
`model_json_schema()` UI form) both independently converged on *exactly* this
shape — a Pydantic config class per unit of work, a schema-generated form, and
fail-closed validation. That convergence is the strongest evidence the design is
right. Two Dagster mechanics are worth adopting **verbatim**, and one gap in the
Phase-1 build is what they expose:

**Exposure — how the surface presents itself** (Dagster's Launchpad):
- Config is a typed Pydantic class with field `description`s + defaults; the UI
  renders a schema form with typeahead, inline docs, and a **"Scaffold Missing
  Config"** button. cairn's `cairn config scaffold <op>` and the console
  Guardrails form are the direct equivalents (both from `model_json_schema()`).
- **Strict by default.** Dagster's default `Config` (a `Shape`) rejects
  unspecified fields with `DagsterInvalidConfigError`; `PermissiveConfig` is the
  explicit opt-in for open-ended config. cairn's `extra="forbid"` on config
  surface models is the same choice — and the reason a typo is caught rather than
  silently ignored. Adopt Dagster's split: **forbid by default**, allow a
  `permissive` opt-in only where a knob is genuinely open-ended (e.g. a
  field-mapping table like `logs/summarize`).
- **Secret/env indirection.** Dagster config fields use `EnvVar("NAME")` /
  `is_secret=True` so a sensitive value is read from the environment and masked in
  the UI, never stored in plaintext. cairn adds a `$env:VAR` indirection for
  config values + a `secret` field marker the console form masks. (Keeps
  ADR-0053-style secrets out of the profile TOML.)

**Enforcement — how it's actually gated** (Dagster's launch-time validation):
- **THE gap.** Dagster validates the *entire* run config against *every* op's
  schema **before execution starts**, and aborts the run with
  `DagsterInvalidConfigError` — no op runs on invalid config. cairn's Phase-1
  build validates only (a) at `cairn doctor` (opt-in, not every run) and (b)
  lazily at each operator's own invocation (mid-graph). So a bad config in a
  never-doctored deployment fails *halfway through a run*, after side effects.
  **Decision: add a run-submit CONFIG PREFLIGHT** in the dispatcher — before
  executing node 1, resolve every reachable operator's effective config and
  `model_validate` it against its `config_schema`; on any failure abort the run
  with a structured `ConfigError` (cairn's `DagsterInvalidConfigError` analog) and
  a per-operator field list. Fail-closed, upfront, once per run. This is the
  primary enforcement hardening (tracked as Phase-1b on #742).
- **Required-per-deployment knobs.** A Dagster `Config` field without a default is
  *mandatory* — the run won't launch until it's supplied. cairn's Phase-1 config
  is all-optional (every knob has a safe code default). Add an opt-in
  **`required_in_env`** marker (or a no-default field) so an operator can declare
  a knob that a deployment MUST set — the config preflight fails if it's unset in
  a non-dev environment. Governance use: force an explicit cost cap
  (`compute/cost_gate.max_usd`) and a promote bar (`model/gate.max_eval_loss`) in
  prod rather than silently inheriting `0`/`None`.
- **Fail-open vs fail-closed on a MISSING signal — decide and document.** Dagster
  learned (post-regression) that a *missing* blocking-check result should let
  downstream proceed with a warning, not silently skip. cairn's
  `dataset_gate_passed` already treats an **absent** verdict as `pass` (fail-open,
  matching Dagster) while an explicit `fail` blocks. This ADR makes that explicit:
  **absent gate signal → proceed + warn; explicit fail → block.** Config
  enforcement is the opposite (fail-closed) because a malformed *deployment* knob
  is an operator error, not missing runtime data.

The net: exposure is already designed right (Dagster/Prefect confirm it);
enforcement gains a **run-submit config preflight** + **required-in-env knobs**,
which is where "strong gating" actually lives.

## Consequences

- **Generic by construction.** Any current or future operator gains
  deployment-tunable config by adding one line (`config_schema = …`) — scaffold,
  console form, docs, doctor validation, precedence, and audit come for free. No
  per-operator plumbing, no touching the ~60 other operators.
- **The profile stays a delta file.** It records only what a deployment changed;
  the full surface is always reconstructable from the bound operators' declared
  schemas. Small, review-friendly, upgrade-safe.
- **Clean boundary restated.** `config_schema` = deployment knobs (per-env);
  `input_schema` = per-run wired data; policy (ADR-0053) = allow/deny rules.
  Config-override and policy-scoping are siblings, both hubbed at the environment.
- **Back-compatible.** `config_schema` is optional; operators without it behave
  exactly as today. A profile with no `[profile.config]` resolves to the current
  defaults byte-for-byte. The three gates' behavior is unchanged until a
  deployment sets a value.
- **Migration.** The shipped profiles (`cairn/profiles/*.toml`) gain the closed
  `config` schema key (parser change) but need no content change; `prod.toml` /
  `secure.toml` MAY set explicit guardrail values as the reference example.
- **Follow-up (out of scope here):** a policy could constrain *which* config keys
  an env may override (lock `format_min_conformant_pct` in prod). This composes
  with ADR-0053 and is deferred.

## Alternatives considered

- **Bind `$input.thresholds` in each operation YAML.** Per-operator, per-YAML
  toil; still exposes raw internal field names; no discovery, no projection.
  Rejected — does not satisfy "generic for all future operators" or "user doesn't
  know the internal variable."
- **A new `$config.<op>.<path>` binding scope only.** Useful for the rare
  computed reference, but as the *primary* mechanism it still requires editing
  every YAML and knowing field names. Kept as an optional escape hatch (for
  per-instance overrides where two invocations of one operator need different
  values); not the main path.
- **Hydra / OmegaConf / dynaconf.** Hierarchical config libs that solve
  composition but bypass our doctor/audit/binding integration and add a heavy
  dep. Pydantic is already the substrate (operator schemas are Pydantic) — "layer
  dicts then `model_validate`" is native. Rejected.
- **Mark input-schema fields `configurable=True` instead of a separate model.**
  Muddier — interleaves wired inputs and deployment knobs in one model, and
  nested sub-models need whole-subtree marking. A dedicated `config_schema` is
  the cleaner, already-half-present shape (the `thresholds` sub-models). Rejected.
