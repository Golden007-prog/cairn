# ADR-0062 — BYO (drop-in) knowledge corpora via account-scoped artifact storage

Status: Proposed (2026-07-05)
Relates to: #516; the knowledge-pack model (ADR-0061, kind="knowledge" + role
composition); the account/tenant model (ADR-0054); workspace scoping (#237); the
artifact storage layer (`ArtifactStore`, `operator-artifact-local`, `operator-s3`);
the connection catalog (#305, account-scoped creds); the RAG ingest chain
(`services/rag/ingest.py` + the `rag/parse` operator). Foundation (the store +
model) landed with this ADR; the ingress + composition below is the build plan.

## Context

A `kind="knowledge"` pack (ADR-0061) ships a corpus as a published pip wheel —
correct for CURATED/registry corpora (MITRE, CVE), too heavy for a customer's OWN
data. The high-leverage case ("point cairn at MY runbooks") needs a lighter path,
and it is **security-sensitive**: a customer's documents must never leak across
tenants. So the source of a BYO corpus must NOT be a raw server path — it must be
a governed, account-scoped artifact reference.

## Decision

A **workspace-scoped record** (`WorkspaceCorpus`: account_id, workspace_id, name,
`source_uri`, role, governance metadata) makes any set of documents behave like a
pack corpus — indexed + composed into a knowledge role — with zero packaging. The
`source_uri` is always one of three governed refs, resolved through the artifact
layer at index time:

1. **`s3://bucket/prefix`** — cairn PULLS from the customer's S3 using **that
   account's stored S3 connection** (connection catalog #305, account-scoped
   creds; never ambient/shared credentials).
2. **`artifact://…`** — files UPLOADED to cairn are written to cairn's artifact
   storage **namespaced by `account_id`/`workspace_id`** (the same isolation
   boundary #237/ADR-0054 enforce for runs + memory), then referenced here.
3. **`file://…`** — local dev only.

### Isolation (the load-bearing part)
- **Every read is tenant-scoped.** The store lists per `workspace_id`; the S3 pull
  uses the account's own connection; the artifact path is prefixed by
  `account_id/workspace_id`. There is no code path that resolves a BYO source
  outside the caller's account boundary.
- **The vector collection is workspace-scoped** (`ws_<id>__rag_<name>`, #237) — so
  account A's `security` corpus and account B's never share a collection.
- **Upload is validated + size-capped**, written only under the caller's
  account/workspace artifact prefix; a raw filesystem path is rejected.

### Composition + indexing (reuse, don't rebuild)
- `workspace_corpus_targets(account, workspace)` maps records → `CorpusTarget`s
  (role, workspace-scoped collection), which `list_roles`/`resolve_role` union
  with pack corpora — so a role composes registry packs + BYO corpora in one slot.
- Indexing resolves `source_uri` → a local temp dir (S3 download / artifact fetch /
  file), then runs the SAME pipeline: `rag/parse` → chunk → embed → upsert. No new
  ingest code; embedder-scoped collections (#512) apply.

### Governance
Same `[knowledge]`-style metadata (license/source/citation) per record, enforced
by the same policy admissibility as pack knowledge (ADR-0061 Slice 4). Provenance
on a BYO hit cites the workspace corpus + source doc.

## Consequences

**Phasing:**
- **Foundation (landed):** `WorkspaceCorpus` model + `WorkspaceCorpusStore`
  (InMemory/SQLite, account+workspace scoped) + tests.
- **Ingress A — S3 pull:** resolve `s3://` via the account's S3 connection →
  temp dir → index. Depends on the connection being account-scoped.
- **Ingress B — upload:** `POST /ui/api/knowledge/corpora/upload` writes to the
  account/workspace artifact prefix → `artifact://` ref → index. Security-review
  the isolation before shipping.
- **Composition:** union `workspace_corpus_targets` into `list_roles`/index_all.
- **UI:** the Knowledge page gets a "Add your data (S3 / upload)" form + BYO
  corpora listed alongside packs (tagged "workspace").

**Why this over a raw path:** a `source_path` field would let one tenant point at
another's data (or the host filesystem). The artifact-ref indirection is what
makes "no leakage" enforceable, and it reuses cairn's existing account-scoped
artifact + connection layers rather than inventing a new isolation mechanism.

**Registry vs BYO:** registry packs are the curated on-ramp; BYO is the retention
moat (a customer's own knowledge, governed). Both compose into the same roles.
