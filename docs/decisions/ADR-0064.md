# ADR-0064 — Training-checkpoint durability: the remote job makes the trainer's checkpoints survive the box and relaunches onto them

Status: Proposed (2026-07-07)
Relates to: #552 (this), #536 (training-infra epic), #551 (remote-job pause/resume
seams), ADR-0038 (RemoteJobChannel / control loop), ADR-0039 (learning gate),
the `s3` connection (connections.py) + #532 cred injection.

## Context

A QLoRA fine-tune runs for hours. The trainer already checkpoints (`save_steps`,
`resume_from_checkpoint`, `train_entry.py`), but checkpoints land on the box's
`/tmp` — so a box death / spot reclaim / terminate / OOM loses all progress, and
`resume_from_checkpoint` only helps for an in-place restart where `/tmp` survives.
The control plane resumes the *run* (ADR-0038) but never relaunches a *dead
training job* onto its last checkpoint. This is the precondition before any spot
GPU (#536 §7 gates Vast on it) — and even a RunPod OOM mid-run currently loses
everything.

## Decision

Split by responsibility. **The trainer owns the checkpoint MECHANISM; the remote
job owns making those checkpoints durable and relaunching training onto them.**
cairn does NOT reimplement optimizer/scheduler/step checkpointing (HF/TRL already
do it — verify-upstream).

### 1. Durable checkpoint sync (S3), during training

- A TRL/HF `TrainerCallback.on_save` uploads each just-written `checkpoint-*` dir
  to `s3://<bucket>/cairn-checkpoints/<run_id>/` via **boto3** (a base dep — no new
  dependency). Bound by `save_total_limit` (prune old checkpoints locally AND in
  S3). Best-effort: an upload error never fails the train.
- **Target resolution.** `cairn-train-local` reads `CAIRN_CHECKPOINT_BUCKET`,
  `CAIRN_CHECKPOINT_PREFIX` (default `cairn-checkpoints`), and `AWS_*` from its
  environment. For the SSH `train/remote` path these are set on the box (EC2-B),
  the same way `MLFLOW_TRACKING_URI`/`HF_TOKEN` already are — NOT exported through
  the `run-train-remote` binding, because a `$default(..., "")` there would shadow
  the box's own value with an empty string and silently disable sync. The one
  binding-side signal that IS injected is `CAIRN_RUN_ID` (by `remote/exec`, from
  `ctx.pipeline_id`) so the S3 key `…/<run_id>/` is per-run and STABLE across
  relaunches (never collides across runs). Absent a bucket → the callback no-ops
  (local-only, today's behavior — no regression). The governed path (bucket+creds
  from the `s3` connection forwarded into the box env without shadowing) is a
  follow-up.
- **HF target.** For `artifact_target="hf"`, the native equivalent is
  `push_to_hub=True` + `hub_strategy="all_checkpoints"` — no custom upload.
- **Also implement `artifact_target="s3"`** for the FINAL adapter (the `_save_adapter`
  stub), reusing the same target resolution.

### 2. Relaunch-from-checkpoint orchestration (control loop)

- Add `checkpoint_uri: Optional[str]` to `RemoteJobRecord`; set it when the job
  first reports a durable checkpoint location (surfaced in `JobStatus.metrics`).
- On a poll that reports a **resumable death** (box/instance gone: pid absent, no
  clean exit — distinct from a clean non-zero exit), the control loop, IF
  `checkpoint_uri` is set AND `attempts < max_attempts` AND the cost gate still
  permits spend: **re-submit** the same job. The box's runner first pulls
  `s3://…/<run_id>/` into `out_dir`, then `resume_from_checkpoint` continues.
  Increment `attempts`. Otherwise → fail the run as today.
- `max_attempts` from the run input (default small, e.g. 2); the pre-existing
  `compute/estimate` + `cost/gate` bound cumulative spend across relaunches.

### 3. OOM safety (bundled)

- `max_seq_len` is already wired into `SFTConfig` (caps over-long rows). ADD a
  `packing: bool` field (default on for real runs) → `SFTConfig(packing=True)` for
  predictable per-step VRAM. ADD `save_total_limit` (bounds local + S3 storage).

### Explicitly NOT in scope

- cairn does not store checkpoint bytes itself or manage optimizer state — that is
  the trainer's. cairn syncs the trainer's output to S3 and relaunches.
- No new artifact-store abstraction — the `s3` connection + boto3 suffice.

## Consequences

- **Spot/OOM safe**: a killed job resumes from its last S3 checkpoint on a fresh
  box, bounded by attempts + cost — the precondition #536 §7 puts on Vast.
- **Reuses machinery** — the `s3` connection, #532 cred injection, the ADR-0038
  control loop, TRL's `resume_from_checkpoint` — so it's mostly wiring + one
  callback + one control-loop branch (no new durable mechanism).
- **Hermetic CI**: boto3 uploads tested against moto; no-bucket → no-op path keeps
  existing local runs green.
- **Cost of relaunch**: an unbounded retry could burn money — hence the hard
  `max_attempts` + cost-gate guard, and `checkpoint_uri`-required (never relaunch
  a job with nothing to resume from).

## Build plan (two subsystems — no file overlap, so parallelizable)

- **Control-plane spine (Opus):** `checkpoint_uri` on `RemoteJobRecord`;
  relaunch-on-resumable-death branch in `job_control.py` (attempts + cost gate);
  `run-train-remote` binding exports the checkpoint env; tests in `tests/core`.
- **Training-operator implementation (one Sonnet agent):** the `on_save` S3-sync
  callback + `checkpoint_uri` surfaced in metrics; `artifact_target="s3"` final
  adapter; `packing` + `save_total_limit` schema fields → `SFTConfig`; the on-box
  S3-pull-before-resume in `local_entry`/runner; hermetic moto tests IN the pack.
