### 24.13 Decision: integration strategy — MCP-first, custom-as-MCP-server

> Triggered by the question: *"Instead of writing custom code for every
> integration, can we salvage Activepieces / Pipedream / MCP servers?"*
> Honest answer: only MCP is the right substrate; the other two are
> workflow-engine conflicts.

**Today's situation.** The incident pack ships a mix:
- ``cairn.services.mcp`` — MCP gateway exists and is used (Slack notify,
  Notion publish, Confluence publish).
- ``cairn.services.{memory,rag,...}`` — direct Python service modules
  for things deeper than tool calls.
- Pack-local code in ``incident/code/tools/*`` — direct API integrations
  (correlation, blast-radius math, postmortem writers).

There's no rule about *when* to add an integration as raw Python vs as
an MCP server. Pack authors don't know which to choose; new
integrations land wherever's easiest.

**Decision: MCP is the integration substrate. Period.** Three sub-rules:

1. **Prefer existing MCP servers** from
   ``modelcontextprotocol/servers`` + community catalogs. If a server
   exists for the system, use it. Pack declares
   ``requires.mcp_servers``; the gateway forwards calls.
2. **For systems without an MCP server, write a custom FastMCP server**
   in ``cairn/integrations/custom/``. Same substrate, just authored
   here instead of upstream. **This will be common — many internal
   tools, smaller SaaS products, and bespoke services won't have
   upstream MCP servers, and that's fine.** FastMCP makes the wrapper
   ~50–200 LoC per system.
3. **Never put raw external-API Python in a pack.** Pack-local code is
   for domain logic (blast-radius math, RCA prompts, scoring); not for
   "call Slack's API." If you're tempted to write a pack-local Slack
   client, write a Slack MCP server (or use the official one) and have
   the pack request it.

#### 24.13.1 Why Activepieces / Pipedream are NOT the substrate

The user's question named three options. Be explicit about why two of
them fail this platform:

| | Activepieces | Pipedream | MCP servers |
|---|---|---|---|
| Owns the workflow runtime? | Yes — conflicts with our Runner | Yes — same conflict | **No — just exposes tools** |
| Language | TypeScript | TypeScript / JS | Python + TS (multiple impls) |
| Adopt as integration provider? | Requires running their engine + writing shim → 10× operational cost | Same | Native |
| Number of integrations available | ~300 pieces | ~2000 components | Growing fast; Anthropic + community |
| Right shape for cairn | **No** | **No** | **Yes** |

The shape mismatch is the kill: Activepieces and Pipedream want to
**own** the workflow ("trigger fires → run this graph"). cairn
already owns that. Adopting them = running two workflow engines, one
as a tool provider to the other. Heavy operational cost for marginal
gain.

**Where Activepieces/Pipedream ARE useful**: as *reference
implementations*. When you need to write an MCP server for a system
with weird auth (Jira's OAuth dance, Salesforce's session handling),
their open-source piece code shows you how to do it. Port the logic
into a Python FastMCP server; don't import the runtime.

#### 24.13.2 Pack manifest extension (§24.3 addition)

Pack declares MCP server requirements alongside capabilities:

```toml
[requires]
capabilities  = ["logs.read", "metrics.query", "comms.post_message"]
mcp_servers   = ["github", "slack"]              # hard deps
services      = ["memory", "rag"]                # abstract (existing)

[optional]
capabilities  = ["compliance.check"]
mcp_servers   = ["notion", "linear"]             # graceful degradation
```

The loader (§24.3 work) treats `mcp_servers` like `capabilities`:
- Hard dep missing → refuse to start
- Optional missing → load + warn; pack exposes `unavailable_mcp_servers`
- Doctor shows status

#### 24.13.3 Doctor `[mcp_servers]` category

`cairn doctor` gains:

```
[mcp_servers]
  ✓ slack:    reachable, 14 tools available
  ✓ github:   reachable, 26 tools available
  ⚠ notion:   optional, not configured
  ✗ jira:     REQUIRED by incident-extended pack, not configured
```

#### 24.13.4 The `integrations/` layout

```
cairn/integrations/
├── mcp_catalog.toml       ← curated registry of known MCP servers
│                            (name, install cmd, auth shape, tools)
├── custom/                ← FastMCP servers for systems without upstream
│   ├── bifrost/           ← e.g. ~150 LoC MCP server wrapping Bifrost
│   ├── helicone/
│   └── ...
├── observability/         ← (existing — Backends, not MCP)
└── mcp/                   ← (existing — gateway, registry, shared utils)
```

The `custom/` dir convention: one subdir per integration, each holds
a `server.py` (FastMCP server entry) + optional `tools/` + `schemas/`
+ `README.md`. Same shape as a pack's `code/` dir — pack authors who
need to write an MCP server learn the layout from one example.

#### 24.13.5 When to write a custom FastMCP server (the common case)

Honest expectation: **most ModelOps + internal-tool integrations will
need a custom FastMCP server** because upstream MCP coverage is still
patchy for:

- Internal company tools (your monitoring, your auth)
- Smaller SaaS products (Helicone, Langfuse, niche AI tooling)
- Bespoke services (your model gateway, your eval system)
- LLM gateways themselves (Bifrost, LiteLLM)

Author rule:

| If… | Then… |
|---|---|
| System has an official MCP server | Use it. Register in `mcp_catalog.toml`. |
| System has a community MCP server you trust | Use it. Same. |
| System has multiple community servers, none clearly canonical | Pick one, document the choice + version pin |
| No MCP server exists | Write one as FastMCP in `integrations/custom/<name>/` |
| MCP server exists but you need 3 specific tools it doesn't expose | Either contribute the tools upstream, OR write a thin custom server that delegates |

**Tooling to make this cheap:**

- `cairn init mcp-server <name>` — scaffold a custom FastMCP server
  with FastMCP boilerplate, auth stub, one example tool, README,
  pyproject (optional dep group). Parallel to `cairn init pack`.
  ~half day to build the scaffold; pack authors save a day per
  integration.

#### 24.13.6 Curated catalog model

`cairn/integrations/mcp_catalog.toml` is the engine's curated list:

```toml
[mcp.slack]
description = "Official Slack MCP server"
source      = "modelcontextprotocol/servers"
install     = "npx -y @modelcontextprotocol/server-slack"
auth        = ["SLACK_BOT_TOKEN", "SLACK_APP_TOKEN"]
tools       = ["slack.post_message", "slack.read_channel", "slack.search", ...]

[mcp.github]
description = "Official GitHub MCP server"
source      = "modelcontextprotocol/servers"
install     = "npx -y @modelcontextprotocol/server-github"
auth        = ["GITHUB_TOKEN"]
tools       = ["github.open_pr", "github.read_file", ...]

[mcp.bifrost]
description = "Bifrost LLM gateway MCP server (custom, ships with cairn)"
source      = "cairn.integrations.custom.bifrost"
auth        = ["BIFROST_API_KEY", "BIFROST_BASE_URL"]
tools       = ["llm.call", "llm.list_models", "llm.estimate_cost"]
```

Stretch surface:

- `cairn mcp catalog` — list known MCP servers
- `cairn mcp install <name>` — read the install cmd from catalog, run
- `cairn mcp status` — show configured + reachable

#### 24.13.7 What this kills + preserves

**Killed:**
- Per-pack Slack client code (use Slack MCP server)
- Per-pack Notion client code (use Notion MCP server)
- Per-pack GitHub client code (use GitHub MCP server)
- The temptation to add `services/<vendor>/` for each new system
- Version-pinning the integration SDK per pack (MCP server owns its deps)

**Preserved:**
- Pack-local DOMAIN logic — RCA synthesis, blast-radius math, scoring,
  custom validators. This is the pack's IP and stays in
  `<pack>/code/`.
- Custom executors for mutating actions (k8s_scale,
  rollback_deployment). Domain-shaped, not integration-shaped.
- Backends in `cairn/integrations/observability/` (these are
  protocol-typed read-only telemetry, not the same shape as
  request/response MCP tools).
- The MCP gateway in `services/mcp/` — this is the runtime substrate
  that makes all of the above work.

#### 24.13.8 Non-goals

- **Don't write our own MCP server framework.** FastMCP is the
  framework; we use it. If FastMCP gains features we want, contribute
  upstream.
- **Don't fork modelcontextprotocol/servers.** Use them; contribute
  improvements back; don't shadow them with parallel implementations.
- **Don't run Activepieces or Pipedream alongside cairn.** They
  are workflow-engine peers, not tool providers.
- **Don't build an Activepieces-pieces-to-MCP adapter.** Theoretical
  ~2000 integrations sounds appealing but the operational + auth
  + lifecycle complexity is enormous. If someone else builds it,
  great; we treat their adapter as just another MCP server.

#### 24.13.9 Effort

| Piece | Effort |
|---|---|
| Pack manifest `requires.mcp_servers` + `optional.mcp_servers` (extension of §24.3 loader work) | ~½ d |
| Doctor `[mcp_servers]` category | ~½ d |
| `integrations/custom/` directory convention + 1 example wrapper (Bifrost MCP server as the reference) | ~1 d |
| `mcp_catalog.toml` + lookup helpers | ~½ d |
| `cairn mcp catalog / install / status` CLI subcommands | ~1 d |
| `cairn init mcp-server <name>` scaffold (FastMCP boilerplate + auth stub + tests) | ~½ d |
| Docs + roadmap reference | ~½ d |
| **Total** | **~4 d** |

Per-integration effort thereafter:

| Case | LoC | Time |
|---|---|---|
| System has official MCP server → add to catalog | 0 Python | ~1 hour |
| System has community MCP server → vet + add | 0 Python | ~half day |
| System needs custom FastMCP server | ~50–200 | ~half to full day |

#### 24.13.10 Phased rollout

| Sub-phase | What | When |
|---|---|---|
| **P2.h** | Pack manifest extension (`requires.mcp_servers` / `optional.mcp_servers`) | Bundled with P2 (§24.3 loader changes) |
| **P3.f** | Doctor `[mcp_servers]` category | Bundled with P3 (workflow consolidation also touches the dispatcher loop where MCP gateway lives) |
| **P3.g** | `integrations/custom/` + Bifrost reference MCP server | Same as P3.f |
| **P4.c** | `mcp_catalog.toml` + CLI subcommands (`cairn mcp catalog/install/status`) | Bundled with P4 (storage layer is needed for any "remembered MCP server config" persistence) |
| **P5.e** | `cairn init mcp-server` scaffold | Optional, bundled with P5 |

P2 effort grows by ~½ d. P3 grows by ~1.5 d. P4 grows by ~1.5 d. P5
grows by ~½ d if scaffold lands. **Total roadmap: ~46 d** (was ~42 d).
