# LLM-as-judge eval — `eval.judge` capability, deepeval behind it, governed through `llm_complete`

## Context

The dataset-readiness pack wants an *evaluation* soft-signal: an LLM judges a
sample of (instruction, response) pairs for quality. Two constraints collide:

1. **Operators cannot call an LLM.** `OperationContext` (§24.20.13) is bounded —
   no LLM/gateway handle — because operators are assumed deterministic and
   replayable ("only the resolved value reaches the operator — keeps replay
   honest"). An LLM-judge is inherently non-deterministic.
2. **Vendor code must not enter core.** deepeval is the judging library we want
   (G-Eval rubrics), but `cairn/core` only holds interfaces + chokepoints.

A third fact resolves the governance worry: the LLM gateway `llm_complete`
(`core/llm/client.py`) is a module-level function whose governance — redaction
(`obs.redact_messages`), budget/routing (`get_gateway().apply`), cost +
telemetry — is **ambient (ContextVar-scoped)**, set by `cost_scope()` around the
whole run. Anything that calls `llm_complete` inside the run inherits all of it.

We also verified (compiler `_build` path, `registry.get(binding.operator)`) that
a template `operation` node resolves a **concrete operator name** — it does
**not** resolve a capability via the active profile. Profile bindings are
consumed only at core seams (redaction at the gateway, audit at the boundary).

## Decision

1. **Model LLM-as-judge as a reusable capability `eval.judge`,** provided by a
   standalone, domain-neutral bundle **`operator-eval-judge`** (`eval/judge`).
   It takes `{criteria, samples:[{input,output}], model}` → scores; it knows
   nothing about datasets, so incident / RAG / future packs can reuse it.

2. **deepeval lives in that bundle, never in core** — an `[eval]` optional
   extra, imported lazily. The judge drives deepeval's `GEval` through a custom
   `DeepEvalBaseLLM` adapter that calls **`llm_complete`**, so every judge LLM
   call is **governed** (redaction/budget/cost/audit apply ambiently).

3. **`eval/judge` is the first deliberately non-deterministic operator.** It
   reaches around the bounded `OperationContext` by importing `llm_complete`
   directly. This is the conscious exception to §24.20.13, justified only
   because the signal is **off by default, never gates, and segregated** (its
   findings are labeled non-deterministic and the deterministic `dataset/gate`
   never reads them). `supports_mock = true`; with eval disabled or no model
   present it returns `checked: false`, so the suite stays hermetic.

4. **dataset-readiness is the first consumer.** A deterministic `dataset/sample`
   operator (in `operator-dataset-checks`) extracts N (instruction, response)
   pairs per format; the pack binds `eval/judge` **by concrete operator name**
   (the only mechanism today) with dataset-quality criteria. `synthesize`
   narrates the soft scores in a separate section.

## Consequences

- **Deferred (each a clean later ADR), promote on real need:**
  - *Capability resolution in operation bindings* → makes `eval.judge`
    profile-swappable (deepeval → ragas/custom) with no pack edit. Trigger: a
    second judge provider.
  - *A core `LLMJudge` protocol* → only if a core seam (not a pack step) must
    invoke judging. Trigger: a chokepoint, not a consumer.
- The non-deterministic-operator exception is **named and bounded here** rather
  than spreading ad-hoc LLM calls across operators. Any future operator that
  calls an LLM must justify itself against this ADR.
- Replay/eval determinism is explicitly relaxed for `eval/judge` only; the six
  deterministic checks + `dataset/gate` remain byte-replayable.
