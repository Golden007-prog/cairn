# ADR-0063 — Model serving: cairn deploys + governs an endpoint, it does not host the server

Status: Proposed (2026-07-07)
Relates to: #545 (serve/vllm); the training epic (#126) + the inference trio
(#543 eval backend, #544 model/merge); the remote-job execution model
(`RemoteJobChannel`, the control worker, #127/ADR-0038); the compute-connection
model (`compute.ssh`/`compute.runpod`, #70/#121); the model registry + HITL
promote (`model/register`, ADR-0034); lineage + model card (#146, #536 AC15).

## Context

cairn closes the ModelOps loop up to **promote**: dataset-readiness → cost gate →
train → eval (#543) → model-eval gate → HITL `model/register`. It stops before
**serve** — a promoted model is not reachable as an endpoint, so the loop
`train → eval → gate → promote → serve` is open at the last hop.

Two ways to close it:

1. **cairn hosts the server.** cairn runs vLLM/llama.cpp as a long-lived service
   it owns and supervises (autoscale, restarts, routing).
2. **cairn deploys + governs.** cairn dispatches a deploy to a provider, records
   the resulting endpoint under the governed run, and gates/audits it — the
   serving *runtime* lives on the provider, not in cairn.

cairn's thesis is the **governed control plane**: it decides go/no-go, records
provenance, enforces cost, and drives long-running remote work through the
`RemoteJobChannel` (submit → poll → cancel). Serving is a *persistent service*
lifecycle (deploy/health/scale/teardown), which is a different shape from cairn's
run-to-completion runs — but the *deploy* of it maps cleanly onto a remote job.

## Decision

**cairn's `serve/vllm` operator DEPLOYS a model to a provider endpoint and
REGISTERS that endpoint under the governed run. cairn does NOT become the serving
runtime.** Concretely:

- **Capability `model.serve`**, modeled as a **long-running remote_job** (reuses
  the existing control-loop poll/cancel; deploy = submit, health-check = poll,
  teardown = cancel). Heartbeat surfaces liveness.
- **Backend enum `vllm | llama-cpp`** (shared vocabulary with #543): `vllm` =
  GPU high-throughput; `llama-cpp` = GGUF/CPU for cheap/edge. `hf` stays
  eval-only (not a serving target).
- **Target = a provider**, resolved from a compute connection (RunPod/Modal
  serverless endpoint, or a vLLM/llama.cpp server on a `compute.ssh` box) — the
  same `execution.compute_target` seam `train/remote` uses. Input is the merged
  model (from #544) or base+adapter.
- **Governed**: serving is gated by the same HITL promote approval; the endpoint
  URL + running cost are recorded into **lineage** and the **model card**, so
  "what is serving this model, what does it cost, who approved it" is auditable.
- **Output**: `endpoint_url` + `deployment_id` + `backend`; the run does not
  block on the (persistent) endpoint — it returns once healthy, and `cancel`
  tears the deployment down.

### Explicitly NOT in scope (kept out on purpose)

- cairn does not run/supervise the inference server process, autoscale it, or
  own its routing table. That is the provider's (or a dedicated serving
  platform's) job. cairn governs the deploy + holds the endpoint reference.
- No new persistent "service" entity in the engine — a served endpoint is a
  registered artifact of a run, queryable via lineage, not a first-class
  long-lived object the run loop babysits.

## Consequences

- **Loop closed, thesis intact.** train → eval → gate → promote → **serve** is
  complete, and cairn stays the governor rather than expanding into a serving
  platform it would then have to operate.
- **Reuses existing machinery** — remote-job control loop, compute connections,
  the HITL promote gate, lineage/model-card — so the operator is mostly wiring,
  not new infra (verify-upstream: no new durable mechanism).
- **CPU-validation friendly** — `llama-cpp` lets a serve deploy be validated on a
  CPU box (mirrors #536), and the deterministic-stub-when-extra-absent pattern
  keeps CI hermetic.
- **Cost of the boundary**: teardown is the user's responsibility via cancel; a
  forgotten endpoint keeps costing money. Mitigation: the endpoint + its running
  cost are surfaced in the console Remote-jobs view (already has cancel) and the
  model card, and a TTL/idle-timeout knob is a follow-up.
- **Follow-ups**: GGUF conversion for the llama-cpp path (bundled with #544's
  `to_gguf`); an idle-TTL auto-teardown; optional eval-against-the-served-endpoint
  (lm-eval `local-completions` backend) to close eval onto the real serving path.

## Build plan (after this ADR is accepted)

`serve/vllm` in the model_registry (or a new `serving`) pack: `ServeInput`
(model_uri | base+adapter, backend, compute_target, gpu, max_model_len, dtype) →
`ServeOutput` (endpoint_url, deployment_id, backend, status). Provider submit →
health-check → register endpoint; cancel = teardown. Optional extras, hermetic
stub when absent. Gated by the promote approval; endpoint + cost → lineage + card.
