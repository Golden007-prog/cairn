### 24.17 Decision: pack-level versioning + lockfile (`cairn.lock`)

§24.11 settled per-template versioning (content-addressed `template_hash`
+ `template_tags` + `runs.template_hash`). That covers "which version of
*this template* ran." It does NOT cover **"which exact set of packs at
which exact shas was deployed at 2:14 AM during the outage"** — and it
does not give us a way to express "incident pack 1.2 requires runbook
pack ≥ 0.5." Both gaps surface the moment a second deployer pulls a
community pack from a registry.

This decision adds the pack-level analogue: a **CompiledPack** artifact
(rollup of child template shas + manifest sha) and a **PackLock** file
(`cairn.lock`, resolved closure of all packs in a deploy). The
template-level work in §24.11 is the building block; §24.17 stacks on
top.

#### 24.17.1 Three artifacts at three levels (clarifying terms)

| Artifact | Scope | What it contains | Status |
|---|---|---|---|
| **CompiledTemplate** | per template | `content_hash`, StateGraph builder, parsed spec | ✅ shipped (`engine/compiled.py`) |
| **CompiledPack** | per pack | every child template/skill/policy compiled + indexed; `pack_sha = sha256(sorted(child shas) ⊕ manifest bytes)`; intra-pack provides/requires resolved | ❌ this decision |
| **PackLock** | per deploy | resolved tree: `[(pack_name, version, pack_sha, source)]` + engine version pin + integrity hash | ❌ this decision |

#### 24.17.2 What `[requires.packs]` looks like in the manifest

Today's `cairn.toml` declares abstract requirements (services,
capabilities). It does NOT yet declare pack-to-pack dependencies. Add:

```toml
[pack]
name        = "incident"
version     = "1.2.0"
cairn_engine = ">= 0.3"   # already a reserved field — enforce now

[requires.packs]
runbook = ">= 0.5, < 1.0"
postmortem = "^0.4"
# optional packs (composition tolerates absence):
[optional.packs]
chaos = ">= 0.1"
```

Semver constraint syntax: reuse Python `packaging.specifiers.SpecifierSet`
(same grammar as pip / `pyproject.toml`'s `dependencies`). Do NOT invent
a new constraint language.

#### 24.17.3 What `cairn.lock` looks like

```toml
# Generated by `cairn lock` — do not edit by hand.
# Lockfile format: 1
engine_version = "0.3.2"
generated_at = "2026-06-12T14:30:00Z"
integrity = "sha256:9f4a..."   # sha of the sorted (name, version, sha) tuples

[[pack]]
name = "incident"
version = "1.2.0"
pack_sha = "sha256:a1b2c3..."
source = { type = "local", path = "cairn/packs/incident" }

[[pack]]
name = "runbook"
version = "0.5.3"
pack_sha = "sha256:d4e5f6..."
source = { type = "registry", url = "https://packs.cairn.dev/runbook" }

[[pack]]
name = "postmortem"
version = "0.4.1"
pack_sha = "sha256:7a8b9c..."
source = { type = "git", url = "git@github.com:org/obs-postmortem.git", rev = "..." }
```

This commits alongside `cairn.toml` in the deploying-team's repo —
same model as `poetry.lock` / `package-lock.json` / `Cargo.lock`.

#### 24.17.4 What this unlocks

| Capability | How |
|---|---|
| **Reproducible deploys** | `cairn.lock` pins exact shas. `cairn serve --lock cairn.lock` refuses to start if any registered pack sha ≠ lock sha (override flag for emergencies). |
| **"Which code ran during the outage?"** | The run's stored `engine_version` + `lockfile_integrity` answer it. Git-blame the lockfile to find the deploy. |
| **Cross-pack version constraint resolution** | `cairn lock` runs `SpecifierSet` resolution. Conflict ("incident wants runbook ≥0.5, chaos wants runbook <0.5") fails at lock time, not at runtime. |
| **Drift detection** | `cairn doctor` `[lockfile]` category: warn when loader-registered pack sha ≠ lockfile sha. Catches "someone edited a vendored pack in place." |
| **Honest visualization across environments** | `cairn visualize template incident-rca --lock production.lock` — render exactly what production sees, from a dev machine. Composes cleanly with §24.16 V2. |
| **Marketplace plumbing** | Registry source type (`source = { type = "registry", url = "…" }`) is the entry point for the future pack marketplace. Lockfile is the integrity boundary. |

#### 24.17.5 Verification — what we use upstream unchanged

| Need | Upstream |
|---|---|
| Semver parsing + constraint evaluation | `packaging.version.Version` + `packaging.specifiers.SpecifierSet` (pip-aligned, already transitively present) |
| TOML reading / writing | `tomllib` (stdlib) + `tomli_w` (or fixed-shape serializer) |
| Content hashing | stdlib `hashlib.sha256` — same as `engine/compiled.py` already uses |
| Dependency-resolution algorithm | Standard backtracking SAT-lite. **If `pip`'s resolver (via `resolvelib`) is acceptable as a dep, use it.** Otherwise hand-code a simple resolver (small N — packs in a deploy are O(10), not O(1000) like pip). |
| Manifest loader | `cairn.core.pack.manifest.load_manifest` — extend, don't rewrite |
| Pack loader | `cairn.core.pack.loader.load_all_packs` — extend with optional `lock` parameter |

#### 24.17.6 Build vs reuse

| New code | Lines | Notes |
|---|---|---|
| `manifest.py` extension: `[requires.packs]`, `[optional.packs]` table parsing | ~40 LoC | Mirror the existing `[requires.services]` shape |
| `compute_pack_sha(manifest_bytes, child_template_shas)` helper | ~20 LoC | Sort, concat, sha256, same pattern as Temporal `sha_for` |
| `CompiledPack` dataclass + `compile_pack(path) -> CompiledPack` | ~100 LoC | Aggregates existing `compile_template` calls |
| Pack version resolver (constraint solver over manifest set) | ~150 LoC OR `resolvelib` integration | Decide at build time based on whether `resolvelib` ships with pip in our env |
| `cairn lock` CLI command — writes `cairn.lock` | ~80 LoC | Reuses loader + resolver |
| `cairn lock --check` (CI gate: manifest changed without lock update) | ~30 LoC | Re-runs resolution, diffs against current lockfile |
| Doctor `[lockfile]` category — drift detection | ~60 LoC | Add to existing `cairn doctor` |
| `cairn visualize --lock <file>` flag for §24.16 V2 | ~20 LoC | Lockfile-aware loader passes through to renderer |
| **Total new code** | **~500 LoC** | Plus tests |

#### 24.17.7 Anti-patterns — do not propose

| Rejected | Why | Use instead |
|---|---|---|
| Custom semver parser / constraint language | `packaging.specifiers` is battle-tested and pip-aligned | `from packaging.specifiers import SpecifierSet` |
| Custom lockfile format (JSON, YAML, bespoke) | TOML is already the manifest format; symmetry matters | `tomllib` / `tomli_w` |
| Lock-format v2 / migrations / schema versioning at MVP | YAGNI — no users yet | Single `format = 1` field; revisit when format changes |
| Runtime enforcement of lockfile drift (hard fail) | Too brittle; emergency-deploy scenarios exist | Doctor warning + opt-in `--strict-lock` flag |
| New compiled-template machinery | Already shipped (§24.11.3) | CompiledPack composes existing CompiledTemplates |
| Pack-version field as the integrity boundary | Version is human label, sha is the integrity | Lockfile pins both; sha wins for verification |
| Marketplace / registry HTTP API in this decision | Out of scope — that's its own decision when packs go public | Lockfile records `source` type but registry impl is future work |

#### 24.17.8 What's deliberately out of scope

- **Pack marketplace HTTP protocol.** The lockfile records `source = { type = "registry", url = "…" }` but the registry itself is a separate decision (post-§24.17, post-community-pack-publish-path).
- **Lockfile signing / supply-chain attestation.** Sigstore / cosign integration is community-pack-marketplace concern. MVP lockfile carries integrity sha; signing layers on later.
- **Cross-engine compatibility matrix.** `cairn_engine` field exists but enforcement is single-version-pin only; multi-version compatibility ranges are future.
- **Hot lockfile reload.** Locks at startup; restart to re-lock. No watcher.
- **Lockfile-aware HTTP pack fetcher.** Local + git sources only at MVP; registry source defined in schema but resolution stubbed.

#### 24.17.9 Effort + placement

| Piece | Effort |
|---|---|
| Manifest extension: `[requires.packs]` + `[optional.packs]` parsing | ~½ d |
| `compute_pack_sha()` + `CompiledPack` dataclass | ~½ d |
| Pack version resolver (`SpecifierSet` + simple backtracking OR `resolvelib`) | ~1 d |
| `cairn lock` CLI + `cairn lock --check` | ~½ d |
| Doctor `[lockfile]` category | ~½ d |
| `cairn visualize --lock` integration with §24.16 V2 | ~¼ d |
| Tests + worked-example pack-set fixture | ~½ d |
| **Total** | **~3–4 d** |

**Placement: P4.** Not blocking demo (single-/two-pack from one repo,
no cross-pack version conflict). Becomes urgent when the second deployer
pulls a community pack from a registry. Lands alongside §24.13 MCP
catalog + §24.16 V2 visualize as the "make packs first-class citizens"
slice of P4.

#### 24.17.10 Phased rollout

| Sub-phase | What | When |
|---|---|---|
| **P4.a** | Manifest extension + `CompiledPack` + `compute_pack_sha` (no resolver, no lockfile yet) | Early P4 |
| **P4.b** | Resolver + `cairn lock` + `cairn lock --check` | Mid P4 |
| **P4.c** | Doctor `[lockfile]` category + `visualize --lock` integration | Late P4 |
| **Future** | Registry source resolution (HTTP fetcher) | Post-marketplace decision |
| **Future** | Sigstore / cosign attestation | Post-marketplace decision |
