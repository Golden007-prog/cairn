# ADR-0050 — One home for DB-store schemas + a migration runner (no ORM)

Status: Accepted (2026-06-30)
Relates to: ADR-0047 (run provenance — content-addressed schema store + versioned installed-workflow records), ADR-0048 (workspaces — `workspace_id` scoping), ADR-0049 (definition source-of-truth). Triggered by #255 (the `/registry/installed-workflows` 500). Tracked work: #255 (slice 1) + a follow-up rollout issue.

## Context

cairn persists state across ~15 store modules and 13 separate `OBS_*_DB` SQLite
files (plus the `OBS_STORAGE=postgres://…` mirror). Every store today:

- defines its schema as an inline `CREATE TABLE IF NOT EXISTS` in its `__init__`,
- has **no schema version and no migration path** (grep for `PRAGMA user_version`
  / `ALTER TABLE` / `schema_migrations` across `cairn/core` + `cairn/services`
  returns nothing), and
- for the two stores with real typed columns (`runs`/`run_events` and
  `workflow_registry`), **hand-maintains parallel SQLite and Postgres DDL**.

This bit us directly (#255): the workspace work (#221/#223/#236) added a
`workspace_id` **column + composite PK** to `workflow_registry.installed`, but
`CREATE TABLE IF NOT EXISTS` is a no-op on an already-existing table, so existing
`~/.cairn/workflows.db` files never gained the column and every
`… WHERE workspace_id=?` raised `sqlite3.OperationalError: no such column`,
taking down the console Workflows page. The class of bug — "post-ship schema
change never reaches existing DBs" — recurs for any store and any backend.

A second, related pain: most stores are **JSON-blob stores** (`(id, …, data
TEXT/JSONB)`) where the real data shape lives in the Pydantic models and the DDL
is thin. So the data *model* is already centralized (in the models); what is
scattered and undisciplined is the **table DDL + migration**.

## Decision

**One home for the store DDL, one migration runner, no new dependency.** Stay on
raw `sqlite3` + `asyncpg` (no ORM); the persistence style and the JSON-blob stores
don't justify SQLAlchemy's weight.

1. **One definition per table, dialect output derived from it.** A table's schema
   is written once. Where SQLite and Postgres genuinely differ (`TEXT`↔`JSONB`,
   `INTEGER PRIMARY KEY`↔`BIGSERIAL`, etc.) the difference is a **small per-dialect
   type/override block inside that one definition — not a second full schema file.**
   Maintaining two complete parallel files per backend is exactly the drift that
   caused #255; it is explicitly rejected.

2. **A shared migration primitive.** `cairn/core/storage/migrations.py` provides
   the tested operations every store needs to bring an old table up to the current
   schema on connect: `table_exists`, `columns`, `pk_columns`,
   `add_missing_columns` (`ALTER TABLE … ADD COLUMN`, idempotent), and
   `rebuild_table` (create-copy-drop-rename — the **only** way to change a PRIMARY
   KEY in SQLite). Postgres uses `ADD COLUMN IF NOT EXISTS` in place.

3. **Migrate on connect, idempotently.** Each store, in its constructor, runs the
   minimal migration to reach the current schema and is a no-op once current. New
   step-wise migrations key on `PRAGMA user_version` (SQLite) / a `schema_migrations`
   table (Postgres); the *unversioned past* is handled by schema **inspection**
   (e.g. "if `installed` lacks `workspace_id` in its PK → rebuild"), since old DBs
   carry `user_version = 0`.

4. **Incremental rollout.** Slice 1 (#255) adds the primitive and fixes
   `workflow_registry`. A follow-up moves every store's DDL into the central home
   and gives each a migrate-on-connect step. Touching all stores at once in the P0
   hotfix is explicitly out of scope.

## Alternatives considered

- **SQLAlchemy Core + Alembic** (define each `Table` once → dialect-correct DDL
  auto-emitted; Alembic autogenerates migrations). This is the textbook "one schema
  → both backends" answer and remains the escape hatch **if the typed-column stores
  grow**. Rejected *now*: it's a real new dependency and a migration of ~15
  raw-`sqlite3` stores, and an ORM adds little value to the JSON-blob stores that
  dominate. Revisit when more stores need real typed columns/relations.
- **Per-backend full schema files** (what the original instinct suggested):
  rejected — it relocates the drift problem instead of removing it (see Decision 1).
- **Status quo (inline `CREATE TABLE IF NOT EXISTS`, no migrations):** rejected —
  it is the direct cause of #255 and offers no upgrade path.

## Consequences

- Existing DBs upgrade transparently on the next engine start; #255 is fixed and
  the bug class is closed for any store that adopts the primitive.
- One place to read the data model's physical schema; per-dialect differences are
  visible as overrides, not divergent files.
- A small, well-tested migration toolkit becomes the project's migration
  convention — new column/PK changes must ship with a migration, enforced by review
  + a regression test that opens an old-schema DB.
- Cost: each store needs a one-time migrate-on-connect addition (the follow-up
  rollout). Postgres PK changes on pre-existing tables still need a manual rebuild
  (documented per-store) since `ALTER` can't repoint a PK cheaply; in practice the
  PG backend postdates the workspace work, so fresh PG tables already carry the
  composite PK.
