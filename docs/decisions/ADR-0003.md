### 24.3 Decision: pack composition contract (`provides` / `requires` / `optional`)

> **Revision note (later in same session):** an earlier draft of §24.3
> modeled pack-to-pack deps with a `[requires.packs]` table and soft
> capability namespacing. The sharper model below replaces that draft:
> dependencies are declared against **capabilities**, not packs, and
> packs declare their public surface explicitly via `[provides]`.
> Everything not exported is private.

**Today's situation.** Packs are discovered via the `cairn.packs`
entry-point group. Every artifact in a pack's asset dirs is registered
globally. No notion of "internal vs public," no notion of "this pack
needs that capability." All capabilities share a global flat namespace
with last-loaded-wins on collision.

**Decision: a three-layer pack contract — assets / provides / requires
— with encapsulation by default.**

A pack can own many internal things, but only some are exported as
contracts to other packs. Think of it like a software package:

| Layer | What it means |
|---|---|
| **assets** | private implementation — files in the pack's asset dirs |
| **provides** | public contract — what other packs can depend on |
| **requires** | dependencies — capabilities this pack needs from elsewhere |
| **optional** | soft dependencies — pack works without them, richer with them |

#### 24.3.1 Manifest shape

```toml
# pack.toml — minimum MVP shape, all sections may be empty

[pack]
name = "incident"
version = "0.1.0"

[provides]
templates    = []   # public template names (e.g. "incident/deep-investigation")
capabilities = []   # public capability names (e.g. "incident.investigate")
policies     = []   # public policy names (e.g. "incident/citation-required")
triggers     = []   # public trigger names (e.g. "incident/pagerduty-incident")
schemas      = []   # public schema names (Phase 2 — see §24.3.6)
events       = []   # public event names (reserved; runtime in P3 — see §24.3.7)

[requires]
capabilities = []   # hard deps — load fails if unsatisfied
services     = []   # abstract services bound by deploying profile (existing)

[optional]
capabilities = []   # soft deps — pack loads without them
```

Real example (incident pack):

```toml
[provides]
templates    = ["incident/deep-investigation", "incident/post-incident-summary"]
capabilities = ["incident.investigate", "incident.generate_rca"]
policies     = ["incident/citation-required"]
triggers     = ["incident/pagerduty-incident"]

[requires]
capabilities = ["logs.read", "metrics.query", "traces.search", "comms.post_message"]

[optional]
capabilities = ["compliance.check", "ticket.create", "kubernetes.read"]
```

Pack body (templates, skills, tools, policies …) can be much larger
than this surface — that's the point. The pack ships 20 files; only a
small stable surface is contractual.

#### 24.3.2 Capability vs Tool — relationship made explicit

The model formalizes the distinction that already exists at the
runtime layer via `CapabilityBinding`:

```
Capability = abstract ability         (comms.post_message)
Tool       = concrete implementation  (slack.post_message)
Skill      = typed reasoning contract (format-incident-update)
Template   = executable graph         (comms/post-update)
Policy     = rule applied by Core     (pii-scan-before-send)
Trigger    = entrypoint / event source (slack-command)
```

Rule: **domain packs request capabilities, implementation packs ship
tools.** Templates inside domain packs (e.g. incident-pack) reference
capabilities; templates inside implementation packs (e.g. slack-comms)
can reference their own tool names directly.

#### 24.3.3 Loader: contribution registry

When packs are installed, Core builds a pack contribution registry:

```
Available templates:
  incident/deep-investigation
  incident/post-incident-summary
  comms/post-update
  compliance/check-message

Available capabilities:
  incident.investigate         (provided by: incident)
  comms.post_message           (provided by: comms)
  compliance.check             (provided by: compliance)
  pii.detect                   (provided by: compliance)
  logs.read                    (provided by: observability-base)
  metrics.query                (provided by: observability-base)

Available policies:
  incident/citation-required
  comms/external-message-approval
  compliance/redact-pii-before-comms

Available triggers:
  incident/pagerduty-incident
  comms/slack-command
```

Load-time validation:
- Does every `requires.capabilities` resolve?
- Are duplicate providers reported as conflict (see §24.3.5)?
- Do cross-cutting policies attach to real capabilities (see §24.3.4)?
- Are template references valid?
- Are trigger event schemas compatible?

Anything not in any pack's `provides` is **private** — invisible to
other packs and to templates outside the owning pack.

#### 24.3.4 Open call A: cross-cutting policy attachment

The compliance-pack pattern — *"compliance's `redact-pii-before-comms`
policy auto-applies to anyone calling `comms.post_message`"* — needs a
concrete attachment mechanism. Today `PolicySpec.applies_to` has
`{action_types, environments, risks}` but **no** `capabilities`.

**Decision:** extend `PolicySpec.applies_to` with `capabilities: [str]`.
A policy can target capability names; when the engine resolves a
capability call, it gathers every matching policy across all installed
packs. Policy stays self-describing.

Alternatives considered:
- Capability binding declares `policies: [str]` it must satisfy —
  inverts who-knows-about-whom.
- Separate "policy router" registry — extra mechanism, no benefit.

Real work: schema add (~½ d), policy resolution at the action-handler
seam (~½ d). Lands in P2.

#### 24.3.5 Open call B: duplicate provider resolution

If `slack-comms` and `discord-comms` both `provides.capabilities =
["comms.post_message"]`, who wins?

| | Behavior | Tradeoffs |
|---|---|---|
| **Fail at load** | Refuse to start; report conflict | Safe; needs profile override for legit cases |
| **Profile picks** | Deploy-time config picks between providers | Best prod story; no zero-config dev |
| **Last-loaded-wins** | Today's behavior | Cheap; bad failure mode |

**Decision:** fail-by-default + profile override.

Concrete: a `[profile.capabilities]` table in deploy config picks
between conflicting providers. In dev with single providers, no config
needed — failure only fires when the user installs two packs both
claiming the same capability.

```toml
# deploy profile (separate from pack.toml)
[profile.capabilities]
"comms.post_message" = "slack-comms"   # picks the winner
```

Real work: load-time conflict detection (~½ d), profile-override read
path (~½ d). Lands in P2.

#### 24.3.6 Open call C: schemas — reserve, defer to P3

Pack exports like `inputSchema: comms.PostMessageRequest` imply a
**named schema registry** resolvable across packs. Today schemas
resolve via Python dotted paths (`cairn.packs.incident.code.schemas.
db_investigation.Input`).

**Decision:** **reserve the slot, defer the registry.** MVP manifest
accepts `schemas: []` as a valid (empty) section; loader stores but
doesn't dispatch. Schemas keep dotted-path resolution through P3. If a
real cross-pack-schema use case lands, build the registry in P4.

#### 24.3.7 Open call D: events — reserve, defer to P3 (with concrete trigger)

The incident pack example exports `events: ["incident.rca_completed"]`.
That implies a pub/sub bus between packs — declarative subscribers,
many-to-many fan-out. Today's only inter-pack invocation mechanism is
cascade chains (skill A → skill B, payload-passing).

**Why this matters (concrete use cases):**

| Use case | What the bus unlocks |
|---|---|
| **Post-incident fan-out** | `incident.rca_completed` → postmortem-pack, comms-pack, ticket-pack, compliance-pack, analytics-pack, rag-pack — all subscribe declaratively. Today's cascade forces incident-pack to hard-code each successor. |
| **Action lifecycle observers** | Engine emits `action.executed` → cost-pack updates ledger; audit-pack writes audit log; rollback-pack arms auto-revert on failure; alerting-pack notices failure-rate spikes. |
| **HITL approval routing** | `approval.requested` → slack-pack, pagerduty-pack, email-pack all subscribe — delivery becomes pluggable. |
| **Cross-pack signal propagation** | `k8s.deployment_rolled_back` → incident-pack closes related open incidents; comms-pack notifies deploy channel. |
| **EventSink convergence** | The Runner already emits `skill_started`/`findings`/`action_decision`/`skill_completed` to `EventSink` for trace storage. The bus = the same stream as a live public subscription channel. Trace store and bus are *one event stream viewed two ways*. |

**Why NOT to build it now:**

| Scenario | Better tool |
|---|---|
| Pack A needs an answer from pack B | Capability call (request/response) |
| Within a single pack's logic | Direct call |
| Hot path (per-token) | In-process; bus overhead adds up |
| Strong ordering required | Workflow (Temporal child) |
| Replay/audit semantics | Trace store directly |

Events pay off when there are **5+ packs** with M-to-N coupling. We
have one. Building the bus now risks getting the API wrong before any
real subscriber exists.

**Decision: reserve `provides.events = []` as a valid slot in MVP;
runtime closure lands in P3 via the §24.10 `Bus` abstraction.**

The mechanism is no longer "future TBD" — see §24.10 for the full
`Bus` Protocol and tiered backends. The §24.3.7 closure is specifically:

- Skill manifests gain `subscribes_to: ["incident.rca_completed", ...]`
- The dispatcher routes Bus messages with matching topics to those skills
- The thin pub/sub layer = `InProcessBus` (Tier 1, no infra) by default;
  `PostgresBus` (Tier 2) for cross-process; `RedisBus` (Tier 3) for
  high-throughput
- Durable subscribers back via Temporal child workflows (post-§24.2)
  for at-least-once semantics

Until P3 closes, cascade chains stay the inter-pack invocation
mechanism for the one-to-one case.

#### 24.3.8 Visibility model — explicit by default

Everything in `provides.*` is public; everything else is private. The
recommended pack body has rich internal structure:

```
incident/
  pack.toml                              ← provides only the public surface
  templates/
    deep-investigation.md                ← exported
    internal-rca-critique.md             ← private (used as subgraph)
  skills/
    rca-synthesis.yaml                   ← private (implementation detail)
  policies/
    citation-required.yaml               ← exported
    internal-evidence-required.yaml      ← private
```

Cross-pack subgraph references resolve only against *exported*
templates. An incident pack can reference its own `internal-rca-critique`
as a subgraph; an external pack cannot.

#### 24.3.9 Cross-pack template subgraph refs

`subgraph_node` references templates by name today. Extend
`resolve_template_path` to:

1. First try the literal name against the *owning pack's* templates
   (private references stay internal).
2. Then try matching `<pack>/<name>` against exported templates from
   any registered pack.

Private templates stay invisible to external callers.

#### 24.3.10 MVP-permissive rule (no big-bang migration)

To unblock work that depends on this without forcing every pack to
migrate at once:

- A pack with **no** `[provides]` section behaves as today (everything
  visible).
- A pack **with** `[provides]` enforces encapsulation immediately.
- Migration is per-pack, at the pack author's pace.

Same incrementalism that lets §24.4 storage Phase 1 land without
rewriting every consumer.

#### 24.3.11 Incident-pack migration

The incident pack today registers 9 templates, 22 capability bindings,
3 skills, 3 policies — all globally visible.

Cleanup work (when ready):
- Decide what's public (probably the 9 templates as-is, the 22
  capabilities, the 3 policies)
- Add `[provides]` to its `pack.toml`
- Mark internal helpers as private by omission

Estimated: ½ d. Can be deferred until P2 closes or later.

#### 24.3.12 Phased rollout

| Phase | What | Effort |
|---|---|---|
| **P2.a** | Manifest schema additions (`provides`, `requires.capabilities`, `optional.capabilities`, reserved `schemas`/`events` slots). Loader parses them; permissive default preserves today's behavior. | ~1 d |
| **P2.b** | Load-time validation: required capabilities resolve, duplicate providers detected (Open call B → fail-by-default + profile override). | ~1 d |
| **P2.c** | Doctor `[packs]` category: shows providers, conflicts, missing required caps, missing optional caps. | ½ d |
| **P2.d** | Encapsulation enforcement: cross-pack lookups only see `provides.*`. Within-pack lookups see everything. | ~1 d |
| **P2.e** | Cross-pack template subgraph refs (private-first, then exported). | ½ d |
| **P2.f** | Open call A: `PolicySpec.applies_to.capabilities` + policy resolution at the action-handler seam. | ~1 d |
| **P2.g** | Tests + docs + migrate incident pack to declare its `provides`. | ~1 d |
| **Total** | | **~6 d** |

Events (Open call D) and named schemas (Open call C) defer to P3 with
the trigger conditions in §24.3.6 and §24.3.7.
