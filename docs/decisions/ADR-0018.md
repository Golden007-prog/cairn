### 24.18 Decision: bounded dynamic-plan pattern — yes; open dynamic-graph generation — no

This question recurs ("should a planner LLM emit the graph at runtime?")
and §24.7 already deferred it once as "dynamic-graph generation (planner
emits TemplateSpec → compile → run)." That deferral was correct but
left the *contract* unspecified — which means every future session
re-litigates the question from scratch. This decision fixes the
position and the contract so the next debate starts from "build it
under §24.18" or "the trigger hasn't hit yet," not from first principles.

The platform's posture (§24.16/§24.12/§24.11 collectively): **graph
shape is author-declared and content-hashed; the LLM picks tokens, not
topology.** Replay, regression eval, audit, and `template_hash` all
depend on this. Any "dynamic" pattern must preserve it or be rejected.

#### 24.18.1 Two patterns the question conflates

| Variant | What the LLM emits | Determinism story | Verdict |
|---|---|---|---|
| **Open dynamic graph** (Self-Discovery, naive) | Arbitrary topology / Python code / new node functions | ❌ Dies. `template_hash` is meaningless. Replay shows what ran but cannot pin or regress. | **Rejected.** Same axis §24.12 rejects autonomous self-modification on. |
| **Bounded dynamic plan** (this decision) | An *ordered selection* from a **declared, finite space** of registered (templates, tools, sub-flows) | ✅ Survives — with `planner_template_hash` + `plan_hash` recorded on the run. Replay reproduces both. | **Approved as a future flow type.** Build when §24.7 trigger condition (open-ended-task packs) lands. |

The first is what most "dynamic agentic" research papers do. The second
is what production systems with audit requirements actually want.

#### 24.18.2 The five-constraint contract (non-negotiable)

If/when we add a `dynamic_plan` flow type, all five hold or it does not
ship. These are what keep the determinism axis intact:

| # | Constraint | Why |
|---|---|---|
| **1** | **Plan space is declared in template frontmatter.** Explicit allow-list of capability names + sub-template refs the planner MAY compose into a plan. | Bounds the search space. Eval can enumerate the universe of possible plans. Audit shows what was *possible*, not just what happened. |
| **2** | **Planner emits a `Plan` Pydantic schema** — an ordered list of `{step_kind, ref, inputs, condition}`. NOT arbitrary code, NOT a StateGraph spec, NOT prose. | Pydantic-validated. Rejectable at emit time. Diffable across runs. Structured-output coercion via the LLM provider's JSON-mode. |
| **3** | **`plan_hash = sha256(canonical_json(plan))` recorded on the run.** Plan persisted in event store alongside `template_hash` and `template_tags` (§24.11.3). | Replay re-applies the same plan. Regression eval compares plan distributions across planner versions. `runs.plan_hash` column. |
| **4** | **Plan compiles to LangGraph at run-start, not at LLM-emit time.** The planner emits *data*; a deterministic compiler builds the StateGraph from that data. Same compile/run seam already used by `_build_state_machine`. | No new substrate. Same content-hashing model. Plan-to-graph compilation is pure and replayable. |
| **5** | **Eval gate: `cairn eval --planner-template <name>`** runs across a dataset and reports plan-diversity + plan-agreement metrics. CI gate fires when planner regresses. | Without this, planner drift is undetectable. Same value prop as §24.11.4's `--compare-against` flag, applied to planners. |

A `dynamic_plan` template that violates any of these does not get to
exist on this platform. The compiler should refuse to build it.

#### 24.18.3 Example frontmatter (what authors would write)

```yaml
---
name: open-research-investigation
version: 1.0.0
flow:
  type: dynamic_plan
  planner_model: gpt-4o
  max_plan_steps: 12      # hard ceiling — guard primitive at plan validation

plan_space:
  # Constraint 1 — declared allow-list. Plans referencing anything not
  # in these lists are rejected before compilation.
  allowed_capabilities:
    - logs.search
    - traces.search
    - metrics.query
    - rag.lookup
    - git.blame
  allowed_subtemplates:
    - incident/db-investigation
    - incident/blast-radius
    - incident/error-spike-triage
  allowed_step_kinds:
    - tool_call
    - subgraph_invoke
    - parallel_fan_out    # uses Engine cap #89
    - guard_check

plan_schema: cairn.core.engine.dynamic_plan.Plan   # Pydantic class

eval:
  planner_dataset: evals/open-research-cases.jsonl
  min_plan_diversity: 0.3       # 30% of cases must produce distinct plans
  min_step_validity: 1.0        # 100% of emitted steps must be in plan_space
---
```

The `plan_space` table is the audit boundary. Anything outside it is a
type error, not a runtime surprise.

#### 24.18.4 Substrate check — what would actually need to build

| Piece | Status | Effort |
|---|---|---|
| Planner template (structured-output `prompt` flow returning `Plan`) | Already supported — any current `prompt` flow with `output_schema` does this | 0 (wire) |
| `Plan` Pydantic schema + step-kind enum | New | ~½ d |
| `[plan_space]` table parsing in manifest/template frontmatter | New, mirrors §24.17 `[requires.packs]` shape | ~½ d |
| Plan→StateGraph compiler (reuses `_build_state_machine` mechanics) | New, ~150 LoC | ~1 d |
| Plan validation (every emitted step is in `plan_space`) | New, ~50 LoC | ~¼ d |
| `plan_hash` computation + `runs.plan_hash` column + event-store persistence | New, mirrors §24.11.3 template_hash exactly | ~½ d |
| Replay: load by `plan_hash`, reconstruct graph from persisted plan | New, ~80 LoC | ~½ d |
| `cairn eval --planner-template` mode (plan-diversity + agreement metrics) | New eval mode atop §24.11.4 infrastructure | ~1 d |
| Doctor `[dynamic_plan]` category — warns on missing plan_space, unbounded allow-lists, missing planner dataset | New | ~½ d |
| **Total** | | **~4–5 d** |

LangGraph already supports building a StateGraph at runtime from a spec —
so substrate-wise this is "wire" not "build." The actual work is the
**policy + eval + audit machinery** around it.

#### 24.18.5 Verification — upstream pieces unchanged

| Need | Upstream |
|---|---|
| Structured output → Pydantic | LangChain `.with_structured_output(Plan)` — already used by current templates |
| StateGraph runtime construction | LangGraph public API — `StateGraph(...).add_node(...).compile()` is callable from a non-LLM compiler step |
| Per-step durability | Existing Restate / Temporal handlers (§24.2) — the executed graph nodes route through the same handlers as static templates |
| Content hashing | `compute_content_hash` pattern from §24.11.3, applied to canonical plan JSON |
| Eval dataset shape | Existing eval infrastructure (§24.5 + §24.11.4 regression) — extend with plan-comparison scorer |

No new infra. The contract is the work.

#### 24.18.6 Anti-patterns — explicitly rejected

| Tempting addition | Why no | Use instead |
|---|---|---|
| LLM-generated Python in plan steps | Breaks the "data not code" boundary. The platform's audit story dies. | Registered capabilities only; new logic ships as a `python_node` in a pack |
| Replanning that adds NEW capabilities mid-run | Plan space must be closed at plan-emit time. | Replanning may re-order, remove, repeat steps from the allow-list — it cannot extend the universe |
| "Soft" plan space (string match instead of explicit allow-list) | Audit ambiguity — what does "logs.*" actually permit? | Referential allow-list; doctor refuses wildcards |
| Skip `plan_hash` because "the plan is in the trace" | Hash is the index for regression eval. Trace is the receipt. Different jobs. | Both. Hash + trace. |
| Allow planner to emit topology directives (loops, branches) directly | Topology becomes LLM-controlled → determinism dies | Topology is implied by step `condition` + `step_kind`; compiler chooses edges deterministically from the plan |
| Skip the eval gate ("we'll add it later") | Without the gate, planner drift is undetectable → silent quality regression | Eval gate ships in the same PR as the flow type, or the flow type doesn't ship |
| `dynamic_plan` inside a `dynamic_plan` (nested planners) | Compounding non-determinism, exponential audit blow-up | One planner per template; sub-templates are static |

#### 24.18.7 When to build (the trigger condition)

§24.7 names the right trigger: **"when open-ended-task packs land."**
Made concrete here:

| Use case | Static templates suffice? | Build trigger? |
|---|---|---|
| Incident response (current incident pack) | ✅ Yes — variability is in *which* sub-template runs; `selector` covers it | ❌ Do not build |
| ModelOps (drift detection, eval, rollback) | ✅ Yes — same structure every time | ❌ Do not build |
| Post-mortem generation | ✅ Yes — deterministic pipeline | ❌ Do not build |
| Open-ended research assistant (steps vary by research question's *shape*, not just parameters) | ❌ No — selector tree would have exponential branches | ✅ Build |
| Threat-hunting (analyst poses a hypothesis; investigation shape depends on hypothesis kind) | ❌ No | ✅ Build |
| Customer-support agent over an open ticket space | ❌ No | ✅ Build |

The line: **if `selector` over a fixed branch tree would have more than
~20 leaves and the choice is data-driven not template-driven, you've
crossed into `dynamic_plan` territory.** Below that line, static
templates are cheaper, more auditable, and more eval-tractable.

#### 24.18.8 What's deliberately out of scope (now and after build)

- **Open dynamic graph generation** (LLM emits StateGraph code). Permanently rejected.
- **Autonomous plan-space expansion** (planner adds new capabilities to its own allow-list). Author-only.
- **Cross-plan learning** (planner remembers prior plans and biases future ones without explicit memory wiring). Goes through the standard memory store like everything else.
- **Multi-planner debates** (two planners argue about the plan). Could be built post-§24.18 as a `state_machine` over two `dynamic_plan` subgraphs, but not part of the base contract.
- **Self-modifying plans during execution** (mid-run, the planner rewrites the remaining plan based on observation). The replanning mechanic in Plan-and-Execute pattern #1 already covers this *inside* a static state_machine — `dynamic_plan` doesn't need to reinvent it.

#### 24.18.9 Effort + placement

**Total: ~4–5 d** when the trigger condition hits.

**Placement: post-trigger.** Not in the current P1–P7 plan. When the
trigger condition fires:
- Lands as its own mini-phase between the triggering pack's scaffolding and its first eval run
- Depends on §24.11.3 (template content hashing — shipped) and §24.11.4 (`--compare-against` eval — shipped)
- Composes with §24.16 visualization (planner template renders normally; emitted plans render as ephemeral graphs at run time)
- Composes with §24.17 lockfile (plan_space allow-lists pin to specific pack versions, lockfile pins pack versions → plan space is reproducible across deploys)

#### 24.18.10 What this section closes

- The recurring "should the planner emit the graph?" debate gets a permanent answer: **yes, bounded; no, open.**
- The contract (§24.18.2's five constraints) is the part future-me will be tempted to skip when excited about the pattern — committing it here means it cannot be quietly dropped.
- The trigger condition (§24.18.7) is concrete enough to argue against: "no, incident response doesn't need this" stays a defensible position with the use-case table to point at.
