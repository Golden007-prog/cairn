# ADR-0073 — The Playground: a governed sandbox surface for trying workflows

Status: Proposed (2026-07-14)
Relates to / builds on: ADR-0072 (dry-run → preflight verdict + "Promote to run"),
ADR-0052/0053 (environment backends + policy scoping — the binding mechanism),
ADR-0068/0070 (operator config surface + scoping), ADR-0071 (config presets) +
#793 (input presets), ADR-0047 (run provenance / receipts), ADR-0069 (pipeline
view, reused component), ADR-0012 (suggestions: propose-not-apply), #800 (CLI
`preflight` / `run --dry-run`). Supersedes the deferred #801 (model-chat
playground). Companion artifacts: `design/cairn-playground-spec.md` (product
spec) + `design/cairn-playground.html` (first prototype) +
`design/cairn-playground-v2.html` (**value-forward mockup — the current design
of record**).

## Purpose — why the Playground exists (the north star)

Every platform ships a playground to do one job: **collapse time-to-value.**
(Activation research: TTV < 5 min = excellent; demo data beats empty states;
3-step flows convert ~72% vs ~16% for 7-step.) But cairn sells **governance**,
which has a unique problem: it is *invisible until something is prevented* — you
can't feel a cost cap until it holds, or trust a gate until you watch it block
bad data. So the Playground's job is sharper than "try a workflow":

> **Make governance tangible, with value before setup.** A first-time user,
> with **nothing connected**, on **their own data**, watches cairn make a
> governance decision — block / cap / gate / cite — in **under 60 seconds**, and
> understands the same decision holds in production.

That sentence is the **definition of done**; every feature is measured against
it. It also makes the Playground cairn's **interactive tutorial** — the fastest
way to learn what a gate / env / policy / HITL / pipeline *is* is to watch one
act on your own data.

Design invariants that follow from the Purpose:
- **Value before setup** — runs with **no connections**; the sandbox env
  auto-provisions; demo data ships pre-loaded (never an empty state).
- **Real decisions, not mocked** — a mocked gate proves nothing. Reads +
  analysis run **live** on a capped sample; only true external *writes* are
  stubbed (refines §3 — mock only write-class ops).
- **Self-contained loop** — inspect → tweak → re-run happens on the page;
  metrics/findings/eval render inline; leaving is optional.
- **Teach by doing** — each governance concept is named where it appears.
- **One click to production** — every session ends a click from a real governed
  run (a bridge, not a cul-de-sac).

## Context

ADR-0072 delivered the **verdict** (side-effect-free ready/blocked) and named
"the iterative dry-run loop" as *the* playground, explicitly deferring a
LiteLLM-style model-chat playground (#801). Since then the product spec has
grown that loop into a **first-class surface**: a console page where a user
picks from a curated set of workflows, drops in config/values/environment, runs
it *safely*, inspects, tweaks, and promotes to a real governed run — cairn's
answer to LiteLLM's playground, but where **the unit is a governed workflow run,
not a prompt**.

Two things ADR-0072 did not decide, and this ADR must:

1. **How is a playground run actually isolated?** ADR-0072's "playground
   environment with stubbed bindings" makes zero-side-effects a property of
   *operator capability metadata being complete* — i.e. by discipline, not by
   construction. That is too weak for the spec's "try-before-install" case,
   which runs **untrusted registry packs** whose declarations cannot be trusted.
2. **What is the surface, concretely** — pre-selected workflows, the run/sandbox
   choice, and the config/values/infra/presets composition that makes it more
   than a second Run tab.

## Decision

### 1. The Playground is a first-class surface, unit = a governed workflow run

Route `/console/w/{ws}/playground`. It offers a **curated, pre-selected set of
runnable workflows** (the flagship dataset-readiness / finetune / incident-rca
family + registry "try before install"), not the full installed list. It is
**not** a workflow builder, a chat, a notebook, or a separate engine (§ Non-goals).
The dry-run **verdict** (ADR-0072) is its inner loop; "Promote to run" is its exit.

### 1a. Eligibility is **derived from capability classes**, not hand-curated

A workflow is offered in the playground iff its plan declares **no `compute`/GPU
capability** — i.e. it can run cheap + fast on a sample. dataset-readiness, eval
(sampled), incident-rca (read-only) qualify; **finetune and quantize do not**
(they need a GPU) and are shown **disabled with the reason** ("needs GPU — not
runnable in sandbox"), never silently hidden. The engine already knows each
operator's capability class, so eligibility — and the per-workflow **metric set**
(§ below) — are both derived, not maintained by hand. Simulate-mode for the GPU
families (plan + cost only, no execution) is a later maybe, not P0.

### 1b. Metrics + report are **schema-driven** per workflow

The Report band renders from the pack's report contract (the same UIContract
mechanism the Run form uses) — dataset-prep shows rows-kept/PII/leakage/gate;
eval shows score/pass-rate/per-category; rca shows confidence/#citations/coverage.
Never hardcoded per family.

### 2. Two run modes: **sandbox** (default) or **direct**

- **Sandbox** — a safe, isolated preview run. The default.
- **Direct** — a real governed run in a target environment. This IS the
  ADR-0072 "Promote to run" path, surfaced as the deliberate graduation.

"The command changes — the guarantees don't" holds in both: a sandbox run is a
real content-addressed run producing a real receipt, tagged `sandbox`.

### 3. Isolation is **tiered by trust** — kernel containment where it's needed

Zero side effects must be a property of *construction*, not of operator honesty.
So isolation is layered, and the layer is chosen by the trust level of what runs:

| Tier | What runs | Isolation |
|---|---|---|
| **A. Binding-stub** | installed, first-party workflows | In-process on the reserved `playground` environment (§5). Write operators stubbed, notifications captured, gates simulated, LLM forced-cheap, reads live. Fast, cross-platform. |
| **B. Kernel sandbox** | untrusted / registry `try-before-install` packs | **subprocess + bubblewrap** — a jailed `cairn run <wf> --input slice.json --env playground`, streaming its JSONL events back to the console. Read-only FS binds + tmpfs scratch + no creds mounted + user/PID namespaces. Side-effect impossibility is enforced by the **kernel**, independent of what the pack declared. |

Bubblewrap is **Linux-only**; Tier B degrades on non-Linux (local macOS dev) to
Tier A, Docker, or direct-run-only. The two tiers are **complementary, not
either/or**: Tier B gives *containment* (no FS escape, no credential theft);
the binding layer still supplies the *useful semantics* (captured notifications,
simulated gates, cheap LLM) that a kernel jail cannot express.

### 4. Egress: default net-open-no-creds; bwrap + allowlist proxy is a slice

The tension: full `--unshare-net` also kills the spec's "reads stay live"
(S3/HF sampling) and the LLM call, and bubblewrap can only toggle the net
namespace whole — it cannot allowlist by host. Decision:

- **Default**: network stays reachable, but **no credentials are mounted** into
  the jail — a run can reach the model gateway / read sources it's *given*, and
  can steal nothing. Writes still can't land (no creds, read-only FS).
- **Hardened (follow-on slice)**: pair bwrap with an **egress-allowlist proxy**
  so only the model gateway + declared read sources are reachable. Tracked
  separately; not required for P0.

### 5. The reserved `playground` environment supplies the binding semantics

Per ADR-0052/0053, a per-workspace environment named `playground`, created on
first use, whose bindings are: reads **live** · writes **stubbed** · notifications
**captured** ("would have sent…") · human gates **simulated** (verdict shown, never
blocks) · LLM roles forced to the **cheap** role · GPU **denied** (finetune/quantize
run in simulate mode) · **hard cost cap** (default $0.25/run, $2/day/user, not
UI-configurable) · same run store, runs tagged `sandbox`, excluded from Insights
aggregates, auto-pruned after 30 days. Enforcement lives in bindings — the same
mechanism prod uses — so `cairn doctor` verifies the sandbox like any env, and no
new engine execution path is introduced for Tier A.

### 5a. Storage — no table for RUNS; one small table for UPLOADED samples

Most of the playground rides existing stores; **runs need no table**:

| Need | Store | New table? |
|---|---|---|
| sandbox runs | existing runs store, tagged `sandbox` | no |
| the `playground` environment | environment store (ADR-0052) — one env row | no |
| config / input presets | `workflow_presets` / `input_presets` (ADR-0071, #793) | no |
| gate what-if history | reports of last-N real runs (runs store) | no |
| rerun lineage (`parent`) + `sandbox` tag | fields on `Run` (JSON blob, shipped #826) | no |
| daily cost-cap accounting | `SUM(cost)` query over sandbox runs / user / day | no |

**But user uploads (Q1) DO need one.** An uploaded sample is real bytes with a
lifecycle (sample → run → **auto-purge**), which the runs store doesn't model. So
add a small **`playground_upload`** table: `{id, workspace_id, filename,
content_type, row_count, sampled_from, storage_ref, created_at, expires_at}` —
metadata + a pointer; the bytes live in the scratch/blob store, TTL-purged (default
7 days). Small, bounded, and the *only* new table the epic needs.

**Saved sessions** (a re-openable composition = workflow + env + config-preset +
input + dataset ref) **start as `input_presets`** (already a named input set) and
graduate to a dedicated `playground_session` table only if share/resume demands
persisting the whole composition together — deferred, not P0.

### 6. The Playground is the composition surface for the config machinery

Its differentiator over the Run tab: it is the **one place** to drop in and swap,
per run, all four axes we already shipped — then dry-run and promote:

- **config** → operator config knobs (ADR-0068/0070)
- **preset values** → config presets (ADR-0071) + author-recommended (#791)
- **values** → input presets (#793)
- **infra / environment** → environment bindings (ADR-0052/0053)

Loop: pick workflow → drop config preset + input preset + target env → **dry-run
verdict** (ADR-0072) → run (sandbox/direct) → inspect → tweak → **partial rerun**
(§7) → promote. The playground is the *consumer* that turns four scattered tabs
into one experimentation surface.

### 7. Retention features (P1): step-level rerun + gate what-if

- **Partial rerun** — because runs are content-addressed, editing one step's
  parameter re-executes only that step + downstream; upstream is served from
  cache. CLI: `cairn run <wf> --from-step <step> --set <k>=<v> --reuse <run-id>`.
  Receipts record `parent:` + a param diff (lineage). Also the "Reproduce in
  playground" path from any failed real run.
- **Gate what-if** — the gate verdict is a pure function of (report, thresholds),
  so a threshold change re-scores **client-side, instantly**, and can be applied
  to the reports of the last N real runs — "would have blocked N of your last 10."
  "Adopt threshold" writes a **policy proposal** (never auto-applied — ADR-0012).

### 8. Supersede #801 (model-chat playground)

The prompt-as-unit chat playground was deferred because it duplicates LiteLLM.
This ADR is the correct reframing — **workflow-as-unit**. A model-chat affordance,
if ever wanted, folds in as an optional per-step probe *inside* a run, not a
separate surface. #801 is closed by this ADR.

### 9. Feature set (P0, derived from the Purpose)

Each row: a Purpose value (user's words) → the feature → the pattern it borrows.

| # | Value | Feature | Borrowed from |
|---|---|---|---|
| 1 | run in 1–2 clicks + meaningful insight | **Instant run** — the page opens with a flagship workflow **and demo data already loaded** (never an empty state); one click → inline verdict + report + findings-cited-to-rows. TTV target < 60s. | demo-data-not-empty-state (activation research); OpenAI/LangSmith one-click |
| 2 | tweak env/config/input/workflow + re-run | **Iterate + compare** — swap any drop-in, re-run; **side-by-side diff of the last 2 runs** (what changed → what it did to the metrics/verdict). | LangSmith side-by-side compare; n8n pin + **edit** data |
| 3 | upload own data | **Upload + auto-sample** (≤1k rows / ≤10 MB; larger → sampled + labeled), ephemeral + TTL-purged; **edit the sample** to inject an edge case (a PII row, a leaked pair) and watch the gate catch it. | n8n edit-pinned-data; Stripe isolated test data |
| 4 | metrics/report/eval inline before ejecting | **Inline report band** (§828, §1b) — findings cited to rows · schema-driven metric tiles · verdict · cost. **Gate what-if** (threshold slider + "would have blocked N of your last 10"). "Full report" is a *secondary* link; **never auto-navigate**. | LangSmith inline eval; cairn-native what-if (no adjacent tool has it) |
| 5 | zero setup | Runs with **no connections**; `playground` env auto-provisions; demo data bundled; cost-cap + write-stubbing make it safe by construction. | Stripe "you start in a sandbox"; PLG zero-config |
| 6 | teach config/env/policy/HITL/workflow/pipeline | **Learn-by-doing layer** — each concept is named inline where it appears (a pause → "this is a HITL gate"; the env selector → "bindings/infra"; a threshold → "this is a policy"), plus a 3-step first-run coach-mark. The Playground *is* cairn's tutorial. | 3-step tours (72% completion); role-based guidance (+30–50% activation) |
| 7 | storage | §5a — a `playground_upload` table + TTL for samples; sessions ride `input_presets`. | Stripe isolated data lifecycle |

**The foundational unlock (do first):** feature 4 and 6 are worthless if the run
is faked, so the **read/write split** (§3 refined — mock only write-class ops,
keep reads/analysis live) is the prerequisite for *real* metrics. That, plus
**gate what-if** (#4) and **upload** (#3), is the re-derived P0 — not the promote
diff modal, which is parked until the above make the sandbox genuinely useful.

**UX framing (from the `-v2` mockup review):**
- **The hero is the governance *decision*, not the metrics.** A prominent
  "cairn caught it — before a GPU spun up" verdict with the value line ("caught
  in 8s for $0, vs ~$2.40 + 40 GPU-min after training"). The catch *is* the wow.
- **Teach by contrast, not by scaring.** The curated sample *passes* (positive
  first impression); a **"⚡ Try breaking it — inject a PII row"** action lets the
  user *cause* the block and feel the gate react. Frame a block as "cairn
  protecting you," never "your data is bad."
- **Explain mode** — the inline concept-naming (feature 6) is a header toggle,
  **on by default**, dismissible for power users.
- **Verdict shows the clean↔broken states** as a segment toggle so the contrast
  is one click, not a re-run.

### Non-goals

Not a workflow builder/editor (DAGs stay in packs/Graph), not a chat (Ask cairn
plans; the playground executes), not a notebook (no arbitrary code — only
installed workflows + their declared parameters), not a separate engine (if a
feature needs execution behavior the real rail lacks, the design is wrong).

## Consequences

**Reused (already shipped — most of P0):** the preflight verdict (#797), console
DryRunPanel + Promote (#798/#799), the CLI face (#800), the pipeline view
component (ADR-0069/#773, "reuse don't fork"), content-addressed runs (rerun
cache substrate), environment bindings + `doctor` (ADR-0052/0053), and the full
config/preset/input-preset machinery (ADR-0068/0070/0071, #793).

**Net-new (the real build):** (a) the reserved `playground` environment + its
capability-class binding table; (b) the **bwrap subprocess seam** + JSONL event
streaming back to the console (Tier B); (c) the egress-allowlist proxy (hardened
slice); (d) step-level partial rerun (`--from-step/--set/--reuse` + lineage);
(e) gate what-if history re-scoring.

**Risks / dependencies:**
- **Capability-class metadata completeness** gates Tier A ("writes stubbed by
  construction" needs reliable read/write/compute declarations — the same gap
  that keeps ADR-0072's credential leg advisory). Tier B (bwrap) is precisely the
  mitigation for the untrusted case; a **spike to audit that metadata** should
  gate P0's Tier-A claims.
- **Platform**: bubblewrap is Linux-only; Tier B is unavailable on dev laptops —
  the fallback ladder (Tier A / Docker / direct-only) must be explicit.
- Simulate mode for finetune/quantize must resolve the full plan + cost without
  compute — leans on `compute/estimate` + the cost gate already shipped.

## Rollout (epic + slices)

**Shipped (P0.a — the plumbing):** eligibility API (#825) · console page +
compose (#827) · sandbox runs via mock mode (#826) · inline report band (#828).

**Re-derived P0.b — make it *useful* (this reprioritization):** the plumbing
runs, but a mocked run proves nothing (§Purpose). Build, in order:
1. **Read/write split** — mock only write-class ops; reads + analysis run **live**
   on the capped sample → **real** metrics (the foundational unlock; finishes the
   #830 capability audit).
2. **Gate what-if** — threshold slider + "would have blocked N of your last 10"
   (the felt-governance moment; client-side re-score, cheap).
3. **Upload + auto-sample** your own data (§Q1) + edit-the-sample edge cases.
4. **Teach-by-doing layer** — name each governance concept inline + a 3-step
   first-run coach-mark.
5. **Instant-run default state** — open with a flagship workflow + demo data
   loaded (never empty); < 60s to first decision.

**Parked:** the promote **diff modal** (old #829) — low value until 1–5 land; when
it returns it is a *readiness gate* ("to run for real, connect X"), not a modal.

**P1 — retention:** side-by-side compare of the last 2 runs · step-level rerun
(cache + lineage) · connected-source sampling · "Reproduce in playground" from
failed runs.

**P2 — breadth + hard isolation:** **Tier B bwrap subprocess** for registry
try-before-install · egress-allowlist proxy · simulate mode for finetune/quantize
with per-profile cost comparison · incident fixtures · eval/redteam sampled runs.

Entry points (spec §9): sidebar item · workflow-card "Try in playground" ·
registry "Try before install" · failed-run "Reproduce in playground" · Ask-cairn
"test this plan first".
