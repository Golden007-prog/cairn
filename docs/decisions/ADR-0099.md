# ADR-0099 — A pipeline declares the services it needs; the launch door enforces it

- **Status:** PROPOSED
- **Date:** 2026-08-31
- **Issue:** #1826 (epic)
- **Builds on:** ADR-0052 §1 (`profile_backends` self-describing backends), #390 (`cairn deploy doctor`), ADR-0084 D9 (the launch door), #1792 (`pipeline explain`), ADR-0097 (compute lifecycle as governed legs), #1793 (the no-bolt-on rule)

## Context

`deploy/prod/docker-compose.yml` defines **19 services**. Three carry no
`profiles:` key and therefore always start — `caddy`, `server`, `postgres`. The
other sixteen are gated behind ten compose profiles, and which of them run is
decided by one hand-edited `COMPOSE_PROFILES` line in the deploy `.env`.

Nothing connects that line to what a pipeline actually needs. The consequences
are the ones this project keeps rediscovering:

1. **A missing service is not a refusal, it is a silent stall.** With
   `OBS_RUNTIME=temporal` and no `temporal` profile, the stack comes up healthy,
   the launch door accepts the pipeline, and nothing ever executes. The failure
   surfaces as an absence.
2. **Nobody can answer "what does this pipeline need?"** without reading the YAML
   and knowing which engine each leg resolves to. On 2026-08-31 the prod box ran
   **11** containers; at least two (`metaflow-service` + its Postgres) serve a
   cross-box capability nothing currently uses, and `temporal-ui` is a debugging
   console reachable only through an SSH tunnel.
3. **The knowledge lives in an operator's head**, which is precisely the
   condition #1793 exists to eliminate. Having to know that a pipeline needs a
   profile, and to hand-edit `.env` before it will run, is a bolt-on.

`cairn deploy doctor` (#390, `core/deploy_check.py`) already catches exactly this
class of mistake — its canonical example in the source is
`OBS_RUNTIME=temporal` without `--profile temporal` → fail loud. But it is
**env-wide, deploy-time, and opt-in**: it answers "does this `.env` agree with
these profiles?", never "can *this pipeline* run here?", and nothing on the
launch path calls it.

## The prior art in this repo, and its lesson

Pack manifests once carried `[requires].services = [...]`. It was **deleted** in
the Phase-1 manifest migration, recorded in `core/pack/manifest.py` as
*"zero packs, read by zero consumers."*

That is the governing lesson for this ADR: **a declaration with no enforcement
point rots.** The design below therefore leads with the consumer (a refusal on
the launch path) and adds the smallest declaration that consumer cannot derive.

## Decision

### 1. Derive the requirement wherever it is already implied

A leg's required service is a consequence of its resolved engine, and that
resolution already exists: `pipeline_explain` prints `engine`, `flow_kind`,
`target` and `selected_via` per leg, computed by calling the same code that
executes. `profile_backends.BACKENDS` already maps each capability to its
environment variable and default.

So the mapping to add is **service value → compose profile + reachability
probe**, as data beside `BACKENDS`, in the same idiom ("adding a backend = one
entry"). No new manifest field for anything derivable from the plan.

### 2. Declare only what is not derivable, at the operator

Whether a pipeline needs MLflow depends on whether some leg calls
`model/register`. That is a property of the operator, not of the plan shape, so
it is declared beside `risk` in the operator's `pack.toml` — where rule 7's
manifest-sync and drift gates already hold declarations honest against the
installed class. Anything declared here must be a service the operator *uses at
runtime*, never a preference.

**The pipeline's requirement set = (services derived from resolved engines) ∪
(services declared by the operators its legs invoke).**

### 3. Enforce at the launch door, before the record exists

`launch_pipeline` is the one convergence point for the CLI, the console and the
cron trigger — where required-input validation, #1802 type coercion and #1252
policy gates already fire ahead of any record or any spend. The service check
joins them, reusing `check_deploy`'s comparison rather than re-implementing it,
and the refusal names the remedy:

```
pipeline training/continual-learning-managed requires the `temporal` profile
  — OBS_RUNTIME=temporal is set but no worker is reachable.
  Add it: COMPOSE_PROFILES=temporal,metaflow-service,mlflow
```

### 4. Refuse; do not auto-start (this rung)

The control plane detects and refuses. It does **not** start containers.

Auto-start would give the control plane power over its own substrate, and the
evidence from 2026-08-31 runs the other way: every failure that cost a session
that day was a *silent degradation* — a blank cost gate (#1804), a benchmark
that stubs when its dependency is absent, an adapter written to `/tmp` (#1715).
Loud refusal is the posture that has been earning its keep.

A later rung has a clean precedent if it is ever wanted: ADR-0097's
`compute/acquire` powers on an EC2 box **after an authorization gate**. Starting
a compose profile behind the same gate would mirror it exactly. Out of scope
here.

### 5. Run the mapping backwards to size a deployment

The same table read in the other direction answers "what is the minimum stack
for the pipelines I intend to run?" — `cairn deploy plan <pipeline>...` emits the
`COMPOSE_PROFILES` line. The check and the generator are one table, two
directions; shipping the check without the generator leaves operators guessing
at exactly the moment the check starts refusing them.

## Consequences

- **Mandatory shrinks to three.** `caddy`, `server`, `postgres` — enough for the
  door to answer and record. Everything else becomes conditionally required,
  per pipeline, with its absence a refusal rather than a stall.
- **A new failure mode at launch.** Pipelines that "worked" on an
  over-provisioned box will now be refused on an under-provisioned one. That is
  the point, but it means the generator (5) is not optional.
- **The requirement set must stay derived.** The one thing that would recreate
  `[requires].services` is a hand-maintained per-pipeline service list. Anything
  a human types twice will drift; the check must read what the plan resolves.
- **Reachability is not configuration.** Checking that `COMPOSE_PROFILES`
  contains `temporal` is weaker than checking a worker answers. The probe is
  what makes this a real gate rather than a lookalike — a profile can be enabled
  and the container still dead, which is exactly how the `prefect` container sat
  in a restart loop for weeks.

## Rejected

- **A dependency-injection / service-registry framework.** Compose profiles are
  the mechanism and they work; this ADR adds a *reader* for them.
- **Per-pipeline `requires:` blocks in the pipeline YAML.** This is
  `[requires].services` again — a second source of truth that drifts from the
  engines the plan actually resolves.
- **Making every optional service mandatory** so the check always passes. That
  is today's 11-container box, and it is what prompted the question.
- **Warning instead of refusing.** A warning at launch is read once and then
  never; the stall it predicts arrives minutes later wearing a different mask.
