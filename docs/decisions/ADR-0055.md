# ADR-0055 — Registry + real server-side install (lifecycle + install-record)

Status: Proposed (owner-approved decisions 2026-07-03; ADR-first before build — #211)
Relates to: the distribution epic #209 / ADR-0045, the registry catalog
(`cairn-registry/index/catalog.json`, `cairn/core/registry_catalog.py`), pack
discovery (`load_all_packs` → in-memory `_PACKS` + operator registry), the two
lockfiles (`cairn.lock` pack closure, `uv.lock` python), operator isolation #204,
sandboxing #205, and the storage-unification epic #427 (the install-record store).

## Context

"What's installed" is today derived purely from **live entry-point discovery**
at startup — runs/events go in the DB, but **installed packs do not**. There is
no authorized, recorded, reversible server-side install of a pack from the
registry (or a manual PyPI/wheel/VCS ref). Installing arbitrary packages
server-side is **RCE-class**, so it needs an explicit lifecycle + authorization +
record. Four distinct indexes must stay separate: registry **catalog** (what's
available) · **cairn.lock** (shipped closure) · **install-record** (what THIS
deployment installed + lifecycle — the gap) · runs/events (execution history).

## Decision

**1. Discovery refresh = restart-required MVP.** After a successful install the
engine **restarts** to re-run entry-point discovery. Simple, safe, deterministic
for an RCE-class operation. In-process **hot-reload** of entry points is a
follow-up (filed separately) — the risk (stale module state, partial reloads,
in-flight runs) isn't worth it for v1.

**2. Env/isolation = container-or-shared only (no per-pack venv).** A lean pack
installs into the engine's single shared env (discovered via entry points); a
heavy/conflicting pack (torch/CUDA) declares `docker`/`remote_job` and runs in
its own container/remote env (#204). **A `uv` resolve conflict is the signal to
push an operator to a container** — not to spin up a per-pack/conda venv. A true
per-pack env is explicitly out of scope for now (revisit with #204 if the
in-process-but-conflicting case becomes real).

**3. Discovery is the source of truth for EXISTENCE; the DB record tracks
lifecycle.** Live entry-point discovery stays authoritative for *what is
importable*. The DB **install-record** tracks actor · source · version · trust ·
content-hash · status, and is **reconciled against discovery** so it never
silently diverges. (Consistent with how runs/triggers/policies are stored; the
record store is a registry-family store under #427 / `OBS_STORAGE`.)

## Install lifecycle (state machine, recorded in the install-record store)

`requested → authorize → resolve+lock → install → discover+validate → installed | failed`

1. **Source** — a catalog entry, or a manual ref (PyPI / wheel / VCS).
2. **Authorize** (RCE gate) — require auth + an install capability + a **source
   allowlist**; signature / trust-tier for community packs (#205).
3. **Resolve + lock** — `uv` resolves deps against the engine env; **detect
   conflicts** → flag for a container target (#204); extend `cairn.lock`.
4. **Install** — `uv pip install` into the engine env, or build/pull a container
   for the heavy/conflicting path.
5. **Discover + validate** — restart → re-run discovery, compile the pack's
   templates (schema · subgraph refs · capabilities) → verdict + content_hash;
   **roll back on failure**.
6. **Record** — write the install-record (actor/source/version/trust/hash/status),
   reconciled with discovery.
7. **Surface** — the console install view shows real status; "Browse registry"
   reads `catalog.json` (replaces today's stub).

## Consequences

- Server-side install becomes an **audited, reversible, authorized** operation
  rather than an out-of-band `pip install`.
- The install-record is the deployment's provenance ledger for packs; discovery
  remains the runtime truth, so a corrupted/stale record can't make an
  un-importable pack look installed.
- Restart-on-install is a visible UX cost (brief control-plane blip) — acceptable
  for v1; hot-reload removes it later.

## Alternatives considered

- **Hot-reload entry points from the start** — rejected for v1 (risk vs reward on
  an RCE-class path); tracked as a follow-up.
- **Per-pack / conda venv** — rejected now; container-or-shared is the isolation
  model, with a `uv` conflict as the containerize signal.
- **DB record authoritative for existence** — rejected; the DB could then disagree
  with what's actually importable. Discovery stays truth; DB tracks lifecycle.
