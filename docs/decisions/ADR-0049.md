# ADR-0049 — Workflow definition source of truth: a content-addressed DB record, populated by *both* code packs and console authoring

Status: Proposed (2026-06-29)
Relates to: ADR-0047 (run provenance — content-addressed schema store + `template_hash` + versioned installed-workflow records), ADR-0045 (distribution v1 — shared env + container-for-heavy; *deferred* OCI), ADR-0026 (locked architecture — declarative composition + the `invoke_operator` chokepoint), ADR-0020 (pack contract), #109 (the `UIContract`). Tracked work: #220/#221. **Supersedes** the "discovery is the source-of-truth, the DB enriches" stance taken in ADR-0048 rev 1 (§2). **ADR-0048 (workspaces) sits on top of this** — it scopes the records defined here.

## Context

cairn is **open-core + a closed managed-infra platform, and the SaaS ships together with the open source** — not a someday add-on. That makes two authoring modes both first-class, day one:

- **Code-authored** packs — operators (Python) + templates (YAML/markdown), discovered from the engine env. The OSS / self-hosted / power-user path. (Like Prefect, Temporal, Dagster, Airflow.)
- **Console / DB-authored** workflows — composed and edited in the console, stored as data. The managed-SaaS / no-code path. (Like n8n, Langflow.)

ADR-0048 rev 1 treated **discovery** (entry-point packs + template files) as the source-of-truth for *existence*. That holds for a single-node, code-only engine, but it cannot express a console-authored workflow, and it diverges across a fleet (discovery is per-process). We need one model that is genuinely **both DB- and code-backed**.

The field already settled this, and it settles it by **splitting the layer**: every platform stores the workflow *graph/definition* somewhere central while the executable *node/operator code* always lives on the worker. n8n & Langflow keep the graph in the DB but node/component code is npm/Python on the worker. **Windmill — cairn's closest precedent (open-core + managed cloud, "both")** — makes Postgres the system of record for definitions, content-addresses each deploy by an immutable hash, and git-syncs them as code. Prefect/Dagster keep code in the user's repo/image and store only metadata + a reference.

## Decision

### 1. Split by layer — this is the reconciliation of "both DB and code"
"Both" cannot apply to operator code; it applies to the definition layer.

- **Operator / capability layer → always code-backed.** Operator implementations are Python; they live in the worker image (OCI) or the installed pack, content-addressed by pack version. They are **never** stored in the DB. (Carries ADR-0045/ADR-0042. In managed SaaS the operator set is a *vetted registry catalog* baked into managed worker images — arbitrary tenant code never runs in a shared fleet; cf. n8n's verified-vs-unverified community-node split.)
- **Workflow / template + input-schema + config layer → both.** Code-authored (packs) **or** console-authored (DB), unified as a single **content-addressed definition that is the DB system of record**.

### 2. The content-addressed definition is the bridge
Extend ADR-0047's content-addressing so the *definition* — the template AST (`template_hash`) **and** the I/O JSON-Schema (`schema_hash`) — is stored content-addressed in the DB. **Both authoring modes produce the same artifact:**

- **code-authored:** pack files → compile → content-addressed definition → upsert installed-workflow record.
- **console-authored:** author/edit in the console → compile → *the same* content-addressed definition → upsert installed-workflow record.

What runs is always the content-addressed definition resolved from the installed-workflow record — origin is just provenance. A definition change (new `template_hash` / `schema_hash`) supersedes the prior active record (ADR-0047), never deletes it, so "run this exact version again" resolves by hash and version drift is detectable (the Dagster-style staleness signal: a workflow is stale when its current definition hash differs from the last run's).

### 3. The DB is the system of record; discovery *syncs into* it (not a parallel read path)
On startup/discovery, code-backed packs are **registered into the DB** (upsert installed-workflow records + content-addressed definitions). Discovery is a *populate* mechanism, like Windmill's `wmill sync` (git↔Postgres) — it is **not** a second source the UI reads.

- **Single-node OSS:** discovery populates the DB at boot; DB and discovery agree; everything reads the DB.
- **Multi-instance / SaaS:** the shared DB is **authoritative** for the enabled/runnable set (desired state); per-node discovery is the *actual* capability pool, reconciled against the DB (a readiness/drift check — "node B is missing operator-qdrant"). Desired-vs-actual, k8s-shaped. (This is the reconcile carried from ADR-0048 rev 1 §2, but now DB-first instead of discovery-first.)

### 4. The console and HTTP API read the DB
The installed/runnable list, the Run form, and run provenance all come from the **DB record** (= content-addressed definition + schema + config). The Run form is still generated from the input schema via the `UIContract` (#109) — but that schema now lives in the DB record, populated either from a code pack's JSON-Schema or from console authoring; either way it is the renderer's input.

This dissolves the "dev/editable packs vanish if the UI is DB-only" risk: discovery registers them into the DB, so a DB-uniform read shows them. Builtins/editable packs appear as records *without* a registry-install origin (provenance flag), not as absent.

## Consequences
- "Installed workflows" shifts from **populate-on-run** (ADR-0047 v1, where the record was written lazily when a run happened) toward **populate-eagerly at install/discovery**, in the DB. The console reads the DB uniformly across OSS and SaaS.
- Operator code stays code-backed/worker-image always; the OSS-vs-SaaS install model splits accordingly (OSS: allowlisted `uv pip install` on your own worker; SaaS: vetted catalog baked into managed images).
- A drift/readiness check (desired DB set vs actual per-node discovery) is needed at scale; single-node it is a no-op (they agree).
- **Supersedes ADR-0048 rev 1 §2.** The source of truth is the content-addressed DB record; discovery feeds it.
- **Security (ADR-0033):** secret-typed inputs in a definition's config persist as *references*, never raw; redacted in the audit.

## Out of scope / deferred
- The console no-code authoring UX (this ADR establishes that DB-authored definitions are first-class; the builder is separate work).
- The OCI image-build substrate that materializes the operator layer for a fleet (ADR-0045's deferred OCI).
- The reconcile-loop implementation (desired vs actual per node).
- The **workspace** scope key that partitions all of these records → ADR-0048.
