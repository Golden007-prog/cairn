# Outbound OAuth via a replaceable broker seam

## Context

`cairn connect` (#68) binds cairn to external infra. Most of the catalog
(model APIs, compute targets, MCP) authenticates with a static key or an
ambient credential chain — handled by the reference model (`secrets` are
SecretStore refs, never values). But a class of providers cairn wants to reach
for incident/RCA and dataset work — GitHub, Slack, Jira, Notion, Google — use
**OAuth 2.0 authorization-code + refresh**. cairn has no machinery for the
auth-code dance, durable token storage, or refresh.

Two roles of OAuth must not be conflated:

- **OAuth *provider* / IdP** (Hydra, Authentik, Zitadel, Dex) — authenticates
  users *into* an app, or issues tokens for *your* APIs. **Inbound.** That is
  the future "SSO into cairn-server" problem, not this one.
- **OAuth *client* / connector** — gets *your app* a token to call *their* API
  on a user's behalf. **Outbound.** This is `cairn connect`.

For the outbound role the candidates are Nango, Composio, and Authlib (DIY).
Langflow itself was surveyed: it has no native multi-provider OAuth engine — it
stores credentials as Fernet-encrypted Variables, has bespoke OAuth only for MCP
+ inbound user SSO, and delegates multi-provider tool auth to Composio
components.

## Decision

Outbound OAuth goes through a **replaceable broker seam**. cairn depends on an
`OAuthBroker` Protocol, never on a vendor SDK.

- `cairn/core/oauth`: `OAuthBroker` Protocol (`start_authorization` /
  `get_access_token` / `revoke`) + a registry (`get_oauth_broker`, default
  `OBS_OAUTH_BROKER=nango`).
- A new connection `kind="oauth"`. `resolve_connection` delegates to the broker
  for a **fresh** access token (the broker owns refresh) and returns it as
  `ACCESS_TOKEN`, so downstream operators consume it identically to an
  `api_key` connection — the broker is invisible below `resolve_connection`.
- `cairn connect add <provider> --via oauth` persists the connection, starts the
  flow, and prints the redirect URL; `cairn connect authorize <name>`
  re-initiates.

**Impl #1 is Nango, run as a sidecar** (self-hosted; Elastic License 2.0). It is
the *default*, not a hard dependency.

### Why Nango, not Composio

Verified against the cached SDKs:

- **Composio executes the tool on its servers.** `tools.execute(slug, args)`
  ships args to `backend.composio.dev`, which holds the OAuth token and makes
  the real third-party call. Data path: `cairn → Composio cloud → target`. The
  open SDK (Apache-2.0) is a thin client; the token vault + execution backend is
  closed and cloud-only.
- **Nango is auth-only.** It hands *cairn's* process a fresh token; **cairn makes
  the call**. Data path: `cairn → target`. Nango never sees the request/response.
  The vault server is in-repo and self-hostable.

The deciding factor is **token custody + execution locus**, not the license
badge. With Nango the call executes in cairn's process, so it still passes the
`invoke_operator` chokepoint (cost / policy / redaction / audit / HITL) over real
inputs/outputs — the governance property Composio's server-side execution gives
up. Composio may return later as a clearly-labeled opt-in convenience pack for
users who accept its cloud; it is not the default.

## Replaceability (the load-bearing requirement)

1. No cairn module imports a vendor type — only the `OAuthBroker` Protocol and
   `Connection.config["broker"]`.
2. Swapping the broker = a new `OAuthBroker` impl + `register_broker(...)` +
   flipping `config["broker"]` (per-connection) or `OBS_OAUTH_BROKER` (global
   default). **Zero call-site changes.** A test proves the env selects the broker
   and an explicit name overrides it.
3. Token custody is a property of *which broker* you pick, not of cairn's code —
   Nango keeps tokens in its own Postgres (on your infra); a future self-built
   broker could keep them in cairn's own store.

## Consequences

- New deployment dependency **only when OAuth connections are used**: a Nango
  sidecar (server + Postgres + Redis). Wired via `OBS_NANGO_HOST` +
  `NANGO_SECRET_KEY` (a SecretStore ref). See `docs/connections.md`.
- The reference model is unchanged for non-OAuth connections.
- Live end-to-end against a real Nango sidecar is verified separately (it cannot
  be claimed from hermetic tests) — per the project's "end-to-end is the only
  trustworthy verification" rule.

## Alternatives considered

- **Composio** — rejected as default (server-side execution + closed cloud
  vault); see above. Possible future opt-in pack.
- **Authlib (DIY)** — build the flows in-process; rejected for now (we would own
  the per-provider catalog + refresh + a token vault). It remains the natural
  basis for a future *self-hosted* `OAuthBroker` impl that keeps tokens in
  cairn's own store — which the seam already allows.
- **Hydra / Authentik / Zitadel / Dex** — wrong role (inbound IdP/SSO), tracked
  separately for cairn-server login.
