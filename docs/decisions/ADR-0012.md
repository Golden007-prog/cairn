### 24.12 Decision: improvement loop — suggested changes, not autonomous self-modification

**The question.** Should the platform learn over time? Should templates, policies, or capability bindings rewrite themselves based on observed outcomes? Should we ship DSPy-style prompt optimizers or auto-fine-tuning?

**The principle.** The platform stays **declarative**, **replayable**, **auditable**.
"Improvement" is **suggested** via a human-reviewed queue, never applied
autonomously. Memory and context evolve automatically; templates,
policies, and bindings do not.

This is consistent with every other "who decides" boundary in the engine
(HITL approval on actions, PolicyEngine review on risky operations,
content-addressed template versioning in §24.11). Extending the same
principle to template-level improvement is the right move for this
platform.

#### 24.12.1 Taxonomy — six distinct forms of "self-improvement"

These are NOT equivalent. They sit at different points on the
autonomy-vs-auditability axis.

| Form | What changes | Audit impact | Autonomy |
|---|---|---|---|
| **1. Memory accumulation** | Memory rows grow over time | Each run records which memory rows it retrieved | Low — context only, template stable |
| **2. Self-critique within a run** | Nothing persistent — refinement inside one run | Refinement loop captured in trace | None across runs |
| **3. Few-shot library accumulation** | Memory namespace of past good outputs | Each run records which examples it used | Low — context only, template stable |
| **4. Suggested improvements (system → human)** | Nothing without human accept | Full PR-style review trail | None — suggests, doesn't apply |
| **5. Auto-tuned prompts (DSPy-style)** | Template body literally rewritten | Templates drift; "what did this run use?" becomes unanswerable | High — engine modifies its own artifacts |
| **6. Auto-fine-tuned models** | New model deployed from accumulated runs | Model identity changes underneath; eval comparisons unstable | High — engine modifies its own model bindings |

#### 24.12.2 Current status — what's shipped

**Form 1 — memory accumulation: ✓ shipped.**
`recall_incident_memory` capability + Qdrant-backed memory store +
`memories` table planned in §24.4. Past incidents inform new
investigations through retrieval. The TEMPLATE doesn't change; the
CONTEXT does. Every run records exactly which memory rows
influenced the output (citation chain in evidence). This is the most
important form of learning because it doesn't violate any platform
principle.

**Form 2 — self-critique within a run: ✓ shipped** (Phase 4 task #71).
LLM critiques its own draft RCA, refines, bounded by
`max_iterations`. Loop captured in the trace. No cross-run effect.

Both are real, in production, and consistent with the platform's
principles.

#### 24.12.3 Decision A: build Form 3 — few-shot library

Accumulate good runs as labeled examples. Template references a memory
namespace (`memory.examples_for: "rca_outcomes"`); at runtime, top-K
relevant examples get injected as few-shot prompts. Context changes;
template stays stable.

Concrete shape:

```yaml
# In a template's frontmatter:
context:
  few_shot:
    namespace: "rca_outcomes"
    k: 3
    rank_by: "similarity_to_trigger"
```

```sql
-- Extension of §24.4 memories table — no new table, just a kind:
-- memories.kind = "few_shot_example"
-- memories.payload = {"input": {...}, "output": {...}, "score": 0.92}
```

Each run records which example IDs were injected → audit intact.
Replay shows the rendered prompt with examples → reproducibility intact.

**Effort: ~2 d.** Just an extension of the existing memory recall
pattern.

#### 24.12.4 Decision B: build Form 4 — suggested-improvement layer

The killer form. Invert the §24.11.4 regression eval direction:

| §24.11.4 use | This use |
|---|---|
| "I changed prompt A → A'. Did anything break?" | "Monitor prod runs. Find pattern. Suggest: if you change template X line 5 from Y to Z, eval agreement goes 82% → 91%. Cost stays same. Open PR?" |

The system surfaces candidates; the human accepts or rejects via PR /
chat / a `cairn suggest review` command. Audit trail intact.
Platform principles intact.

Concrete categories of suggestion:

| Category | Example suggestion |
|---|---|
| **Prompt-quality** | "Switching this template to gpt-4o-mini saves $0.04/run with no agreement drop on last 500 runs. Open PR?" |
| **Skill-binding** | "Service `payment-api` triggers two skills; the second always returns no findings on this service. Want to add an exclusion?" |
| **Policy-tightening** | "Policy `production-rollback` approved 47/50 requests last 30 days under risk=low. Want to auto-approve at risk=low?" |
| **Pattern extraction** | "Memory rows about `db-pool-exhaustion` outnumber every other category 10:1. Want to extract a dedicated playbook template?" |
| **Capability-rerouting** | "For service `checkout-api`, mock backend has failed 12 times this week; clickstack is healthy. Want to pin this service to clickstack?" |

**Where suggestions come from:**

- Production runs feed a continuous-eval pipeline (subscribes to
  `engine.run.completed` event via §24.10 Bus)
- Aggregates by template / skill / pack / service / time window
- A rule-based suggestion engine (low-magic, explainable) surfaces
  candidates that meet thresholds
- Optional LLM-based "summarize this pattern" step turns aggregates
  into human-readable PR descriptions
- Output: a `suggestions` table with status (pending / accepted / rejected / expired)

```sql
CREATE TABLE suggestions (
  id              TEXT PRIMARY KEY,
  pack            TEXT NOT NULL,
  category        TEXT NOT NULL,           -- prompt_quality | skill_binding | …
  target          TEXT NOT NULL,           -- which template/skill/policy
  description     TEXT NOT NULL,           -- human-readable
  proposed_diff   JSONB NOT NULL,          -- the actual change
  evidence        JSONB NOT NULL,          -- runs / metrics supporting it
  confidence      NUMERIC,
  status          TEXT NOT NULL,           -- pending | accepted | rejected | expired
  surfaced_at     TIMESTAMPTZ NOT NULL,
  decided_at      TIMESTAMPTZ,
  decided_by      TEXT
);
```

CLI surface:

```bash
$ cairn suggest list                          # pending suggestions
$ cairn suggest show <id>                     # details + evidence
$ cairn suggest accept <id> --as-pr           # opens GitHub PR with diff
$ cairn suggest reject <id> --reason "..."
```

**Effort: ~3-5 d** (after §24.11.4 regression eval lands as the
machinery for the per-run comparison).

#### 24.12.5 Decision C: do NOT build Form 5 (auto-tuned prompts) into the engine

DSPy-style optimization rewrites the template body to maximize a
metric. Breaks every principle we've committed to:

- **Replay**: unstable. The template that ran yesterday isn't today's.
- **Eval comparison (§24.11.4)**: impossible. You can't `--compare-against` a moving target.
- **Audit trail for prod incidents**: gone. "Who changed this prompt?" → "An optimizer."
- **Operator trust**: SREs don't want a system that silently rewrites itself.

**For incident response, this is the wrong tradeoff.** Verification of
RCA quality is subjective and expensive; the autonomy-for-quality
trade is bad.

**Where DSPy-style optimization IS legitimate:** open-ended task packs
where verification is cheap and unambiguous (e.g., "did the generated
SQL query return the right rows"). For those, build a
`prompt-optimization-pack` that **operates on templates as artifacts**:
input = template + dataset; output = a candidate template version
written to disk and tagged. Human reviews and merges. Pack-level, not
engine-level. **Not on the current roadmap.**

#### 24.12.6 Decision D: do NOT build Form 6 (auto-fine-tuning) into the engine

Same shape as Form 5 — autonomy-for-quality trade is bad for
incident-response stakes. Auto-fine-tuning is what the ModelOps
**fine-tuning-execution-pack** (separate doc, future work) does: as a
*workflow*, not an engine feature. The pack invokes training, deploys
the new model as a tagged option, eval pack validates it, human
approves binding to production. **Workflow, not engine background
process.**

#### 24.12.7 What this preserves

After Decisions A + B land, the engine has:

- **Declarative artifacts**: templates, skills, policies stay
  human-edited text.
- **Replayability**: every run is reproducible against its
  content-addressed template hash (§24.11.3).
- **Audit trail**: changes go through suggestion → human review → PR.
- **Real improvement over time**: memory + few-shot library + suggested
  changes mean the system *does* get better; just not autonomously.
- **Clear "who decides" boundary**: same as HITL on actions, same as
  PolicyEngine on risky operations — extended consistently to artifact
  evolution.

#### 24.12.8 What's deliberately out of scope (and why)

| Out of scope | Why |
|---|---|
| Auto-tuned prompts in the engine | Breaks replay + audit + trust (§24.12.5) |
| Auto-fine-tuned model deployment in the engine | Same reasons (§24.12.6) |
| `prompt-optimization-pack` | Build as a pack if the open-ended-task market demands; not core |
| RLHF / RLAIF loops | Same as fine-tuning — workflow, not engine |
| Per-tenant prompt personalization | Needs multi-tenancy first (Steal-1) |
| Auto-modification of `provides`/`requires` contracts | Composition is operator policy, not learned behavior |

#### 24.12.9 Effort

| Piece | Effort |
|---|---|
| Form 3 — few-shot library (template `context.few_shot:` + memory `kind = "few_shot_example"` + per-run example tracking) | ~2 d |
| Form 4 — suggestion engine (continuous eval pipeline + aggregation rules + `suggestions` table) | ~3 d |
| Form 4 — CLI: `cairn suggest list / show / accept / reject` | ~1 d |
| Form 4 — GitHub PR adapter (open PR with proposed diff + evidence) | ~1 d |
| Tests + docs | ~½ d |
| **Combined** | **~7-8 d** |

Depends on: §24.11.4 regression eval (provides the per-run comparison
machinery), §24.10 Bus (subscribers to `engine.run.completed` feed the
suggestion pipeline).

#### 24.12.10 Phased rollout (revises §24.6)

| Sub-phase | What | When |
|---|---|---|
| **P4.b** | Form 3 — few-shot library (extends §24.4 memory store) | Bundled with P4 (storage Phase 1 lands the memory store first) |
| **P5.c** | Form 4 — suggestion engine + `suggestions` table + CLI | Bundled with P5 (Postgres + Bus Tier 2 land first; both are dependencies) |
| **P5.d** | Form 4 — GitHub PR adapter (optional) | Same as P5.c |
| **Future** | DSPy-style optimization pack (if and when) | Separate pack, not core |
| **Future** | Auto-fine-tuning workflow | Lives in ModelOps fine-tuning-execution-pack |

P4 effort grows by ~2 d (Form 3 library). P5 grows by ~5 d (Form 4
suggestion engine). Total roadmap: **~42 d**.
