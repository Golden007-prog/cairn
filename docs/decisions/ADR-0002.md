> **Superseded by ADR-0024:** Restate dropped (BSL). Temporal (MIT) is the durable engine.

### 24.2 Decision: durable execution — Restate AND Temporal, by use case

> **Revision note (2026-06).** An earlier draft of this section argued for
> consolidating onto Temporal and retiring Restate. That conclusion was
> wrong: Restate and Temporal have genuinely different operational
> footprints, and forcing one tool across both axes either bloats simple
> deployments (Temporal cluster for a few HITL approvals) or starves
> serious infra automation (Restate for a 3-day VPC + RDS migration).
> The decision below replaces that draft.

**Status before:** two durability systems at different layers, with one
fully wired and the other scaffolded.

| Layer | Implementation | Wired? |
|---|---|---|
| Graph runtime (template execution) | `cairn/core/runtime/temporal/` — full Temporal integration using `temporalio.contrib.langgraph` (Steps 95–96) | Scaffolded; default path is still `InProcessRuntime` |
| Action saga | `cairn/core/actions/restate_handler.py` + `restate_service.py` (Steps 35–38, 88) | Yes — `SlackApprover` HITL relies on Restate's durable promise |

**Decision: keep both. Use each for what it's actually good at. Add a
Temporal action handler alongside the existing Restate one. Do NOT
delete Restate.**

#### 24.2.1 Two durability profiles, two backends

The action sagas a real deployment runs fall into two genuinely
different shapes — and the runtime that's right for one is wrong for the
other:

| Shape | Example | What it needs | Right backend |
|---|---|---|---|
| **HITL + short work** | Slack-approve a deploy. dry_run + approve + execute take seconds; the wait for a human can be hours. | Durable pause/resume across restarts. Per-step retry is rare. | **Restate** — durable promise, single-binary self-host, RocksDB, low ops cost. |
| **Long-running infra automation** | Provision VPC → wait → create RDS → wait → migrate data → verify → flip DNS. 20–100 steps over hours to days. | Durable timers (`workflow.sleep("4h")`), per-step retry budgets, compensation chains, cross-machine resumption. | **Temporal** — heavyweight cluster, but the native model for this. |

Trying to force HITL onto Temporal is overkill (you need a Cassandra/
Postgres-backed cluster for a single Slack approval). Trying to force
VPC-and-RDS-migration onto Restate hits walls on durable timers, signal
ergonomics for long flows, and tooling for inspecting multi-day
workflows. Both criticisms are real; both are solved by routing each
workflow to the runtime that matches its shape.

#### 24.2.2 Two-runtime architecture

```
                    Restate                    Temporal
                    ───────                    ────────
What runs:          ActionSaga (HITL,          ActionSagaWorkflow (long-
                    short work, durable pause) running, durable timers,
                                               compensation chains)

HITL primitive:     Durable promise            workflow.signal("approve")

Per-step retry:     ctx.run(max_attempts=N)    Activity RetryPolicy

Durable timers:     ctx.sleep (short)          workflow.sleep (any duration,
                                               survives restarts)

Operational cost:   Single-binary docker       Cluster (frontend +
                    compose up                 history + matching + DB)

When you use it:    80% of deploys — HITL,     20% — VPC/RDS migrations,
                    short durable async work   region failovers, terraform
                                               apply orchestration
```

The LangGraph **template** (the agent) keeps running in-process or on
the Temporal graph runtime; it doesn't change. When the agent produces
an `ActionCandidate`, the configured `ActionHandler` decides which
durable backend hosts that action's saga:

```python
# Pattern 2 (Restate as async tool manager) — what we already have
# and what we keep.
agent (LangGraph template, runs in-process or on Temporal runtime)
  └── produces ActionCandidate
      └── ActionHandler.execute(candidate, decision, context)
            ├── in_process → hand-coded saga shell (dev/test)
            ├── restate    → Restate ActionSaga workflow (HITL + short work)
            └── temporal   → Temporal ActionSagaWorkflow (long-running)
```

Three handler kinds, three durability profiles, one protocol the Runner
talks to.

#### 24.2.3 Why we rejected the alternatives

| Alternative | Why we passed |
|---|---|
| **Wrap LangGraph in a Restate service handler** (Restate journals the whole `graph.ainvoke`) | Wrong granularity. Crash mid-graph replays every prior LLM call. `InMemorySaver` inside doesn't survive process death, and the workaround (one `ctx.run` per node) defeats the simplicity argument. |
| **Custom Restate-backed LangGraph checkpointer** | Speculative. PostgresSaver is battle-tested; building a Restate checkpointer is maintenance burden against an evolving upstream protocol. Restate Virtual Object storage isn't designed as a general checkpoint store (value-size + history limits). Re-evaluate only if checkpoint cost becomes a real problem. |
| **LangGraph interrupts + Postgres checkpointer as a third action-handler tier** | Functionally equivalent to Temporal signals for HITL. Adding it would double the durability infrastructure for no functional gain — the exact sprawl this section is meant to avoid. If Temporal is in the stack, `workflow.signal` covers HITL; if Restate is in the stack, the durable promise covers HITL. LangGraph stays where it lives: as the graph runtime for template execution. |

#### 24.2.4 Build plan (~3 d total — additive, no deletion)

The existing Restate handler stays as-is. Build the Temporal handler
alongside. The original §24.2 draft's deletion steps (T4–T6 in the
session task list) are no longer in scope.

| Step | Effort |
|---|---|
| Build pure-Python action-saga core (testable via fake context, same pattern as `test_restate_saga.py`) | ~½ d |
| Build `ActionSagaWorkflow` (`@workflow.defn`) wrapping the core; HITL via `@workflow.signal("approve")` + `workflow.wait_condition`; per-step activities for dry_run/execute/verify/compensate with Temporal `RetryPolicy` | ~1 d |
| Build `TemporalActionHandler` (client side) mirroring `RestateActionHandler`'s shape: starts workflow, relays approval as signal, awaits result | ~½ d |
| Factory: `HandlerKind` gains `"temporal"`; settings `OBS_ACTION_HANDLER ∈ {in_process, restate, temporal}`; doctor `check_temporal_action()` probe | ~½ d |
| Offline tests via fake-Temporal-context, mirroring `test_restate_saga.py`'s 337-LoC coverage of crash-resume + step memoization | ~½ d |

What's intentionally NOT in scope:
- `SlackApprover` migration — stays Restate-relay for the `restate`
  handler. The `temporal` handler gets a parallel approval-relay code
  path that sends `client.get_workflow_handle(id).signal(approve, …)`
  instead of POSTing to Restate. Both paths coexist.
- Removing `restate_handler.py`, `restate_service.py`,
  `scripts/restate_serve.py`, the Restate doctor check, or the Restate
  setting. **Restate is not deleted.**
- Changing `OBS_RUNTIME` (graph runtime selection). That stays
  independent — pick `inprocess` or `temporal` for graph execution,
  pick `in_process`/`restate`/`temporal` for action sagas. Six valid
  combinations.

#### 24.2.5 Future: per-action routing (deferred)

The deployment-wide `OBS_ACTION_HANDLER` knob is the right MVP — one
deployment, one backend. But the natural follow-on is letting an
*individual* `ActionCandidate` declare its durability profile:

```python
class ActionCandidate(BaseModel):
    ...
    durability: Optional[Literal["fast", "durable", "long_running"]] = None
```

The dispatcher consults the field if set, falls back to the deployment
default otherwise. A single deployment can then route
`comms.post_message` actions to Restate (HITL pause) and
`aws.provision_vpc` actions to Temporal (multi-hour saga) — without
splitting the pack into two services.

Defer until at least one pack actually ships mixed-shape actions in
one deployment. Roughly ~1 d of dispatcher work once that pressure
exists.

#### 24.2.6 What good looks like after this lands

- Two handler-kinds wired in production (`restate` and `temporal`),
  one for dev/test (`in_process`).
- Per-deployment selection via `OBS_ACTION_HANDLER`.
- Restate keeps doing HITL approvals and short-durable async work —
  what it's already good at, with no operational change.
- Temporal handles the long-running infra-automation use cases that
  Restate is genuinely wrong for — VPC provisioning, RDS migrations,
  region failover, terraform apply orchestration.
- Operators pick the runtime that matches their workload; nobody is
  forced into Temporal cluster ops just to ship a Slack approval flow,
  and nobody is forced into Restate's single-region story just to
  avoid Temporal.
