# ADR-0053 — Policy scoping: the environment is the wiring hub

Status: Accepted (2026-07-01)
Relates to: the policy engine (`cairn/core/policy/engine.py`), the three-layer
policy store (pack YAML ① / user overlay ② / console DB store ③), the profile
layer (`cairn/core/pack/profile.py`, ADR: profile is the pack↔env seam), and the
console Environments surface (#302/#303 backends form). Implements #317.

## Context

Policies today merge from three sources into one flat list at
`PolicyEngine` construction, deduped last-wins-by-name:

1. **① pack YAML** — `<pack>/policies/*.yaml`, immutable distributable defaults.
2. **② user overlay** — `~/.cairn/policies/*.yaml`, hand/git authored.
3. **③ console DB store** — `SqlitePolicyStore`, authored in the console (#316).

Every **enabled** store policy applies **globally** to every run in the process
(`_store_policies()` loads them all). Environment scoping exists only *inside*
each policy, via `applies_to.environments`, which the matcher compares against
`request.environment` — a fixed deployment tier `dev | staging | production`.

Two problems:

- **No per-deployment wiring.** An operator who wants "these three store policies
  enforced in *this* environment, none in the test environment" has to hand-edit
  `applies_to.environments` on each policy. There is no single place — an
  environment — that owns "which policies run here."
- **Two meanings of "environment."** The enforcement engine keys on the
  `dev|staging|production` tier. The console "Environment" is a **profile TOML**
  (`cairn/profiles/*.toml`, listed by `list_profiles()`) — the pack↔env seam that
  already carries `bindings`/`capabilities`/`backends` (#303 edits it). The
  profile is loaded at runtime via `OBS_PROFILE` → `load_profile_from_env()`, but
  nothing connected it to policy evaluation.

The user's requirement (verbatim intent): *"make it env based. env should allow to
add/remove multiple policy as a deployment… a test env does not need policy all the
time however it will inherit policy if pack has one. later we can add an admin/
workspace config where policy can't be removed."*

## Decision

**The environment (profile) is the wiring hub for store policies.** It owns an
attach-list; pack and user-overlay policies are always inherited.

1. **Attach-list lives in the profile TOML**, not a new store:

   ```toml
   [profile]
   policies = ["gate-high-risk-prod", "require-hitl-external-write"]
   ```

   Added to the closed `[profile]` schema (`_PROFILE_TOP_KEYS`) and the `Profile`
   dataclass as `policies: list[str]` (store-policy **names**). Same file #303's
   backends form edits; same file the runtime already loads. `extends`: a child
   that declares `policies` **replaces** the parent's list (present-wins, matching
   the per-key override the other profile tables use); absent → inherit parent.

2. **Engine gating — inheritance vs attachment:**
   - **Pack ① + user-overlay ② policies always apply** (inherited; not detachable
     from the console). This is "a test env inherits pack policy if the pack has one."
   - **Store ③ policies are gated by the active profile's attach-list.**
   - `PolicyEngine(..., attached_store_policies: set[str] | None = None)`:
     - `None` (attach-list **absent** from the profile) → **all** enabled store
       policies apply. Preserves today's behavior; a profile that never opts in
       does not silently lose enforcement. This is the back-compat default.
     - a set (attach-list **present**, incl. **empty**) → a store policy applies
       **only if its name is in the set**. `policies = []` therefore means "inherit
       pack policies only, no store policies" — the test-env opt-out.
   - Implemented by tagging each loaded policy with its source (`pack` / `overlay`
     / `store`) and consulting the set only for `store`-sourced policies. Matching
     otherwise unchanged: `applies_to.*` (incl. the `dev|staging|production` tier
     and `capabilities`) still filters after the attachment gate.

3. **Runner wiring (closes the #11 gap, for policies).** The runner reads
   `load_profile_from_env().policies` and passes it as `attached_store_policies`
   into `PolicyEngine`. `None` when the profile omits the key. This is the single
   point where the console-authored environment reaches enforcement.

4. **API + console.** `GET/PUT /ui/api/profiles/{name}/policies` (tomlkit write,
   mirroring `_apply_backends`). The Environments view gets a multi-select of
   available store policies to attach/detach; pack/overlay policies are shown as
   **inherited (locked)**, not attachable/detachable.

## Consequences

- **Bypass is deliberate and scoped.** Running with a profile whose `policies = []`
  gives you a store-policy-free environment for testing — but pack policies still
  apply, so you cannot silently ship a pack's guardrails away. There is no
  per-run `--no-policy` flag; the escape hatch is an environment, which is audited
  config, not an ad-hoc override.
- **Not yet non-bypassable.** Any operator who can edit the profile TOML (or the
  console Environments view) can detach a store policy. The **workspace-level lock**
  ("policies that can't be removed") is explicitly **deferred** to a later admin/
  workspace config — noted here, not built.
- **Two environments stay distinct.** The `dev|staging|production` tier keeps its
  role inside `applies_to.environments`; the profile attach-list is an orthogonal,
  additional gate for store-sourced policies. We did **not** collapse them.
- **Back-compat.** Profiles without a `policies` key behave exactly as before
  (all store policies apply). The three existing shipped profiles need no change
  unless they want to opt into gating.
- **Delete-safety interplay (#319).** A store policy attached to an environment
  should warn on delete; tracked separately.
