# Secrets — a profile-bound `secrets.store` capability, scoped per operation

## Context

`OperationContext` declares a `SecretStore` (`protocol.py`: `get` /
`available_keys`) and operation bindings declare a `secrets: [...]` allow-list,
but neither was wired — `invoke_operator_inprocess` always built the context
with the default `NullSecretStore` and never read `binding.secrets`. An operator
that needs a token (e.g. a private Hugging Face repo pull) had no way to get one.

The question raised was where secrets should live: plaintext files, OpenBao,
Infisical, sops, Vaultwarden. The engine's answer is the same as for
`audit.sink` / `notify.sink` / `redact.text`: a **capability with swappable
providers**, not a hard-coded backend.

## Decision

1. **`secrets.store` is a profile-bound capability.** Core owns the
   `SecretStore` interface + a resolver/scoper (`core/operator/secrets.py`); it
   holds no backend. `get_secret_provider()` resolves the bound operator from the
   active profile's `[profile.bindings]` (`secrets.store`), cached, fail-open —
   mirroring `obs.audit.get_audit_sink`.

2. **Default provider = `operator-secrets-env`** (`secrets/env`, builtin,
   zero-dep) — reads `os.environ`. Dual-interface like `operator-audit-store`:
   `get`/`available_keys` (the SecretStore the runtime injects) + a `run` node
   path that is a **presence check only** (never returns a value — that would
   leak it into state / the trace).

3. **Per-operation scoping (§24.20.13).** `invoke_operator_inprocess` now builds
   `ctx.secrets = build_scoped_secrets(binding.secrets)`: a `ScopedSecretStore`
   that exposes ONLY the keys the binding declared, backed by the bound provider.
   An undeclared key raises `KeyError` before the backend is consulted (a typo
   can't leak an unrelated secret). Nothing declared → empty `NullSecretStore`;
   declared but no provider bound → reads raise (fail-loud).

```toml
[profile.bindings]
"secrets.store" = "secrets/env"
```
```yaml
# an operation that needs a token declares it; only this key is readable
secrets: [HF_TOKEN]
```

## Consequences

- The wiring is **inert by default**: existing operators declare no `secrets:`,
  so they keep getting `NullSecretStore` — no behavior change.
- Heavier backings are additive, no core change:
  - **sops + age** — single-binary, no server, GitOps (commit encrypted secrets,
    decrypt with an age key). The recommended lightweight step up.
  - **OpenBao** — single-binary secrets *server* (dynamic secrets, leases,
    audit) when you outgrow files.
  - Rejected for the default: **Infisical** (needs Postgres+Redis — not
    single-binary) and **Vaultwarden** (a password manager, not an app/service
    secrets store).
  Each ships as `operator-secrets-sops` / `-openbao` providing `secrets.store`.
- Plaintext `.env`/`.json` is local-dev only (gitignored), never committed.
- This unblocks the deferred private-Hugging-Face-repo pull (its operation
  declares `secrets: [HF_TOKEN]` and binds `secrets.store`).
