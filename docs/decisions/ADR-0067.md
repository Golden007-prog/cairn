# ADR-0067 — One governed operations layer; expose it over HTTP + MCP; CLI/ask/console/agents are clients

Status: Accepted (2026-07-08; implementation decisions locked 2026-07-09 — see Addendum)

Tracking issue: an internal issue (relates: #620 ask roadmap, #69 inbound MCP gateway, #109 UIContract, #572 observability reads).

## Context

Cairn's thesis is governance: **no interactive surface may take an action the
policy engine + audit boundary hasn't sanctioned** (call it the *no-bypass*
guarantee). Today the code does not structurally enforce that at a single
boundary — it relies on the shared core.

Current state (from the code):

- **CLI** — ~24 typer verbs. **20 call the CORE in-process** (`build_default_runner`,
  `build_storage`, `cairn.core.*`); only `remote` (+ parts of doctor/pack/pilot)
  go over **HTTP** (`remote` drives a running `cairn-server` over HTTP+SSE).
- **ask** — a 4-route LLM classifier (`workflow`/`capability`/`knowledge`/
  `out_of_scope`) + inline REPL; `cairn/ask/resolve.py` resolves and executes
  against the **CORE in-process** — not via the API.
- **cairn-server (HTTP API)** — a separate FastAPI server that drives the
  **console** and `cairn remote`.

So there are **two surfaces over one core**: (a) in-process for CLI + ask,
(b) HTTP for console + remote. Governance lives in the shared core (policy
engine, dispatcher), so it is not a *governance* bypass today — but it is a
**duplicated surface**: the interactive paths don't uniformly cross the API's
auth/audit boundary, the "allowed operation set" is implicit and lives in two
places, and there is **no outbound MCP surface** (the #69 gateway is *inbound* —
external tools *into* workflows).

We also want ask to be **real-LLM-driven** and, ideally, for cairn to be callable
by the wider agent ecosystem (Claude, Cursor, …) without inventing a second,
lower-governance path.

## Decision

**Introduce ONE governed operations service — the single policy + audit boundary —
and make every front-end (CLI, ask, console, external agents) a client of it,
exposed over BOTH HTTP and MCP as thin adapters.**

```
CLI · ask · console · external agents
   └──────┬──────┬──────┘
          ▼      ▼
   MCP server   HTTP API        ← thin protocol adapters (no logic)
          └──────┬──────┘
                 ▼
   governed operations service   ← the ONE policy + audit boundary
                 ▼
   core seams: policy · run store · dispatcher · compiler
```

1. **Governed operations service.** Extract the explicit set of allowed
   operations (below). Each operation resolves auth/workspace, checks policy,
   emits audit, then calls the core seams. This is the *only* place the
   no-bypass guarantee is enforced.
2. **HTTP API and MCP server are thin adapters** over that service — protocol
   translation only, no policy/run logic. The **MCP server exposes each
   operation as a typed tool** whose schema **reuses the UIContract JSON-Schemas
   (#109)**. This is the *inverse* of #69: cairn *as* an MCP server (outbound).
3. **CLI and ask become clients of the service** — not privileged direct-core
   callers. In-process invocation stays allowed as an optimization for the
   single-binary case, but **through the same governed operations interface**,
   so there is no path that skips the boundary.
4. **ask keeps its own real-LLM loop** (classify → plan → synthesize via
   `cairn.core.llm.client`); MCP is only its *tool-invocation layer*. ask calls
   structured, typed tools instead of parsing NL → CLI strings.
5. **Exposing cairn as a governed MCP server is a first-class capability**, not
   just an ask detail: any MCP client can then drive cairn through the same
   governed surface. ask is the first consumer / dogfood.

### The exposed operation set (= MCP tools = API endpoints = CLI verbs = ask routes)

1. **Discovery** — list templates / bundles / operators / packs; describe a
   template (input schema, graph, required capabilities).
2. **Dependency resolution** — doctor: installed vs required, missing
   capabilities, offered governed install.
3. **Planning** — assemble a deterministic plan; dry-run; **governed pre-flight**
   (estimated cost + which policies gate + which HITL approvals will fire).
4. **Execution** — run a template/bundle; resume a HITL gate; cancel; restart
   (remote-job aware).
5. **Observability (read)** — query runs (status/results/metrics); audit trail;
   lineage; eval verdicts + failure clusters; remote-job status. Grounded,
   cites `run_id`s.
6. **Knowledge (read)** — grounded, cited Q&A over bound corpora (#506).
7. **Registry** — install / uninstall packs; catalog + versions; resolved-operator
   pinning.
8. **Admin (governed, gated)** — environments (list/create/attach-policy);
   connectors (list/test/add); schedules/triggers (list/create). The
   mutation-heavy operations carry the strongest policy + HITL.
9. **Improvement** — surface governed suggestions (#478) as action-items;
   "explain this run/failure".

Reads are grounded; mutations are gated; the interactive surfaces get **no
operation the governed service does not expose** (= the no-bypass guarantee,
made structural).

### Transport selection (the fallback ladder)

A client (`cairn ask`, the CLI) does not care *how* it reaches the governed
operations service — only that it reaches the same one. It picks a transport by
what is available, in this order:

1. **MCP** — if a cairn MCP server is reachable (e.g. running locally, or a
   configured endpoint). Preferred for agent/tool ergonomics and typed tools.
2. **HTTP API** — if a `cairn-server` is reachable (local or remote) but no MCP.
   The standard client/server split (auth token, HTTP+SSE), same as `cairn
   remote` today.
3. **In-process** — **the standalone fallback**: no server, no MCP, single
   binary. The client calls the governed operations service directly in the same
   process (a torch-less/serverless laptop install must still work).

All three go through the **same governed operations interface**, so the
no-bypass guarantee is transport-independent — MCP/HTTP/in-process differ only in
*where the process boundary is*, never in *what is allowed or audited*. In-process
is not a privileged path: it is the service called without a network hop, with
the same policy + audit. This is what lets a standalone install (no MCP daemon,
no server) still be fully governed. Selection should be explicit + overridable
(flag / env), and the resolved transport surfaced to the user so it is never a
silent downgrade.

## Phased plan

- **Phase 1 — Extract the service seam.** Define the operations interface and
  route the HTTP API through it (mostly a refactor of the existing server). No
  behaviour change; establishes the single boundary.
- **Phase 2 — MCP server (thin adapter).** Expose the read-heavy, lowest-risk
  operations first (discovery, observability, knowledge) as typed MCP tools with
  UIContract schemas. Dogfood in ask (slice 1 of #620 = the observability route).
- **Phase 3 — Move CLI + ask onto the service.** Replace direct-core calls with
  the governed interface (in-process transport allowed). Add execution + admin
  tools with policy + HITL.
- **Phase 4 — Publish cairn-as-MCP-server** for external agents; add the
  compose-from-vetted authoring slice (#581) behind human review.

## Consequences

- **The no-bypass guarantee becomes structural** — one boundary, adapters on
  top. Easier to audit and reason about than "governance lives somewhere in the
  shared core."
- **Build once, reach the ecosystem** — the same governed surface powers ask,
  the console, the CLI, and any external MCP client. cairn becomes *the governed
  ModelOps tool an agent can safely call*.
- **UIContract is reused** as the tool/endpoint schema source (#109) — no third
  schema definition.
- **Cost:** a refactor (extract the operations service; move CLI/ask off
  direct-core) plus a new MCP adapter. Some added indirection; the in-process
  transport keeps single-binary latency acceptable.
- **Risk:** if the MCP server or the CLI re-implements policy/run logic instead
  of calling the one service, governance drifts — the ADR forbids that (adapters
  carry no logic).

## Alternatives considered

- **Keep two surfaces (status quo).** Rejected: implicit, duplicated
  "allowed-operation" set; the interactive paths don't cross a uniform audit
  boundary; no ecosystem surface.
- **Make everything go over HTTP (no in-process).** Rejected as a hard rule:
  needless latency/coupling for the single-binary local case. In-process is fine
  *through the governed interface*.
- **Build ask directly on the HTTP API only (no MCP).** Rejected: misses the
  ecosystem leverage (external agents) and the typed-tool ergonomics; MCP over
  the same service gets both for one build.
- **Expose the core directly as MCP (no service seam).** Rejected: that makes
  MCP a second enforcement path and re-introduces drift; the point is one
  boundary.

## Addendum (2026-07-09) — implementation decisions

The design discussion for #621 settled the *how*. Key realization: **most of the
target already exists**, so this is consolidation, not construction.

1. **The FastAPI app IS the governed operations layer — no new service class.**
   `cairn/core/triggers/server.py::build_app()` already exposes ~58 governed
   endpoints; policy + audit already run inside them (via the core/dispatcher
   they call). "Thin façade" therefore means *no parallel `OperationsService`
   re-implementing run/policy/audit logic* (that would be a second code path that
   drifts — the exact duplication #621 kills). Everyone becomes a **client of the
   app** instead of reaching into raw core.

2. **Ops MCP is auto-derived, not hand-written.** `FastMCP.from_fastapi(app)`
   (fastmcp 3.3.1, already a dep) generates one MCP tool per route from the
   OpenAPI schema. A deliberate `route_maps` **allow-list** selects which routes
   become agent tools (Discovery/Plan/Run/Resume/Query/Registry; mutations behind
   the strongest gates; exclude `/healthz`, `/token`, `/auth/*`, static). MCP
   tools inherit governance because each just calls the already-governed endpoint.

3. **Placement — beside the API, not in `services/mcp/`.** New file
   `cairn/core/triggers/mcp.py`; mounted onto the same app via
   `app.mount("/mcp", mcp.http_app())` → one server, one port, one auth
   middleware, two protocols. Rationale = coupling direction: this file is a
   *projection of the API* (couples up to `triggers`), whereas the existing
   `cairn/services/mcp/server.py` is a *pack-tools* MCP (couples down to
   `core.pack`). Different concerns → different homes. `services/mcp/server.py`
   stays untouched; a one-line pointer notes where the ops MCP lives.

4. **CLI/ask are `httpx` clients of the app.** Local install → `httpx` with
   `ASGITransport(app=cairn_app)` (in-memory, no socket, no running server,
   ~zero latency); remote (`OBS_ENDPOINT` set) → `httpx` over the network. Same
   endpoints, same policy, same audit either way — this is the in-process rung of
   the transport ladder, redefined as *"in-memory ASGI to the same app,"* not
   *"reach into raw core."* `cairn ask` migrates onto this (today it's the odd one
   calling core directly); it uses the **one** ask endpoint the console calls.

   **Concurrency (requirement): CLI ask + console ask must work at the same time,
   on the same state.** There is ONE ask endpoint; both surfaces (and external
   agents) are concurrent clients of it. So the transport default matters: when a
   server is running/configured (`OBS_ENDPOINT`, or a local server up), the CLI
   talks to **that server over the network** — sharing the same run store / audit /
   sessions with the console, so both operate on the same data simultaneously. The
   in-memory `ASGITransport` path is only the **standalone-CLI-with-no-server**
   fallback (single-binary, where no console is running anyway). Ask itself is
   stateless-per-request (or session-keyed in the store), so N concurrent clients
   are fine.

5. **CLI split — governed operations vs dev tooling.** *Operations* verbs
   (`ask`/`run`/`resume`/`cancel`/`remote`/observability) route through the app.
   *Dev/inspection* verbs (`init`/`lock`/`validate`/`ls`/`doctor`) **stay
   in-process** — fast, offline, and not governed operations, so no-bypass doesn't
   apply. (Also avoids spinning the app's scheduler/control-loop lifespan for a
   one-shot command.)

6. **Rich CLI is NOT compromised by going over HTTP.** Presentation is 100%
   client-side; the transport only changes where the bytes come from (JSON + SSE).
   Proof: cairn's rich surfaces **already run over HTTP+SSE** — `cli/tui/app.py`
   is an `httpx` Textual client, and `cairn remote` renders `rich.Table`/`Live`
   and drives interactive HITL over `GET /runs/{id}/stream` today.

7. **Retire the Textual TUI (#638).** With web console + `cairn remote` (Rich over
   HTTP+SSE) + `cairn ask`, the bespoke Textual app (`cli/tui/`, `cairn remote
   console`, the `[tui]`/`textual` deps) is a third overlapping surface with low
   marginal value → removed. `cairn remote` (HTTP+SSE) is the rich-terminal surface
   going forward. Re-scopes #56.

### `cairn ask` scope — RED LINE (2026-07-09)

Ask is a **read-only conversational surface that hands off to the human for any
action.** It never authors and never runs.

- **NEVER:** author/compose workflows (no #581 authoring loop — out entirely for
  now); run / resume / cancel / install / admin mutations. **A workflow is run
  only by a human.**
- **CAN (read-only + preview only):** inform over policy · knowledge packs · RAG
  answers · cost · runs · results · eval state · insights · suggestions (grounded,
  cited); **show the plan / dry-run** for a workflow (computes cost + gates + graph,
  executes nothing); **render the run UI** (the UIContract form with plan/dry-run/run
  buttons) — the human clicks run.

Enforcement is by **capability, not policy check**: ask's bound tool set contains
**no mutation tool** — `query_runs`/`get_run`/`get_results`/`get_cost`/`get_insights`/
`get_eval_state`/`get_suggestions`/`answer_knowledge`/`get_policy`/`plan_workflow`
(dry-run, read-only)/`render_run_ui` (emit UIContract). No `run_workflow` exists in
ask. Because the tool set is entirely within the safe envelope, ask's internal LLM
loop MAY be a ReAct agent bound to these read/preview tools — there is nothing
dangerous it can autonomously do. Execution stays a human action in the console /
`cairn run`. (Whether the *external-agent* MCP surface exposes gated mutations is a
separate decision from ask's binding.)

### Net shape
```
core/triggers/server.py  → build_app()                       = governed operations layer (exists, 58 routes)
core/triggers/mcp.py     → from_fastapi(app) + mount /mcp     = ops MCP (same server)        [NEW]
services/mcp/server.py   → pack capability tools MCP          (separate concern, untouched)
CLI (ops) / ask          → httpx client of the app (ASGITransport local / network remote)
CLI (dev verbs)          → in-process (init/lock/validate/ls/doctor)
console                  → fetch
```

### Sequencing (reads-first)
1. Migrate `ask/resolve.py` (+ in-process operation verbs) to httpx clients of the
   app; land the observability read route (#620 slice 1) through it.
2. `core/triggers/mcp.py` — `from_fastapi` + `route_maps` allow-list (reads first),
   mount at `/mcp`.
3. Extend the allow-list to mutations (strongest gates) once reads are proven.
4. Retire the TUI (#638) once `cairn remote` covers the interactive-watch need.
