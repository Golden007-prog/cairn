# ADR-0044 — Per-node run events (live canvas node states)

Status: Accepted (2026-06-27) — built
Relates to: ADR-0034 (operation-gate HITL / interrupt), #179 / #181 (web console — live run-state overlay), the dispatcher run-event stream (`RunStore.append_event` → `_EventHub` → SSE `/runs/{id}/stream`).

## Context
The web console's Workflows canvas (#179) overlays *run-level* lifecycle events
(`queued → running → awaiting_approval → resumed → done`) onto the graph: every
node sits idle until the run finishes, then all go green at once. The engine
emits only run-level events — the dispatcher wraps the whole graph execution in
one `await run_within_budget(compiled, …)` (one `ainvoke`), so there is no
per-node progress to show *during* the run. #181 flagged "per-node mid-run
states" as needing per-node engine events.

LangGraph already streams per-node updates: `compiled_graph.astream(…,
stream_mode="updates")` yields `{node_name: delta}` as each node completes (and
`{"__interrupt__": …}` at an approval gate). So the data exists — the gap is
emitting it onto the run-event stream the console already consumes.

## Decision

### 1. A new `node` run-event, emitted as each node completes
The dispatcher emits `node` events with `{"node": <name>, "state": "done"}` as
the graph runs. These flow through the existing `append_event → SSE` path
unchanged — the stream endpoint already forwards `event: {ev.type}` for any
type, and `node` is an **event**, not a run **status** (the `Status` literal is
untouched; the run status stays `running` while nodes complete).

We emit **done-per-node** (not start/running). LangGraph's `updates` mode fires
*after* a node finishes — that is the cheap, correct signal. The console derives
the **running frontier** (the blue "●" nodes) on the client from the done-set +
the graph edges it already has: a node is `running` when all its predecessors
are done but it isn't. This gives the live progression (gray → blue → green)
without the heavier `astream_events` machinery. A true per-node *start* event
(if ever needed) is a follow-up.

### 2. Opt-in streaming — byte-identical fast path when nobody listens
Per-node streaming is gated by a **contextvar sink** (`node_stream.py`):

- **No sink set** (CLI, durable runtimes, every existing test) → the in-process
  runtime calls `graph.ainvoke(…)` exactly as before. Zero behavior change.
- **Sink set** (the dispatcher sets it around a template run + its resume) → the
  runtime drives the graph via `astream(stream_mode=["updates","values"])`,
  emitting a `node` event per completed node and reconstructing the same return
  value `ainvoke` would produce — including merging the `__interrupt__` chunk so
  the HITL pause/resume path (ADR-0034) is unaffected.

The contextvar (not a threaded parameter) keeps the change surgical: only
`inprocess.py`'s invoke/resume sites change, not `CompiledTemplate.run` /
`run_within_budget` / every caller signature. It propagates across `await` and
through `asyncio.wait_for` (the wall-budget wrapper copies the context).

### 3. Scope: in-process runtime only
The in-process runtime is the console/dev path. Temporal/DBOS drive the graph
inside their own workflow bodies (separate `ainvoke` loops); per-node events
there are a follow-up keyed on those runtimes' streaming hooks. The sink is a
no-op for them (they never set it), so nothing regresses.

## Consequences
- Console canvas nodes light up progressively during a real run (proven e2e on
  `training/finetune`), and the frontier shows the live "running" node.
- The `node` events are persisted in the run-event log (replayable, like every
  other event) and published on the Bus topic `run.node`.
- Risk is contained to the new streamed path: a quirk in `astream`-vs-`ainvoke`
  reconstruction can only affect console-driven runs, never the CLI/durable
  paths (which keep `ainvoke`). Covered by a unit test that asserts the streamed
  path returns the same terminal state as `ainvoke` and emits one `node` event
  per node, plus an interrupt test that the `__interrupt__` still surfaces.
