# ADR-0060 — The evaluation engine: auto-eval on completion, workflow-scoped failure diagnosis, and gated suggestion routing

Status: Proposed (2026-07-05, for the failure-driven eval epic #480)

Relates to: ADR-0012 (governed self-improvement — the autonomy line: diagnosis
automated, actuation always human-gated), ADR-0057 (eval recipes — `[demo.*].eval`
golden + `[eval.*]` runtime, reference-free, operator-backed), ADR-0059 (storage
topology: Postgres ledger system-of-record + OTLP fan-out; §D2 the store dividing
line; §D5 the UI split — cairn owns the verdict, Langfuse owns raw traces; §D6 eval
computes in cairn). Builds on the shipped primitives: `cairn/core/eval/taxonomy.py`
(#474), `cairn/core/eval/recipe.py` (#442), `cairn/core/eval/diagnosis.py`,
`cairn/core/eval/cost_baseline.py`, `cairn/core/storage/eval_ledger.py` (#244),
`cairn/core/dispatch/dispatcher.py` (`_label_failures` hook), the
`/insights/*` + `/runs/{id}/diagnosis` endpoints in `cairn/core/triggers/server.py`
(#481), and `cairn/web/src/views/InsightsView.tsx`. Sequences the gated tickets:
#475 (metric contract), #477 (continuous-eval + Bus Tier 2), #478 (clustering +
suggestion engine), #458 (honest-eval / trustworthy metric).

## Context

The closed loop's *plumbing* exists (ADR-0059): a Postgres eval ledger, a
deterministic failure taxonomy that runs on completion, an on-demand recipe
runner (`POST /runs/{id}/evaluate`), a per-run "Why?" (`/runs/{id}/diagnosis`),
and an Insights dashboard. But dogfooding on cairn's own runs surfaces **two
concrete gaps** that make the layer a tally rather than a diagnosis tool:

1. **No auto-eval.** `dispatcher._label_failures` (dispatcher.py:435) runs
   `classify_failure` on every terminal run and persists `failure_labels` — but
   it **never runs the eval recipe**. A recipe verdict lands in the ledger
   (`eval_runs`) *only* when a human clicks "Evaluate this result"
   (`POST /runs/{id}/evaluate`, server.py:782). So a workflow that declares
   `[eval.*]` (e.g. `training/finetune`'s `model/gate`, ADR-0057) is never
   scored automatically. The ledger has a verdict table that fills only
   on demand.

2. **Insights is global-only and is a tally, not a drill-down.**
   `/insights/failures` (server.py:967) returns `{by_type: [{failure_type,
   count}]}` across *all* runs in the workspace — you see "8 performance_failures"
   but there is **no path** from that number to the 8 failing runs, to their
   evidence, to whether they share a root cause, to what to do. The three panels
   (`InsightsView.tsx`) are fleet counters. The per-run `/runs/{id}/diagnosis`
   exists but nothing links a count to the runs behind it, and nothing is scoped
   to a single workflow — which is the unit an engineer actually improves.

This ADR closes exactly those two gaps and lays the (gated) rail from a
diagnosed cluster to a human-approved fix. It is scoped by three locked product
decisions: **(P1)** the primary job is diagnose-and-fix failures; **(P2)** the
primary viewer is the engineer improving one workflow, not an exec; **(P3)** it
must be genuinely useful on cairn's own dev/eval/deploy runs first.

The design principle throughout is **own the verdict, bind the scorers, stop at
the diff** (ADR-0012 + ADR-0059 §D6): cairn computes and persists the verdict and
the diagnosis; it deep-links Langfuse for raw traces; and it **never actuates** —
the suggestion layer stops at "here is the proposed diff + evidence, open a PR?".

## Decision

**Two jobs, one pipeline — evaluate, then diagnose.** The engine's *first* job is to
**evaluate every run's result** — score the output quality against the workflow's recipe/contract
(D1/D2), producing a verdict (`pass`/`degraded`/`fail`) for *every* run, including ones that
succeeded mechanically. Its *second* job is to **diagnose the bad ones**. A bad outcome is one of
two things, and **both must flow into the same diagnose→cluster→suggest pipeline**:

- a **mechanical failure** — the run errored (timeout, tool error, budget breach): the taxonomy
  labels it today (#474);
- a **quality failure** — the run *finished* but its *result* was scored bad (a `fail`/`degraded`
  verdict: low faithfulness, wrong schema, missed a gate). Today this produces a *verdict* but **no
  label**, so it is invisible to the failure drill-down/clustering — a hole D1 closes below.

So "evaluate results" is not a side capability under failure-diagnosis; it is the engine's first
job, and a bad *quality* verdict is a first-class diagnosable case, exactly like a crash.

### D1 — Auto-eval on completion, in-process, as a sibling of failure-labeling

**Extend `dispatcher._label_failures` into a `_score_run` completion step** that
does two independent things on every terminal run:

1. **Label** — `classify_failure` → `failure_labels` (already shipped; unchanged).
2. **Score** — resolve the workflow's runtime `[eval.*]` recipe and, if present,
   run it over the run's stored output, persisting an `eval_runs` verdict.

Concretely, the new step reuses the exact primitives the on-demand endpoint
already uses (`resolve_runtime_recipe` + `extract_run_output` + `run_eval_recipe`
+ `record_eval_run`, all in `recipe.py` / `eval_ledger.py`), so this is **wiring
an existing path into the completion hook**, not new eval machinery. It writes to
`self.backend.eval_ledger` (the same store `_label_failures` already targets, so
labels and verdicts co-locate regardless of tier).

```python
# dispatcher.py — replaces the two `_label_failures(inv.id)` call sites
async def _score_run(self, run_id: str) -> None:
    inv = await self.store.get(run_id)
    if inv is None:
        return
    events = await self.store.get_events(run_id)
    await label_run_failures(inv.model_dump(mode="json"),
                             [e.model_dump(mode="json") for e in events],
                             ledger=self.backend.eval_ledger)   # #474, unchanged
    await auto_eval_run(inv, ledger=self.backend.eval_ledger)   # NEW (D1)
```

`auto_eval_run` lives next to `label_run_failures` in a new
`cairn/core/eval/auto_eval.py` (parallel to `diagnosis.py` — the one module
allowed to depend on both the recipe runner and the ledger), and is **best-effort
by the same contract as diagnosis**: any exception (no recipe, bad selector,
judge outage, ledger hiccup) is caught, logged, and swallowed — auto-eval must
never break a run's completion. It mints a fresh `EvalRun(run_id=…, recipe=…,
verdict=…, aggregate_score=…, judge_meta={…})` exactly as the `/evaluate`
endpoint does today (server.py:849), so the ledger shape is identical whether the
verdict came from the hook or a human click.

**Scope of what auto-evals (cost control is the whole game here):**

| Rule | Behaviour | Why |
|---|---|---|
| **Only terminal `done`/`failed`** | same gate as `_label_failures` | awaiting-approval / cancelled aren't verdict-ready |
| **Only if `[eval.*]` resolves** | no recipe → no-op | ADR-0057: reference-free runtime eval is opt-in per workflow |
| **Deterministic recipes always run** | `model/gate` / `cost/gate` are free | ADR-0057 D6 / ADR-0059 §D6 — gates are free, run every run |
| **LLM-judge recipes are SAMPLED** | `OBS_AUTOEVAL_JUDGE_SAMPLE_PCT` (default e.g. 0.2); always-on when a run already carries a failure label (score the tail we care about) | ADR-0057 D6: "judge is sampled, run async, off the hot path" |
| **Per-env kill switch** | `OBS_AUTOEVAL=off` disables the whole step | a prod/high-volume env can turn it off; dev/dogfood defaults on |
| **Cost-gated like any operator** | the eval operator runs through the ordinary governed surface (`run_eval_recipe` → `OperationContext`), so its LLM cost is tracked and budget-gated | ADR-0059 §D6 — the verdict is a governed, cost-tracked computation, not a side channel |

The judge sample/skip decision is deterministic per run (hash of `run_id` vs the
sample pct) so it is reproducible and testable. A skipped-judge run still gets its
free deterministic gates; the `eval_runs` row records `judge_meta.sampled=false`
so the UI can distinguish "judged: fail" from "not judged".

**A bad verdict is a diagnosable case, not just a number (closes the quality-failure hole).**
When `auto_eval_run` returns a `fail`/`degraded` verdict, it **also emits a failure label** carrying
the failing gate/objective + the judge's evidence, so a mechanically-successful run with a bad
*result* enters the *same* `failure_labels` path the taxonomy uses — and therefore the same
drill-down (D3) and clustering (D4). This is the unification of the two jobs: mechanical failures
come from `classify_failure` (events), quality failures come from the verdict, and both land as
labels an engineer can drill and cluster. Without this, a low-faithfulness compliance report would
show only as a `fail` in the verdict mix, with no path to "which runs, sharing what root cause."
(The label *type* for a quality failure is Open Decision #7.)

**Why in-process, not the bus.** The durable Bus Tier 2 (#477) that would let a
separate continuous-eval worker subscribe to `engine.run.completed` is deferred.
The completion hook is a synchronous seam that **already runs on every run**
(`_label_failures`), so extending it is the near-term-honest path. §D9 defines
the later swap: `auto_eval_run` is a pure `(run, ledger) → None` function, so
moving it behind a `run.completed` subscriber (#477) is a call-site move, not a
rewrite — same reason `label_run_failures` is bus-ready. The heavy/off-hot-path
work (LLM judging a large sample, re-scoring history) is what waits for #477; the
free gates + the sampled judge run in-process now.

### D2 — The metric contract (#475): declare what "good" means per workflow

Today `[eval.*]` is a single recipe → a single verdict. That is enough for a
gate, but "8 performance_failures on `training/finetune`" needs a per-workflow
definition of *good* to be actionable. **The metric contract extends the existing
`[eval.*]` block — it is not a new file or a new engine concept** (ADR-0057 D2:
adding capability is a new operator, never a schema/engine change; the contract
adds *declared intent*, still declarative, still in `pack.toml`).

A workflow's eval declaration gains three optional facets, all expressed as
ordinary recipes over `$output.*` (so they resolve through the same
`run_eval_recipe` path — no new evaluator kind):

```toml
[eval."training/finetune"]                      # a single recipe still works (back-compat)
uses = "model/gate"
  [eval."training/finetune".inputs]
  metric = "$output.metrics.eval_loss"; at_most = 1.5

# — OR — the richer contract form (#475), a list of named clauses:
[[eval."training/finetune".gate]]               # HARD GATE — a fail here = a failed verdict
uses = "model/gate"
  [eval."training/finetune".gate.inputs]
  metric = "$output.metrics.eval_loss"; at_most = 1.5

[[eval."training/finetune".objective]]          # OBJECTIVE — scored, tracked, non-blocking
name = "helpfulness"
uses = "eval/judge"
  [eval."training/finetune".objective.inputs]
  output = "$output.report"; rubric = "evals/helpfulness.md"

[eval."training/finetune".slice]                # SLICES — cut the verdict by a dimension
by = ["$output.meta.dataset", "$output.meta.model_role"]
```

- **Gates** (hard): a `fail` on any gate → `EvalRun.verdict = "fail"`. These are
  the deterministic-first, free-to-run clauses (ADR-0059 §D6 ordering: gates
  first).
- **Objectives** (soft): scored and persisted per objective, never block; they
  are the quality signal a suggestion later optimizes. Judge-backed objectives
  are subject to D1 sampling.
- **Slices**: dimensions to break the verdict down by (dataset, model-role,
  tenant). Each `eval_case_results` row already carries a `slice JSON` column
  (eval_ledger.py:75) — the contract's `slice.by` is *what fills it*. This is how
  Insights answers "the failures cluster on `dataset=synthetic`, not the model."

**Verdict aggregation** (`EvalRun.verdict`, an existing column): `fail` if any
hard gate fails; else `degraded` if any objective is below its declared floor;
else `pass`. This gives the three-value `final_verdict` ADR-0059 §D3 already
reserved on `runs`, computed once and persisted, not recomputed per read.

`manifest.py`'s `_validate_runtime_evals` (manifest.py:657) parses `[eval.*]`
into `runtime_evals: dict[str, EvalRecipe]` today; #475 widens the value to an
`EvalContract` (a dataclass holding `gates: list[EvalRecipe]`, `objectives:
list[NamedRecipe]`, `slice_by: list[str]`), with the single-recipe form parsed as
a one-gate contract for back-compat. Nothing else in the engine changes.

**Trust caveat (binds to #458):** the contract makes verdicts *structured*, not
*trustworthy*. An objective judged by a lying LLM-judge is still a lie. The
contract is safe to ship for **gates and diagnosis** (deterministic, or
human-inspectable evidence) before #458; **objectives that feed the suggestion
engine wait for #458** (§D5, §D8).

### D3 — Insights information architecture for the engineer (the core UX)

This is the highest-value change: turn the global tally into a **drill path that
ends at an action**. The path, and the endpoint behind each screen:

```
①  Fleet summary            → GET /insights/summary        (exists as 3 calls; add per-workflow rollup)
        │  "which workflow is unhealthy?"  ← the ONE new entry the engineer needs
        ▼
②  Per-workflow view        → GET /insights/workflows/{wf}          NEW  (P2: the unit of improvement)
        │  health · cost-vs-baseline · verdict mix · failure-type breakdown FOR THIS WF
        ▼
③  Failure-type breakdown   → (same endpoint, `by_type` scoped to {wf})
        │  "8 performance_failures on THIS workflow"
        ▼
④  The failing runs list     → GET /insights/workflows/{wf}/runs?failure_type=…&verdict=…   NEW
        │  ← the missing link today: from a COUNT to the ACTUAL RUNS
        ▼
⑤  Per-run evidence          → GET /runs/{id}/diagnosis     (EXISTS, server.py:916) — reuse verbatim
        │  failure labels + evidence + eval verdict + cost + "Open trace in Langfuse"
        ▼
⑥  Cluster view              → GET /insights/workflows/{wf}/clusters      NEW (§D4)
        │  "these 8 share root cause X" — grouped, with a representative run + evidence
        ▼
   Per-run "Why?"            → RunDiagnosisView (EXISTS) — the leaf, reached from ④ or ⑥
```

**What each new endpoint returns (in-process over `dispatcher.list` + the ledger,
exactly like the existing `/insights/*` — ADR-0059 §D2 names ClickHouse as the
scale path, deliberately not built at dogfood volume):**

- **`GET /insights/summary`** — a per-workflow rollup so screen ① is one call, not
  N. For each workflow (`_run_template_ref`, the same grouping key
  `/insights/cost` already uses, server.py:1006): `{workflow, run_count,
  failure_rate, verdict_mix: {pass,degraded,fail}, top_failure_type,
  savings_usd}`. This is the "which workflow is unhealthy" triage screen. It
  reuses the existing three aggregations, just grouped by workflow instead of
  globally — the exact axis the current page is missing.

- **`GET /insights/workflows/{wf}`** — the per-workflow deep view (P2). Everything
  the three global cards show today, scoped to one workflow: failure-type
  breakdown (`by_type`), health tiles, cost-vs-baseline, plus the **verdict mix**
  from `eval_runs` (the auto-eval verdicts D1 now produces) and **slice
  breakdown** (D2). This is the screen an engineer lives in.

- **`GET /insights/workflows/{wf}/runs`** — **the link that does not exist today.**
  Given a workflow and optional `failure_type` / `verdict` / `slice` filters,
  return the actual runs: `[{run_id, status, verdict, failure_types,
  created_at, cost_savings_usd, langfuse_url}]`. Each row deep-links to
  `/runs/{id}/diagnosis` (screen ⑤). This is the concrete "drill from the number
  to the runs" fix.

- **`GET /insights/workflows/{wf}/clusters`** — §D4. Groups the failing runs into
  root-cause clusters, each with a representative run + shared evidence +
  member `run_id`s.

**Frontend (`cairn/web/src/views/`, no inline CSS per house rule):** the existing
global `InsightsView` becomes screen ①'s triage table (workflow rows, click →
route). A **new `WorkflowInsightsView`** (routed `/insights/workflows/:wf`) hosts
screens ②–④ and ⑥ as sections, reusing the `.card`/`.frow`/`.htile` classes
already in `cairn.css`. Screen ⑤/leaf is the **existing `RunDiagnosisView`** — no
new trace viewer (ADR-0059 §D5: deep-link Langfuse). **Vite proxy caveat:** every
new `/insights/workflows/*` route must be added to `API_PATHS` in
`web/vite.config.ts` or it 404s in dev (repo memory: only a live e2e catches this).

### D4 — Failure clustering: rule-based first, embedding as a gated upgrade

Turn "8 performance_failures" into "these 8 share root cause X." **Rule-based,
deterministic, and shippable now** — it needs no trustworthy metric (it groups
*labels*, not *quality scores*), so it is UNGATED and lands before #458.

**Cluster key = a deterministic tuple over signals already in the ledger + run
record:**

```
cluster_key = (failure_type, template_ref, failing_node/operator, evidence_signature)
```

- `failure_type` — from `failure_labels` (#474).
- `template_ref` — `_run_template_ref` (the workflow, P2's axis).
- `failing_node/operator` — from the label's `evidence` dict, which the taxonomy
  already populates: `evidence.action_type` / `candidate_id` for tool failures
  (taxonomy.py:253), `event_seq`/`event_type` for others. The responsible
  node/operator is derivable from these.
- `evidence_signature` — a normalized digest of the evidence's discriminating
  field: the error-keyword bucket (`_TIMEOUT_KEYWORDS` vs `_RATE_LIMIT_KEYWORDS`
  vs `_PROVIDER_OUTAGE_KEYWORDS`, taxonomy.py:103) for system/perf failures; the
  `reason` string for others. This is what separates "8 timeouts on the same
  operator" (one cluster) from "5 timeouts + 3 rate-limits" (two clusters).

A cluster row is `{cluster_key, size, member_run_ids, representative_run_id,
shared_evidence, first_seen, last_seen}`. Computed **on read** in
`/insights/workflows/{wf}/clusters` at dogfood volume (no new table needed yet —
see D7); persisted to a `failure_clusters` table only when volume forces it (D7 /
#478).

**Embedding-similarity upgrade (GATED, #478):** the rule-based key over-splits on
free-text `reason` variance ("connection reset by peer" vs "connection reset").
The upgrade is to cluster the residual by **embedding similarity of the evidence
text**, *within* a `(failure_type, template_ref)` bucket (never across — that
would blur genuinely different root causes). **Bind, don't build**: use an
existing embedding model via the already-wired `eval` extras (sentence-transformers
or the platform's LLM-embedding client) + a standard clustering lib (`hdbscan` /
scikit-learn agglomerative) as an optional extra with the rule-based grouping as
the deterministic, hermetic fallback (repo rule: production libs behind extras,
deterministic fallback so tests stay hermetic). This is an *upgrade to the key*,
not a new pipeline — the endpoint contract is unchanged.

### D5 — Diagnosis → suggestion routing (GATED on #458)

The rail from a diagnosed cluster to a human-approved fix. **This entire decision
is gated on #458 (honest-eval): a suggestion engine against a lying metric
optimizes the lie.** It is specified here so the ungated work (D1–D4) is built
with the right seams, but **nothing in D5 ships before #458 proves the metric.**

**Routing: cluster → optimizer category → actuation surface → PR.** Each
`failure_type` (and its cluster evidence) maps to a *responsible optimizer
category* (the ADR-0012 §24.12.4 suggestion categories) and an *actuation
surface* — the versioned, lockfile-pinned artifact a fix would touch:

| Cluster signal | Optimizer category | Actuation surface (versioned artifact) |
|---|---|---|
| `generation_failure` / low-quality objective on a template | prompt-quality | template version (content-addressed, ADR-0012 §24.11.3) |
| `performance_failure` (cost/latency), no quality drop | capability-rerouting / model-role | model-role binding (#352) |
| `retrieval_failure` clustered on a source | eval-dataset / RAG-binding | retrieval config / eval dataset |
| repeated same-category failures with a known-good pattern | few-shot | memory namespace (`kind="few_shot_example"`, ADR-0012 Form 3) |
| `safety_failure` on a policy path | policy-tightening | policy artifact |

**Where it plugs in:** a `suggest` step consumes clusters (D4) + verdicts (D1) +
the metric contract's objectives (D2), applies rule-based thresholds
(ADR-0012 §24.12.4: "low-magic, explainable"), and emits rows to the
`suggestions` table whose schema ADR-0012 §24.12 already specifies (`proposed_diff
JSONB`, `evidence JSONB`, `status pending|accepted|rejected|expired`). **The
engine stops there.** Actuation is the existing human path: `cairn suggest list /
show / accept --as-pr / reject` (ADR-0012 §24.12.4) opens a GitHub PR with the
diff + evidence. No auto-apply, no self-modifying prompt (ADR-0012 Decision C/D —
the autonomy line). The suggestion layer's output is **always** "here is the
proposed diff + evidence, open a PR?" and never a mutation.

**The #458 gate, concretely:** the suggestion step must not run against an
objective whose scorer is not yet trust-verified. #458's honest-eval fix is the
precondition that a `degraded`/objective signal *means* something. Until then:
clustering + diagnosis (D4) ship (they group *deterministic labels*, no
trustworthy verdict required); the *suggestion emitter* is dark.

### D6 — Reports: per-run (exists) + the new per-workflow report, projected from the ledger

Two report projections, both **rendered from the ledger, never a stored blob**
(ADR-0059 §D6: the clean report is a projection, so it stays consistent with the
system of record and is re-derivable):

- **Per-run report** — EXISTS: `/runs/{id}/diagnosis` (the "Why?", server.py:916)
  + `/runs/{id}/report`. Unchanged; auto-eval (D1) simply means its `eval_runs`
  section is now populated without a human click.

- **Per-workflow report** — NEW: `GET /insights/workflows/{wf}/report` — the
  engineer's health report for one workflow, a projection over the same ledger
  reads D3 uses: **failure profile** (by_type + trend), **cost-vs-baseline**
  (from `/insights/cost`'s per-workflow group), **health** (success/verdict mix),
  **top clusters** (D4), and **suggestions** (D5, when ungated). Exportable as an
  immutable artifact the same way the per-run report is (Markdown/JSON
  projection), so it can be attached to a PR or a review. It is a *projection
  endpoint*, not a new store — the same reason ADR-0059 §D6 keeps the per-run
  "Why?" a projection.

### D7 — Data-model deltas (minimal; most is projection over what exists)

The ledger schema (ADR-0059 §D3 / eval_ledger.py) already carries what D1–D3
need: `eval_runs` (verdict + aggregate_score + judge_meta), `eval_case_results`
(with the `slice JSON` column D2 fills), `failure_labels` (with `evidence`).
Deltas:

| Delta | Store | Status |
|---|---|---|
| `eval_case_results.slice` populated per D2's `slice.by` | Postgres (exists, unfilled) | UNGATED — D2 writes it |
| `runs.final_verdict` populated by auto-eval (reserved in ADR-0059 §D3, unpopulated today) | Postgres | UNGATED — D1 writes it |
| `judge_meta.sampled` / `judge_meta.autoeval` flags on `EvalRun` | Postgres (JSON, no migration) | UNGATED — D1 |
| `failure_clusters(cluster_id, workflow, cluster_key, size, member_run_ids JSON, representative_run_id, shared_evidence JSON, first_seen, last_seen)` | Postgres | GATED — only when read-time clustering (D4) costs too much; #478 |
| `suggestions` (schema in ADR-0012 §24.12) | Postgres | GATED on #458 (D5) |

**Store dividing line (ADR-0059 §D2) is unchanged:** verdicts, labels, clusters,
suggestions are **gate/audit data → Postgres** (bounded, joined, audited). Raw
spans, per-token metrics, and volume aggregations (the eventual cluster-count and
p95 at scale) are **ClickHouse**, joined by `run_id`. At dogfood volume the
in-process reads over `dispatcher.list` are honest and cheap; the ClickHouse
aggregation is the documented scale swap, not a day-one build.

### D8 — The trust gate ordering (why sequencing is a design decision, not a nicety)

A suggestion engine optimizes whatever metric it is handed; a lying metric is
optimized into a worse product. So the honest-eval fix (#458) is a **hard
predecessor of the suggestion/actuation layer (D5)** — but *not* of clustering or
diagnosis (D4/D3), which group **deterministic labels and human-inspectable
evidence**, requiring no trustworthy verdict. This splits the epic cleanly:
everything that helps a human *see and understand* failures ships now; everything
that lets the system *propose a change* waits for the metric to be trustworthy.
The metric contract (D2) is safe to ship for its gate and diagnosis facets before
#458; only its *objective* facet (the quality signal a suggestion would optimize)
is gated.

### D9 — In-process now, durable bus later (the swap seam)

`auto_eval_run` (D1) is a pure `async (run, ledger) → None`, invoked from the
dispatcher completion hook — the same shape and the same call site as the shipped
`label_run_failures`. When Bus Tier 2 (#477) lands, both move behind a durable
`engine.run.completed` subscriber (a continuous-eval worker) **without changing
their bodies** — it is a call-site relocation, and it is what unlocks the
off-hot-path heavy work: judging a large sample, re-scoring history, and
cross-process fan-out. The near-term in-process hook is deliberately *not*
blocked on the bus; the bus is the throughput/durability upgrade, not the
correctness path.

## Consequences

- **The gap closes:** every `[eval.*]` workflow gets an automatic verdict on
  completion (D1); the engineer can drill global → workflow → failure-type →
  failing runs → evidence → cluster (D3/D4); the per-workflow report (D6) is the
  actionable artifact P2 asked for.
- **Cost is bounded by design:** free deterministic gates every run; LLM-judge
  sampled + always-on only for already-failed runs; per-env kill switch;
  everything cost-tracked through the governed operator surface.
- **The autonomy line holds:** diagnosis and clustering are automated; the
  suggestion layer stops at a proposed diff + evidence and is dark until #458
  (D5/D8). Nothing self-modifies (ADR-0012).
- **Reuse over rebuild:** D1 wires the shipped on-demand path into the hook; D3
  re-scopes the shipped `/insights/*` aggregations by workflow and adds the
  missing drill links; D5 reuses the ADR-0012 `suggestions` schema + `cairn
  suggest` CLI; the leaf view is the existing `RunDiagnosisView`; embedding
  clustering binds existing libs. The only genuinely new code is the completion
  step, ~4 workflow-scoped read endpoints, the `WorkflowInsightsView`, and (gated)
  the cluster/suggest steps.
- **Cost of the change:** the `_score_run` hook + `auto_eval.py`; the
  `EvalContract` widening in `manifest.py` (#475); the workflow-scoped endpoints +
  view; the read-time clusterer. The gated tail (embedding clustering, suggestion
  emitter, durable bus, `failure_clusters`/`suggestions` tables) is scheduled, not
  built.

## Non-goals

- **An exec/compliance summary layer.** P2 fixes the viewer as the improving
  engineer; the roll-up-for-leadership view is a later, separate layer (ADR-0059
  §D5's own framing).
- **A cairn-built trace waterfall.** Deep-link Langfuse (ADR-0059 §D5); the leaf
  is `RunDiagnosisView` + an "Open trace in Langfuse" link.
- **Auto-apply / self-modifying prompts / auto-fine-tune.** The autonomy line
  (ADR-0012 Decisions C/D) — the suggestion layer stops at the diff.
- **A new analytical engine or a mega-table.** ClickHouse via ClickStack is the
  documented scale tier (ADR-0059 §D2); in-process reads are the dogfood path.
- **Ingesting external systems' telemetry.** On-platform scope (ADR-0059 §D4).
- **Shipping the suggestion engine before #458.** By design (D8).

## Open decisions

1. **Auto-eval judge sample default.** *Recommendation:* default
   `OBS_AUTOEVAL_JUDGE_SAMPLE_PCT=0.2` for objectives, **but always score judge
   recipes for runs that already carry a failure label** (label the tail we care
   about at 100%, sample the healthy body). Deterministic gates are unconditional.
2. **Should `runs.final_verdict` be written by the hook or stay ledger-derived?**
   *Recommendation:* write it in D1 (denormalize onto `runs`) so the per-workflow
   summary (D3 ①) is a single indexed read instead of an N-way ledger join —
   ADR-0059 §D3 already reserved the column for exactly this.
3. **Read-time vs. persisted clustering.** *Recommendation:* read-time now (D4,
   no table); introduce `failure_clusters` (D7) only when the per-read cost is
   measured to hurt at real volume — carry it as the #478 deliverable, not a
   day-one migration.
4. **Cluster key granularity — include model-role / connector in the tuple?**
   *Recommendation:* start with `(failure_type, template_ref, node/operator,
   evidence_signature)`; add `model_role` as a *slice* (D2) rather than a cluster
   key so "same root cause, different model" stays one cluster you can slice,
   not two clusters.
5. **Does auto-eval run on `failed` runs (not just `done`)?** *Recommendation:*
   yes — a failed run's stored output (partial) is often exactly what a runtime
   gate should verdict; `extract_run_output` already tolerates empty output
   (returns `{}` → recipe skips cleanly). The failure *label* and the eval
   *verdict* are independent signals and both are useful.
6. **D5 actuation surface — git-PR vs console-approval (pluggable + toggleable).**
   *Recommendation:* the suggestion actuator is a **pluggable seam** with two bindings that both
   preserve human-gate + audit + reversibility; the suggestion *engine* is identical, only the
   final approval step differs:
   - **git-PR binding** — opens a PR (diff + evidence) to the repo holding the pack/artifact. Right
     for cairn's own **dogfood** and for **code-managed** customers (packs-as-code in their git
     repo). This is the Phase-1 default.
   - **console-approval binding** — a "proposed change → review → approve → new version" flow *in
     the console*, for customers whose workflows are **DB/console-managed** (ADR-0049 system-of-
     record) and who don't run a git repo of packs.

   The actuator is **enable/disable per deployment** — a shop can turn suggestions/PRs off entirely.
   **Deferred follow-on:** applying an approved change to an *installed* workflow — bumping it to a
   new **deployed version** (ADR-0047 versioned installed-workflow records) — is the console-
   approval binding's "apply" step; git-PR ships first, the installed-workflow-versioning path is
   built when a DB-managed customer needs it. *(Whole decision is gated with D5 on #458.)*
7. **How a quality-fail becomes a label (D1 unification).** When auto-eval returns `fail`/
   `degraded`, what failure-label *type* does the emitted quality label carry? *Recommendation:* a
   distinct signal keyed on the failing gate/objective (so it clusters *by objective* — "faithfulness
   is failing on compliance/report") rather than folding into the mechanical `GENERATION_FAILURE`.
   Options: a new `QUALITY_FAILURE` taxonomy member vs. reuse `EVAL_FAILURE`/`GENERATION_FAILURE`
   with an `evidence.source="eval_objective"` marker. Lean toward a distinct type so the drill-down
   cleanly separates "the run crashed" from "the run's output was judged bad."
