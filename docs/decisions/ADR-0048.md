# ADR-0048 — Workspaces: the first-class tenancy boundary (day-one), and the hybrid control-plane SaaS shape

Status: Proposed (2026-06-29, **rev 2** — supersedes the `tenant_id`-column / "defer multi-tenancy" framing of rev 1)
Relates to: ADR-0049 (definition source of truth — the DB records that a workspace scopes), ADR-0045 (distribution v1; *deferred* OCI = the per-workspace managed-image substrate), ADR-0047 (run provenance — the records that get workspace-scoped), ADR-0033 (credentials are references), ADR-0029 (registry mirror), ADR-0042 (one verb per operator). Open issues: #204 (dependency isolation), #205 (sandboxing), #223 (the first concrete scoping step — to be reframed `tenant_id` → `workspace`).

## Context

cairn is **open-core + a closed managed-infra platform, and the SaaS ships *together* with the open source.** So multi-tenancy is a **day-one product requirement**, not a deferred migration.

That corrects rev 1, which assumed "self-hosted single-org now, SaaS someday" and therefore proposed a quiet `tenant_id` column defaulting to `"default"` to retrofit later. Given the actual business model, two things change:

1. **Timing:** the tenancy boundary must exist from the start, not be deferred.
2. **Form:** a bare always-`"default"` discriminator with *no entity behind it* is the wrong shape — it is the Airflow Multi-Team anti-pattern (logical scope on a shared DB, which their own docs call "*not* multi-tenancy / not real isolation"). The field's **open-core-plus-managed-cloud peers — exactly cairn's model** — all use a *first-class boundary entity*: **Windmill workspaces**, **Prefect workspaces** (inside accounts), **Dagster+ deployments**, **Temporal namespaces**. None retrofit a default column.

## Decision

### 1. The workspace is a first-class entity, present from day one
A `workspace` is a real entity — `id`, `name`, settings, an **encryption-key reference** (per-workspace data isolation, cf. Prefect's workspace-unique keys), membership/RBAC, and a blob namespace — **not** a bare column.

- **OSS self-hosted = one implicit `default` workspace** (single-workspace mode; no switcher, no friction).
- **Managed SaaS = one workspace per tenant** — the unit of isolation, RBAC, billing, and quota.

Same schema both ways: SaaS does **not** require a migration, it *activates* multi-workspace.

### 2. Everything cairn defines (ADR-0049) is workspace-scoped
The scope key is **`workspace_id`** (FK to the workspace entity), carried on every record: installed-workflow records + their content-addressed definitions (ADR-0049), runs (+ traces / results / replays), the schema store, environments/profiles, secret-references, policy overlays, audit.

- **Blobs** (traces, replays, artifacts) get a **`workspace/<id>/` key prefix** — a local directory self-hosted, an object-store prefix (S3/GCS) on a fleet. `workspace/<id>/` is the blob *namespace*, not "the workspace."
- **Per-workspace encryption key** gates data isolation on the metadata side.

### 3. The only non-workspace thing is operator *code*
Operators are the **shared capability pool** (ADR-0049 §1): pip-installed wheels (shared env) or containerized/sandboxed images. You cannot drop a wheel in `workspace/<id>/` and import it per-workspace without per-workspace venvs (rejected, ADR-0045). Per-workspace *execution* isolation is **sandboxing (#205) + dependency isolation (#204)**, not code directories. "Enable pack for workspace X" = a workspace-scoped DB record enabling it + isolated execution — never an env mutation per workspace.

### 4. The SaaS shape is the hybrid control-plane
Both relevant open-core-plus-cloud peers (**Prefect Cloud, Dagster+ Hybrid**) converge here, and it matches cairn's posture (execution on managed/customer compute, secrets-as-references that never leave):

- The **managed control plane** holds workspace-scoped **metadata** — runs, the installed-workflow registry + definitions (ADR-0049), schemas, policy, audit.
- **Execution + operator code + secrets** run on **workspace-scoped managed compute** (GPU rentals, sandboxes), reached **outbound-only**; the control plane never reaches into the execution environment or sees code/secrets.

Open-core fit: **OSS self-hosted** = single workspace, you run your own control plane + workers. **SaaS** = a managed multi-workspace control plane + managed per-workspace compute. The workspace scopes the control-plane metadata; compute is provisioned per-workspace.

### 5. Isolation tiers — start shared, upgrade per workspace
The `workspace_id` key is identical across backends; *how strongly* a workspace is isolated is a per-facet upgrade, not a rewrite:

- **Relational** (SQLite or Postgres, possibly remote/managed): shared tables + `workspace_id` (default) + optional Postgres **row-level security**. **Schema-per-workspace** / **database-per-workspace** are strict-isolation upgrades.
- **Blobs:** `workspace/<id>/` prefix on the configured blob backend (local dir self-hosted → object store on a fleet).
- **Compute:** a shared managed pool with **workspace tagging** (Windmill worker-groups / Temporal per-tenant task-queue precedent) → dedicated per-workspace workers for premium / strict isolation.

## Consequences
- The `workspace` entity + `workspace_id` on the ADR-0049 record stores land **day one**; OSS runs single-workspace transparently; SaaS activates multi-workspace with no schema rewrite.
- A request → **workspace resolution** (subdomain / header / token claim) is required for SaaS; OSS resolves to `default`.
- The install model splits along the open/managed seam (ADR-0049): OSS = allowlisted `uv pip install` on your own worker; SaaS = vetted registry catalog baked into managed per-workspace images — no arbitrary code in a shared fleet.
- Object-store blobs + a reconcile-loop + the per-workspace OCI image substrate are the heavy lifts — staged, not v1.
- **Supersedes rev 1's** `tenant_id`-default-column mechanism and its "defer until a second tenant" stance.

## Open questions
- Workspace resolution: how a request maps to a workspace (subdomain / header / token claim).
- Per-workspace secrets backend scoping (ADR-0033) and per-workspace policy overlays.
- Compute isolation default: shared-pool-with-tagging vs dedicated per-workspace workers.
- RBAC *within* a workspace (roles), and the OSS-vs-SaaS feature split (Prefect precedent: RBAC / SSO / audit-logs are Cloud-only).
- Object-store abstraction for `workspace/<id>/` blobs vs. keeping small artifacts inline in the DB.

## Scope note
Direction-setting; it does not change #221 (correct single-node DB provenance). The first concrete step (**#223, reframed `tenant_id` → `workspace`**): introduce the `workspace` entity + `workspace_id` on the ADR-0049 record stores (default single workspace), the `workspace/<id>/` blob prefix, and one `current_workspace()` resolver (returns `default` until SaaS auth/routing lands) — so the model is workspace-aware before any of the heavier fleet / sandbox / OCI / hybrid-control-plane work.
