# ADR-0061 — Knowledge as a governed, cross-pack-composed context slot

Status: Proposed (2026-07-05)
Relates to: #471; the RAG service (`cairn/services/rag/{lifecycle,ingest}.py`, the
`rag/parse` operator with docling/markitdown backends), the pack manifest
`[requires.rag.*]` → `RagRequirement` (`cairn/core/pack/manifest.py`), the skill
composition engine (`cairn/core/engine/skill_engine.py`), the policy engine +
ADR-0053 policy scoping (`cairn/core/policy/engine.py`), the model-role registry
(#352), the few-shot library #473 (sibling context-augmentation), run provenance
(ADR-0047), the explainability/Citations facet (#472), and the failure-driven
eval/suggestion engine (#478/#480). **Supersedes the "standalone corpus + governance
metadata" framing of #471** with a composition-first model.

## Context

Packs today contribute three kinds of runtime material:

1. **Policy** — composes across packs. The policy engine merges pack ① + overlay ②
   + store ③ policies into one enforced set (ADR-0053).
2. **Skills** — compose across packs. `skill_engine` bundles skill-augmented
   compiled templates from whatever packs contribute them.
3. **Knowledge** (RAG corpora) — **does not compose.** A corpus is queried only by
   an *explicit node* authored into one workflow: `incident/operations/search-runbooks.yaml`
   calls `rag/search` against the pack-local `runbooks` corpus. Confirmed: retrieval
   is explicit-node-only — there is no ambient augmentation and no way for one
   workflow to pull knowledge contributed by another pack.

Two consequences follow, and both are load-bearing:

- **A corpus nobody queries is inert.** Shipping a `kind="knowledge"` pack as pure
  data + governance metadata delivers nothing on its own — something must retrieve
  it. So the value is not in the *packaging*, it is in the *retrieval binding*.
- **The real value is consumer-side, not provider-side.** The question is not "do
  two packs share one corpus" (no second consumer today). It is "can **one** workflow
  compose knowledge from **many** independently-owned, independently-versioned packs
  into a single context." An RCA run wants, composed together: the `incident` pack's
  runbooks + a `security-kb` pack's MITRE/ATT&CK + a `compliance-kb` pack's controls
  + the customer's own `postmortems-kb` — four owners, four release cadences, one
  context slot, and the author vendors none of them.

The proto that already exists (`incident` runbooks + a hardcoded search node) is
"model A": corpus and query co-located in one workflow. It works, but a standalone
knowledge kind that only supports model A is just that split into two packs — the
coupling returns at authoring time, so the new kind earns nothing.

Own-vs-bind (recurring project rule): cairn **owns** what governs and routes a
verdict/context (the role, the composition, the admissibility policy, the provenance
= the moat); it **binds** the commodities (embedders, parsers, vector stores — all
already wired).

## Decision

**Model knowledge as a first-class, cross-pack-composed, policy-governed context
slot — the third member of the pack-contribution family, built by analogy to how
policy and skills already compose.** Underneath it reuses the existing ingest +
`rag_{name}` collections; on top it adds a role/slot, a cross-pack composer, an
injection step, and a policy gate.

1. **`kind="knowledge"` pack.** A corpus-only pack — data + the `__init__` shim,
   **no `.py`** (packs are DATA). Ships raw source docs (`.pdf/.docx/.pptx/.xlsx/.md`),
   auto-parsed via the existing `rag/parse` (docling/markitdown, deterministic `pypdf`
   fallback) → chunk → embed → `rag_{name}`. No hand-conversion to markdown required.
   Carries **governance metadata**: `license`, `source`, `citation_policy`, `attribution`.
   May optionally ship its own `search` operation (model B) but does not have to.

2. **Knowledge role/slot.** A named slot a template declares — mirrors the model-role
   registry (#352) and skill composition. A template declares e.g.
   `knowledge: [incident_context]`; a knowledge pack declares which role(s) its
   corpora provide into. **Resolution = the union of every bound corpus, across every
   installed pack, that provides that role.** The role is the composition seam; the
   corpus name stays the physical `rag_{name}` collection. This is the piece that
   makes "many packs → one slot" work without the workflow naming any corpus.

3. **Ambient retrieval + injection (model C).** At a declared augmentation step, the
   engine queries the composed corpora for the slot's role, injects the top-k hits
   into the LLM context, and stamps each hit's provenance (source pack + corpus +
   page/source-path, already present on `ParsedDoc.metadata`). Deterministic: no bound
   corpora → empty injection, workflow output unchanged. This is the **context-
   augmentation family** shared with few-shot #473 — *declare a slot → bind a provider
   → inject at runtime → record provenance* — and the two should share scaffolding.

4. **Policy governs admissibility (the differentiator).** Reusing ADR-0053 pack-based
   policy: a policy may gate **which** packs' knowledge may enter a given workflow's
   slot (by `trust_level` / `publisher` / pack name) and attach **obligations** —
   redact PII-classified corpora at injection, require citation of every injected
   chunk, cap per-pack contribution. Enforced at the injection step, audited via
   provenance. This is what makes it *governed context assembly*, not a RAG bolt-on:
   observability vendors and orchestrators retrieve; they do not govern what may
   enter context.

5. **Provenance + citation.** Every injected chunk is cited by source pack + corpus
   + locus, surfaced in run provenance (ADR-0047) and the #472 Citations facet.
   Directly upgrades the eval/suggestion engine (#480/#478): binding an
   `optimization_playbook` knowledge pack turns rule-routed suggestions into
   **retrieved, grounded, cited** ones — a smarter flywheel that stays auditable.

6. **Reuse, do not rebuild.** `rag/parse` ingest, `rag_{name}` collections,
   `discover_corpora`, the registry install/loader, and the `VectorStore` abstraction
   are all unchanged. **Net-new is only:** the governance metadata fields, the knowledge
   role registry, the cross-pack composition resolver, the injection step, and the
   policy hook.

## Consequences

**Phasing (each slice ships value; slice 1 is the manifest work #471 already scoped):**

- **Slice 1 — manifest (small).** `kind="knowledge"` + governance metadata +
  corpus-only pack validation + an example pack shipping real source docs. Delivers
  the governed installable corpus (models A/B) on its own.
- **Slice 2 — role + composition.** Knowledge role registry + cross-pack resolver
  (union of bound corpora across packs). Enables "many packs → one slot."
- **Slice 3 — ambient injection.** The augmentation step + provenance/citation. The
  "install knowledge → decisions improve + cite source, no workflow edit" unlock.
  Shares scaffolding with #473.
- **Slice 4 — policy gating.** Admissibility + obligations via ADR-0053. The
  governance moat.

**Cross-pack composition is now CORE, not deferred.** This reverses the earlier
provider-side call to defer binding: the value is consumer-side (one workflow, many
knowledge packs), and it is the whole point of a standalone `knowledge` kind.

**Unifies the pack-contribution model.** Policy, skills, and knowledge become one
story — pack-contributed, cross-pack-composed, policy-governed runtime material —
rather than three unrelated mechanisms.

**Latent until fuel.** Like the eval engine, this is depth/retention, not
acquisition. The multi-pack composition only pays once real corpora and run volume
exist; a design partner's knowledge should be the first fixture, not a synthetic one.

**Open decisions (to resolve before the affected slice builds):**

- **(a) Role namespacing** — global role names vs pack-scoped (`security_kb:context`).
  Global is simpler and matches the `rag_{name}` collection namespace; pack-scoped
  avoids collisions between vendors. Lean global with a reserved-prefix escape hatch.
- **(b) Role discovery** — how a workflow author sees which roles/knowledge are
  installed and bindable (doctor output + a console Library "Knowledge" facet).
- **(c) Retrieval budget across many corpora** — dedup, per-pack top-k caps, and
  cross-corpus ranking when a slot binds N corpora, so one large corpus cannot crowd
  out the rest.
- **(d) Obligation timing** — do redaction/citation obligations run inline at
  injection, or as a pre-index transformation pass (cheaper at query time, but the
  index then holds redacted text)?
- **(e) BYO drop-in corpus** — the customer-knowledge path: a workspace-local,
  non-packaged corpus that provides into a role without authoring a pip distribution.
  Reuses the same ingest + role + policy; skips packaging. Likely its own ADR once
  slice 2/3 land.
