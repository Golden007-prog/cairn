### 24.11 Decision: template lifecycle — versioning, regression eval, deferred Jinja

**Today's situation.**

| Concern | Status |
|---|---|
| Template prose rendering | Static — markdown body passed verbatim as system message. **No Jinja, no variable interpolation.** Runtime state goes to a separate `HumanMessage` via `_format_user_input`. |
| `version: 1.0.0` field on templates | Declared but **not enforced** — engine reads it, doesn't use it for resolution |
| `tag: v1.0` in skill template refs | Declared but **ignored** — always resolves to the file on disk |
| Content-addressed identity (hash of template body) | Designed in §3.7/§11 as "Docker-style tags + immutable hashes" — **not built** |
| Prompt regression eval | **Not supported.** §24.5 eval checks schema/structural validity, not "did the prompt change cause a quality drop" |

**Decision: four coordinated calls, none of them Jinja.**

#### 24.11.1 Decision A: do NOT add Jinja rendering in MVP

Jinja interpolation on the prose body was considered and **deliberately rejected** for the current platform stage. Reasons:

1. **The "interpolate state into prompt" need is already met.** The compiler passes runtime state (trigger event, payload, service, prior node outputs) as the `HumanMessage`. The LLM sees everything. Jinja's marginal value is shaping the system message, not enabling state access.
2. **Versioning gets harder.** Today a template body is text — `diff v1.md v2.md` is meaningful. With Jinja, the same body renders differently depending on context. Regression eval has to answer "did the prompt change or did the data change?" — Jinja muddies that.
3. **Replay clarity drops.** Today reading the template body tells you what the LLM saw. With Jinja, you need the rendered output to audit — which means storing rendered prompts per run (storage + grepability cost).
4. **Validate gets more work.** Jinja AST parsing + checking referenced vars exist in `input_schema` — new failure modes, more code.
5. **The init.py stub bug from session 2** (used `{{ payload | tojson }}` claiming Jinja) is fixed by editing the stub, not by adding Jinja.

**Re-add Jinja only when a concrete use case lands:**

| Trigger condition | What it would unlock |
|---|---|
| Template author needs conditional prompt sections (e.g., "if HIGH severity, prioritize root cause") that meaningfully change LLM behavior | Conditional `{% if %}` blocks |
| Community pack needs DRY across templates (shared citation rules, common refusal patterns) | `{% include "shared/x.md" %}` partials |
| RAG-heavy templates need to format hit lists in prompt-author-controlled ways | `{% for %}` loops |
| Multi-tenant prompt variants of the same template | Variable-driven phrasing |

None of these are blocking incident pack or the first three ModelOps packs. Defer.

#### 24.11.2 Decision B: if Jinja ever lands, persist the rendered prompt

When Jinja is added, two non-negotiable rules:

1. **Render once, at compile time per run, before sending to LLM.** No re-rendering inside the LLM call path.
2. **Persist the rendered prompt to the trace store** alongside `findings` / `action_decision` events. Replay shows what the LLM actually saw, not the template source.

```python
# New event type when Jinja lands:
{"type": "prompt_rendered", "data": {
    "template": "incident/deep-investigation",
    "template_hash": "sha256:abc...",
    "rendered": "...",          # the actual string the LLM received
    "node": "synthesize_rca",   # which state machine node
}}
```

This keeps replay/audit honest: the rendered prompt is canon, the template source is the recipe.

#### 24.11.3 Decision C: build content-addressed versioning + mutable tags

The §3.7 / §11 design ("Docker-style tags + immutable content hashes") was specced but not built. Resurrect it as a concrete phase.

**Mechanism:**

- Compute `template_hash = sha256(canonical_json(frontmatter) + body_text)` at compile time
- `CompiledTemplate.content_hash` carries this
- A new `template_tags` table maps `(pack, name, tag) → template_hash`
- Skill `template.tag` resolves through `template_tags` → hash → load by hash from `templates` (history) table or from disk-by-tag at compile time
- Storage tables (new in §24.4):

```sql
CREATE TABLE templates (
  pack         TEXT NOT NULL,
  name         TEXT NOT NULL,
  template_hash TEXT NOT NULL,         -- sha256 of frontmatter + body
  body         TEXT NOT NULL,          -- full text as compiled
  spec_json    JSONB NOT NULL,         -- parsed TemplateSpec
  author       TEXT,
  created_at   TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (pack, name, template_hash)
);

CREATE TABLE template_tags (
  pack         TEXT NOT NULL,
  name         TEXT NOT NULL,
  tag          TEXT NOT NULL,           -- "latest", "v1.0", "stable"
  template_hash TEXT NOT NULL,
  updated_at   TIMESTAMPTZ NOT NULL,
  updated_by   TEXT,
  PRIMARY KEY (pack, name, tag)
);
```

**What this unlocks:**

- `cairn ls templates` shows `incident/deep-investigation@v1.2 (sha256:abc123)`
- Skill refs resolve to immutable hash even when written as tag — engine pins the hash at compile time, audit shows which exact version ran
- Rollback = `UPDATE template_tags SET template_hash = <old> WHERE tag = 'latest'`
- `cairn eval --pin <hash>` runs eval against a specific historical version
- `runs.template_hash` column → every run records the exact template version that ran (added to `runs` schema in §24.4)

#### 24.11.4 Decision D: prompt regression eval (the killer comparison feature)

Build on top of `cairn eval` (§24.5):

**MVP — `--compare-against` flag:**

```bash
$ cairn eval incident --compare-against incident/deep-investigation@v1.1
✓ pagerduty-checkout-latency  (cost: $0.04 → $0.02, -50%; agree)
✗ db-pool-payment-service     (cost: $0.06 → $0.03, -50%; DIFFER)
                              prior:    root_cause="db connection leak"
                              current:  root_cause="unrelated network issue"
✓ kubernetes-pod-oom          (cost: $0.05 → $0.03, -40%; agree)

Summary: 2/3 agree (67%), cost -45%
Below 80% agreement threshold — REGRESSION
```

Same dataset, runs against both versions (current + comparison), reports:
- Per-case: agreement (semantic match via schema + structural diff) / cost delta / latency delta
- Aggregate: agreement %, cost delta %, p50/p95 latency delta
- Exit non-zero if agreement drops below threshold (CI gate)

**Phase 2 enhancements:**

- Statistical significance (paired t-test on numeric metrics, McNemar's on binary)
- Judge-LLM semantic comparison ("are these two RCAs equivalent?")
- Per-dimension scoring (correctness, hallucination, citation, brevity)
- `--rollback-on-regression` flag for production deployment automation

This is the differentiator. Phoenix / Langfuse / Braintrust sell this as products. We get it cheap because we already have the run pipeline.

#### 24.11.5 What's deliberately out of scope

- **DB-backed templates with hot reload** (templates served from DB, editable via UI). Real UX win for non-developer users, but lowest priority technically — pushed to P5+ or whenever there are non-developer users. Today's filesystem-based loading is fine.
- **Multi-tenant template variants.** No tenant model exists yet (Steal-1 covers identity). Worry about it when there's more than one tenant.
- **Prompt A/B testing infrastructure.** Tools like LaunchDarkly / GrowthBook do this; integration belongs in a future "experimentation" pack, not core.
