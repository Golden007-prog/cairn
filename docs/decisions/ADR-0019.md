### 24.19 Decision: pack code architecture — operator packs vs. domain packs

**The problem.** The naïve answer to "how do packs ship code/scripts
natively?" is "each pack ships a `code/scripts/` dir with a declared
entry-point contract." That answer is wrong, because it makes every
pack a mini Python project — heavy to maintain, hard to develop, hostile
to the community-pack motion. Domain experts won't write 200 LoC of
Ray boilerplate just to declare "fine-tune a model on this dataset."

**The decision.** Split the pack world into two distinct tiers, with a
hard boundary between them. Borrow the right pattern from
Terraform (providers / modules), Ansible (modules / playbooks),
Kubernetes (operators / manifests): **separate the thing that DOES work
from the thing that SAYS what work to do.**

#### 24.19.1 The two-tier pack model

| Tier | What it is | Who writes them | What it ships | How many |
|---|---|---|---|---|
| **Operator pack** | A library exposing a class of operations (Ray train/serve, Unsloth fine-tune, BentoML build, DVC version, HF Hub download, W&B log, Presidio redact, Evidently drift). | Domain experts / library authors / platform teams. | Python: `Operation` subclass(es) with Pydantic input/output schemas + optional image + resource declarations. Real test suite. Strict semver. | Small. ~10–30 across the ecosystem. Vetted. |
| **Domain pack** | Declarative composition of operators into a workflow. | Users / teams / community. SREs, MLEs, product engineers. | **No Python code beyond Pydantic schemas.** YAML templates, skills, policies, declarative operator bindings, evals, examples. | Many. Every team writes them. Easy to share, fork, version. |

**The hard rule (enforced by doctor at load time):** *Domain packs MAY
NOT ship Python code other than Pydantic schemas.* Anything procedural
goes in an operator pack. The boundary is binary. Soft boundaries decay.

#### 24.19.2 The `Operation` protocol (mirrors `Executor`)

Verified upstream finding (§24.19's verify-upstream report): we already
have `ExecutorRegistry` + `Executor` protocol for the action-decision
path. The `Operation` protocol is the **graph-node-step** analogue —
same registry shape, same entry-points discovery pattern, different
role.

| Concept | Capability | Executor | Operation (new) |
|---|---|---|---|
| Shape | Function | Class | Class |
| Registered by | `default_registry.register(name, fn)` | `ExecutorRegistry.register(name, Executor)` | `OperatorRegistry.register(name, Operation)` |
| Called via | `tool_call` step in template | `ActionHandler` (after policy gate) | `operation` step in template |
| I/O | callable signature | `ActionDecision → ActionOutcome` | `inp: InputSchema → out: OutputSchema` |
| Runtime | Always inline (orchestrator process) | Inline, Restate, or Temporal | Inline OR external (via §24.14 C1) — chosen by whether `image:` is declared |
| Discovery | Pack `__init__.py` factory | Pack `__init__.py` factory | Entry-points group `cairn.operators` |

```python
# cairn/core/operator.py — new
from typing import Generic, TypeVar
from pydantic import BaseModel

I = TypeVar("I", bound=BaseModel)
O = TypeVar("O", bound=BaseModel)

class Operation(Generic[I, O]):
    name: str                    # "unsloth/finetune"
    version: str                 # "0.3.1"
    input_schema: type[I]
    output_schema: type[O]
    image: str | None = None     # if set → routes through §24.14 C1
    resources: ResourceSpec | None = None

    def run(self, inp: I) -> O: ...
```

Mirroring `ExecutorRegistry` exactly. No new plumbing patterns.

#### 24.19.3 What a domain pack looks like (no Python beyond schemas)

```
obs-pack-finetune-llama-instruction/
├── pack.toml                                # declares operator deps
├── templates/
│   └── finetune.md                          # state_machine, references operators
├── operations/                              # YAML bindings, NOT scripts
│   ├── download-base.yaml                   # → hf-hub/snapshot operator
│   ├── prepare-data.yaml                    # → dataset-transform operator
│   ├── train.yaml                           # → unsloth/finetune operator
│   ├── eval.yaml                            # → hf-eval operator
│   └── deploy.yaml                          # → bentoml/build operator
├── schemas/                                 # Pydantic only — data shapes
│   ├── train_input.py
│   └── train_output.py
├── skills/
│   └── manual-finetune-trigger.md
├── policies/
│   └── require-approval-before-deploy.yaml
├── evals/
│   └── instruction-quality.jsonl
└── tests/
    └── test_pack_loads_and_composes.py      # ONE meta-test
```

Manifest declares operator deps (not Python deps):

```toml
[pack]
name = "finetune-llama-instruction"
version = "0.1.0"

[requires.operators]                          # new — mirrors §24.17 [requires.packs]
unsloth           = ">= 0.3, < 1.0"
hf-hub            = ">= 0.5"
bentoml           = ">= 0.2"
dataset-transform = ">= 0.1"
hf-eval           = ">= 0.2"
```

Operation binding (the escape hatch — declarative, not code):

```yaml
# operations/train.yaml
operator: unsloth/finetune                    # operator-pack-qualified name

inputs:
  base_model:        $state.base_model_ref
  dataset:           $state.prepared_dataset_ref
  max_seq_length:    2048
  lora_rank:         16
  lora_alpha:        32
  learning_rate:     2e-4
  num_epochs:        3

outputs:
  model_ref:  $state.trained_model_ref
  metrics:   $state.training_metrics

environment:
  resources: { gpu_count: 1, gpu_type: A100, memory_gb: 80 }
  secrets:   [HF_TOKEN, WANDB_API_KEY]
  timeout_min: 240
```

Template node referencing the operation:

```yaml
nodes:
  train:
    type: operation                           # new step type
    ref: train                                # → operations/train.yaml
    on_complete:
      success: evaluate
      failure: notify_failure
```

#### 24.19.4 What an operator pack looks like (where code legitimately lives)

```
obs-operator-unsloth/
├── pack.toml
├── pyproject.toml                           # declares unsloth, torch, trl
├── operators/
│   ├── finetune.py                          # class FinetuneOp(Operation)
│   └── inference.py                         # class InferenceOp(Operation)
├── schemas/
│   ├── finetune_input.py
│   └── finetune_output.py
├── images/
│   └── Dockerfile.unsloth                   # builds the runtime image
└── tests/
    ├── test_finetune_op.py                  # real unit + integration tests
    └── fixtures/
        └── tiny_dataset.jsonl
```

```python
# operators/finetune.py — the ONE place this kind of code lives
from cairn.core.operator import Operation, register_operator
from .schemas import FinetuneInput, FinetuneOutput

@register_operator(name="unsloth/finetune", version="0.3.1")
class FinetuneOp(Operation[FinetuneInput, FinetuneOutput]):
    input_schema  = FinetuneInput
    output_schema = FinetuneOutput
    image = "cairn/unsloth:0.5"
    resources = ResourceSpec(gpu_count=1, gpu_type="A100")

    def run(self, inp: FinetuneInput) -> FinetuneOutput:
        from unsloth import FastLanguageModel
        from trl import SFTTrainer
        # well-tested, well-versioned glue
        ...
        return FinetuneOutput(model_ref=..., metrics=...)
```

Domain experts maintain ~10–30 operator packs. Everyone else writes
domain packs in YAML.

#### 24.19.5 Binding-expression language (bounded, not Jinja)

The `inputs:` / `outputs:` blocks in operation bindings use a **small,
bounded expression language**, not Jinja (§24.11.1 rejects Jinja for the
same reasons here).

Grammar (complete):

| Form | Meaning |
|---|---|
| `$state.<dotted.path>` | Read from current graph state |
| `$<node_name>.<dotted.path>` | Read from a previous node's output |
| `$input.<dotted.path>` | Read from the template's input schema |
| Literal (string, number, bool, list, dict) | Inline value |

No conditionals, no loops, no function calls, no string concatenation.
If you need any of those, your binding is too complex and the logic
belongs in an operator. Doctor lints this.

#### 24.19.6 What we use upstream unchanged

| Need | Upstream |
|---|---|
| Class-shaped registry + entry-points discovery | Mirror existing `ExecutorRegistry` (`actions/executor.py`) + `pack/loader.py` entry-points loader. New group: `cairn.operators`. |
| External-job runtime (when `image:` is declared) | §24.14 **C1 External Job** primitive (#161). Operations with `image:` route through C1; without `image:` run inline in the orchestrator process. |
| Pydantic v2 for I/O schemas | Already standard; same path as §24.11 and template `output_schema` |
| Lockfile pinning operator pack versions | §24.17 `cairn.lock` — extend `[[pack]]` with operator kind, same shape |
| Visualization of operator nodes | §24.16 V2 renders `operation` steps as labeled nodes; operator pack name shown in tooltip |
| Test framework | `pytest` — operator packs use full pytest test suites; domain packs ship one meta-test ("pack loads + composes") |
| Existing `python_node` primitive | Kept for backward compat; doctor warns on new use ("consider declaring this as an operator") |

#### 24.19.8 Anti-patterns — rejected, do not propose

| Anti-pattern | Why rejected | Use instead |
|---|---|---|
| Let domain packs ship even a single `.py` file beyond Pydantic schemas | Soft boundary; will decay. Either packs can write code or they can't. Pick a side. | Write an operator pack. |
| Operators discoverable via Python imports from domain packs | Removes the boundary. Reference must be by registered name, not by import. | `operator: unsloth/finetune` — name resolution at load time |
| Jinja in operation bindings | Same §24.11.1 rejection — kills the data/code boundary and replay clarity | The bounded grammar in §24.19.5 |
| Operators with hooks (`pre_run`, `post_run`) | Hooks invite custom code in subclasses | Operators are simple `run(in)→out` callables; compose at template layer |
| Domain packs override operator behavior with monkey-patches | Kills the boundary | Configure inputs differently; or write a new operator |
| Templates importing operator Python directly | The whole point of named registration | Reference by name; fail loud if missing |
| Build a parallel registry/discovery system instead of mirroring `ExecutorRegistry` | Verified upstream: ExecutorRegistry shape works | Reuse the pattern |
| Per-pack Python virtualenvs for dep isolation | Overkill MVP; deps merge at install time via pip extras | Pip extras at install time; venv isolation only if conflicts emerge in practice |
| Make operators inherit from Pack | Different abstractions; operators are *units*, packs are *bundles* | Operators register inside operator packs; entry-points loader keeps the boundary |
| Skip the bounded binding-expression language and just use Python eval | Determinism + security disaster | The grammar in §24.19.5 |

#### 24.19.9 What this deprecates (slow path)

- `python_node` step type: kept for backward compat. Doctor emits a
  hint when a new template adds one: *"consider declaring this as an
  operator — `python_node` does not compose across packs."* Active
  packs (incident) are not forced to migrate; new packs are nudged.
- `code/tools/`, `code/capabilities/`, `code/executors/` inside the
  incident pack: existing structure stays. New domain packs follow the
  operator model. Incident pack is a "transitional pack" — older shape,
  still supported.

#### 24.19.11 Effort + placement

**Total: ~5–6 d substrate work.**

**Placement: P3.** Before any community-pack publish path. Reasons:
- Every multi-pack workload (not just fine-tune-ops) benefits — anything
  composing 3+ packs hits the "where does code live" question
- Incident pack stays on the older `code/tools/` model unchanged; this
  is additive for new packs, not a migration
- Unblocks future packs (fine-tune-ops, security-response, data-quality,
  etc.) without requiring §24.14 Tier 3 promotion
- Composes cleanly with §24.17 (in P4) — operator pack versions get
  pinned by the same lockfile mechanism

#### 24.19.12 What this section closes

- "How do packs ship code?" — answered: domain packs don't; operator
  packs do, by following the `Operation` protocol
- "How do multi-pack workloads compose code-heavy operations?" —
  answered: state passes through templates; operators are referenced by
  name; no cross-pack code imports
- The recurring temptation to add `code/scripts/` to every pack is
  permanently redirected to the operator-pack tier

**Note (superseded by §24.20).** §24.19.3 and §24.19.7 earlier showed
domain packs with `schemas/*.py` (Pydantic). The §24.20 Lock Spec
tightens this: domain packs ship **zero Python** — schemas live as
`schemas/*.schema.yaml` (JSON Schema 2020-12). Pydantic stays in
operator packs only. The architectural decision in §24.19 is unchanged;
the schema-format detail is overridden by §24.20.
