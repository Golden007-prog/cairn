# Runtime layering — Temporal for durable templates; DBOS as a batch-executor tier

## Context

ADR-0035 made `dbos` a third **runtime tier** that wraps the compiled LangGraph
graph: `OBS_RUNTIME=dbos` runs `run_template` as a DBOS workflow whose body is
`await graph.ainvoke(<entire template>)` (dev = SQLite, prod-single-box = Postgres).

Issue #41 was reproduced **locally** this session: a hard deadlock on that path for
any **parallel** template (e.g. dataset-readiness's fan-out of checks) run through
the real multi-loop server.

Root cause (confirmed): DBOS executes the `async` workflow via
`submit_coroutine(run_template())`, which routes onto the loop captured at
`DBOS.launch()` — uvicorn's serving loop (`BackgroundEventLoop.set_main_loop`,
`dbos/_event_loop.py`). A DBOS worker thread then blocks on
`run_coroutine_threadsafe(...).result()` against that same loop → a reentrant
single-loop deadlock. (Full trace + a failed isolation attempt are in #41.)

The deeper finding is architectural, not a bug: **wrapping a whole LangGraph graph
inside a DBOS workflow is a mismatch.** LangGraph is built for AI decision loops,
not as a heavy background-job / data-pipeline engine; DBOS is built for durable
background queues + parallel fan-out, not for hosting a foreign async graph on the
host event loop.

## Decision

Split by **workload shape**, not by a single "durability tier" enum:

1. **Heterogeneous governed templates** (dataset-readiness, incident RCA, …) — the
   compiled LangGraph graph runs **as-is**. Durable tier = **Temporal** (the
   `temporalio.contrib.langgraph` plugin is designed to run the graph durably — the
   proven path); dev/test = **in_process**. **DBOS does not wrap these graphs.**

2. **Data-parallel batch** (eval N items, batch inference, fine-tune sweeps) —
   **DBOS as a batch-executor tier**: a DBOS `Queue` owns chunk fan-out + fan-in to
   Postgres (`Queue.enqueue` / `DBOS.start_workflow` → `WorkflowHandle.get_result()`
   — note: `DBOS.gather` does **not** exist in DBOS 2.x). Each chunk calls a cairn
   operator that **may** use LangGraph *internally* for a per-item agent/judge loop.
   This lives on the **executor axis** — which ADR-0035 already declares orthogonal
   to the runtime tier — not on the runtime-tier axis.

Consequently `OBS_RUNTIME` narrows to **`{ in_process, temporal }`** for running
templates; `dbos` leaves the runtime-tier enum and becomes an executor/job tier.

## Consequences

- **#41 → won't-fix-by-design.** The deadlocking path (DBOS wrapping the graph) is
  removed, not patched. Root cause preserved in #41.
- **#34 / #35** (EC2 tests of `dbos`-as-runtime on SQLite / Postgres) → **superseded**;
  the durable-template path is Temporal (#36).
- DBOS's value (durable queues, crash-safe fan-out, Postgres transactions) is
  realised where it pays off — batch jobs — tracked by a new issue; ties to #7
  (remote_job executor), #8 (HP sweeps), #20 (batch inference), #70 (Axis-2 compute).
- Prefect / Argo / Windmill remain **executor-tier-only, demand-gated, never a
  runtime** (ADR-0023 §3.4/§24.22, #30) — unchanged.
- ADR-0035's tier matrix is amended: drop the two `dbos` rows from the
  *durable-template* matrix; keep in_process (dev/test) + temporal (prod/HA). The
  governance spine (cost/policy/redaction/audit/replay + HITL `interrupt()`) stays
  in the graph at the `invoke_operator` chokepoint, unchanged, for templates.

## Alternatives rejected

- **Fix the DBOS bridge** (sync `run_template`, isolate the loop, etc.) — even
  fixed, it re-homes the governance spine onto DBOS steps for no gain over Temporal,
  which already runs the graph durably. Parked in #41 for a possible future fresh
  look; not the path.
- **Prefect as the pipeline orchestrator** — rejected (ADR-0022, ADR-0023): a 4th
  engine + a server, weaker durability than Temporal, reopens a settled decision.

## Amendment 1 (2026-09-01) — the deadlock is gone; the decision stands on better grounds

This ADR's stated basis was #41: a hard deadlock when a **parallel** template ran
through the multi-loop server. That basis has expired. The decision has not.

### #41 no longer reproduces

Re-tested on **DBOS 2.31.0** (the repo pins `dbos>=2.0`; 2.23.0 was installed).
`incident/incident-rca` — two `type: parallel` waves, the exact shape that
deadlocked — completed under `OBS_RUNTIME=dbos`:

| path | result |
|---|---|
| CLI, in-process (baseline) | ok, 8.59s |
| CLI, DBOS + SQLite | ok, **7.24s** |
| uvicorn server, DBOS + SQLite | `queued → running → done`, ~12s |

DBOS recorded `workflow_uuid=run-incident--incident-rca-638517 status=SUCCESS
name=cairn.run_template`. Output parity with the in-process run was exact:
identical 20 output keys, identical finding counts, `root_cause` synthesized,
`cost` / `citations` / `resolved_operators` / `schema_hash` all present.
`tests/core/test_dbos_runtime.py` is 5 passed / 2 skipped (Postgres tiers, no
local PG), including gated resume, parallel gated resume, and crash recovery
with completed work preserved.

So "the deadlocking path is removed, not patched" is no longer why DBOS is not a
runtime tier. The reason is now the one the original text reached for
architecturally and could not yet demonstrate.

### What the re-test actually demonstrated (#1847)

Wrapping the graph works only because a **second** durability model is doing the
real work, and that model is off by default:

1. **The determinism contract is satisfied by composition, not by design.** DBOS
   requires non-deterministic work to sit in `@DBOS.step`; `run_template` calls
   `graph.ainvoke` — LLM calls, HTTP, DB — directly in the workflow body with no
   steps. It survives replay only because it asks the LangGraph checkpointer
   whether a thread exists and resumes from it. That is a deliberate, documented
   trade (steps would fight the checkpointer's node-skipping), and it is tested.
   It is also the whole of DBOS's contribution being routed around.
2. **`OBS_CHECKPOINTER` defaults to `memory`.** With the default, DBOS recovery
   re-seeds `initial_state` and replays the entire graph — every operator and LLM
   call charged twice — while still calling itself durable. `deploy_check` had a
   rule for exactly this footgun under Temporal and none for DBOS.
3. **Ungated graphs never resume at all.** A checkpointer is attached only to
   mark an approval gate, so most flows — `incident-rca` included — restart from
   zero on recovery.
4. **A gated run could not be approved.** DBOS pauses inside the workflow, so the
   dispatcher never set `awaiting_approval`; the run sat at `running`, and
   `POST /runs/{id}/resume` refuses anything not `awaiting_approval`. The gate
   fired, the checkpoint persisted, and no API could deliver the decision — it
   would have hung until the 24h `recv` timeout. Temporal fixed this same bug in
   #456; DBOS shipped the identical pause shape and never got it.

Points 2–4 are fixed (#1847). The point is not that they were unfixable — it is
that DBOS-as-runtime needed **three separate corrections** to be merely safe, and
delivered nothing in exchange that Temporal-running-the-graph does not already
provide via `temporalio.contrib.langgraph`. Point 1 is not a bug and is not
fixed: it is the shape mismatch this ADR named in 2026-06, now visible as a
concrete dependency on a second recovery model rather than as a prediction.

### Decision: unchanged

`OBS_RUNTIME` stays `{ in_process, temporal }` for running templates. DBOS
remains the **executor tier** — a `Queue` owning chunk fan-out where its
checkpointing is real, resume happens at chunk boundaries, and steps do not
compete with anything (batch inference #1676, eval sweeps, HP sweeps).

The `dbos` runtime code path still ships and is now fail-closed rather than
silently non-durable. That is deliberate: removing it would delete working,
tested code for a shape someone may yet have a use for. It is not recommended,
and `durable_runtime = "dbos"` in a profile does not even select it —
`profile_backends` does not rewire consumers, which is its own trap (#1847).

### What would reopen this

Not a DBOS version bump. The bar is a workload where DBOS wrapping the graph
beats Temporal running it, given `temporalio.contrib.langgraph` exists and is
installed — with the comparison written down before code moves. Nothing found in
this re-test comes close; the closest DBOS came was being 1.35s faster on one
mock-backend run.
