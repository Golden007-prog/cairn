### 24.14 Decision: platform primitives for governed long-running workflows

> **Provenance.** Derived from the June-2026 ModelOps Training Pack brief
> (fine-tuning, GPU allocation, budget governance, artifact lineage).
> The primitives below are *explicitly general* — the same set supports
> AIOps, ML inference observability, security forensics + remediation,
> data-pipeline orchestration, long-running infra automation, and a
> stronger incident-response saga. Validated against an 8-pack usage
> matrix (§24.14.3) before committing.

**Today's situation.** The §24.3 composition contract, §24.2 durable
execution (Restate + Temporal), §24.4 storage strategy, and §24.10 Bus
collectively give us a platform that handles short-bounded
LLM-driven workflows well. They do *not* yet handle the workflow
shapes the brief identifies as universal across many future packs:

  - **Hours-to-days external jobs** (training runs, infra provisioning,
    vulnerability scans, batch ML inference)
  - **Real-money budgets** with checkpoints and hard stops
  - **Artifacts with lineage** (model weights, datasets, postmortem
    docs, evidence chains, eval reports — every pack produces them)
  - **Approval as a first-class graph primitive** (today: embedded in
    the action saga; brief: standalone graph node)
  - **Compensation chains** spanning multiple workflow steps
  - **Sandboxed setup tasks** for safe, controlled, idempotent
    infrastructure-touching actions
  - **External metrics → workflow signals** so observability data can
    pause / branch / cancel running workflows
  - **A structured replay event taxonomy** so cross-pack analytics
    + dashboards + audit queries become possible

**Decision: codify ten core platform primitives (C1–C10) and prioritize
them by *universality across realistic future packs*, not by domain.**

#### 24.14.1 The ten primitives

| # | Primitive | Effort | What it gives |
|---|---|---|---|
| **C1** | **External Job primitive** (`type: external_job` graph node — submit / poll / heartbeat / cancel / timeout / resume / collect-artifacts) | ~5–7 d | Long-running async-job lifecycle as a first-class graph node. Training jobs, infra provisioning, vulnerability scans, batch inference. |
| **C2** | **Setup Task primitive** + sandboxed executors (`docker_run`, `kubernetes_job`, `shell_command` only in dev/sandbox) | ~3 d + ~5 d | Safe, controlled, idempotent infrastructure-touching actions. Brief's "never let LLM freely run shell" rule. |
| **C3** | **Budget Engine** — basic cost tracking (already partial via `cost_usd`) + checkpoints + projected overrun + hard stops + provider-specific cost models | ~1 d basic + ~5–6 d advanced | Cost governance across LLM + compute + storage + egress. Basic is universal; advanced features for heavy-compute domains. |
| **C4** | **Approval Gate as graph primitive** (`type: approval_gate` with `requiredWhen` conditional, role-based approvers, timeout-with-action) | ~2–3 d | First-class HITL gate at compile time, not embedded in the action saga. Composable with any graph. |
| **C5** | **Compensation Chain primitive** — multi-step ordered cleanup that runs on success / failure / cancel / timeout / crash | ~3–4 d | Generalized from Restate's per-action saga to arbitrary workflow level. Multi-resource transactions. |
| **C6** | **Artifact Lineage** — typed `ArtifactRecord` + lineage queries + storage abstraction | ~5–7 d | Every artifact (model, dataset, postmortem, eval report, evidence file) has a provenance chain. Cross-pack truth. |
| **C7** | **Object storage tier** (S3 / MinIO / R2 / GCS) — `ObjectStore` Protocol + adapter; extends §24.4 `StorageBackend` | ~3 d | Large-blob storage alongside Postgres + pgvector. Models, datasets, attachments, training checkpoints. |
| **C8** | **Structured Replay Event taxonomy** — typed event envelope + standard categories (`run.*`, `approval.*`, `budget.*`, `artifact.*`, `external_job.*`) + searchable index | ~2–3 d | Universal event hygiene. Cross-pack dashboards + analytics + audit queries become possible. |
| **C9** | **External metric → workflow signal bridge** — turn observability metrics into workflow signals (`budget_80pct`, `gpu_underutilized`, `error_rate_spike`) that pause / branch / cancel running workflows | ~3–4 d | Observability-aware workflows. ModelOps GPU pressure, AIOps drift detection, incident-response error spikes. |
| **C10** | **External Job → Bus emission** — durable jobs publish lifecycle events to the §24.10 Bus so subscribers (cost tracker, dashboards, audit log, downstream packs) can react | ~1–2 d | Ties C1 into §24.10. Universal subscribers benefit from any pack's job emissions. |

**Total: ~32–45 d** across C1–C10 (basic C3 only; advanced C3 is the
upper bound).

#### 24.14.2 Categorization by universality

Validated against an 8-pack matrix (§24.14.3). Tiered by "how many
realistic future packs *hard-require* this primitive":

**Tier 1 — Universal (~12–14 d).** Every realistic pack uses these.
Highest leverage per day. Build regardless of which domain packs ship next.

| # | Primitive | Why universal |
|---|---|---|
| **C8** | Event taxonomy | 8/8 packs emit events; standardized categories enable cross-pack analytics + audit + dashboards |
| **C6** | Artifact Lineage | 8/8 packs produce outputs worth tracking provenance for |
| **C4** | Approval Gate | 7/8 packs gate at least one state-changing action (postmortem is the read-only exception) |
| **C3-basic** | Cost tracking | 8/8 packs incur LLM cost; the `cost_usd` field already exists, formalize the engine surface |

**Tier 2 — Broad (~9–12 d).** Most action-taking packs benefit. Build
when 3+ packs need them — likely concurrent with P3/P4.

| # | Primitive | Why broad |
|---|---|---|
| **C7** | Object storage tier | 4/8 hard-need + 4 soft-benefit; pack-output size determines |
| **C1** + **C10** | External Job + Bus emission | 4/8 hard-need (any pack with async-job lifecycle); subscribers universal once Bus + C1 land |

**Tier 3 — Selective (~14–18 d, only the relevant pieces).** Build
alongside the specific pack work that needs them. Each piece is
~3–6 d of work — defer until the consuming pack is committed.

| # | Primitive | Triggering pack |
|---|---|---|
| **C2** | Setup Task + sandbox | ModelOps, security remediation, long-running infra |
| **C5** | Compensation Chain | Long-running infra (VPC + RDS), multi-resource state-changing packs |
| **C9** | Metric → signal bridge | ModelOps (GPU pressure), AIOps (drift), advanced incident response |
| **C3-advanced** | Budget engine hard-stop + projected overrun + provider cost models | ModelOps, long-running infra (real-money workflows) |

#### 24.14.4 What this does NOT include (intentionally pack-level)

The ModelOps brief was deliberately mined for *general* primitives.
The following are pack-level domain content and belong in the
ModelOps pack when that pack is committed — not in the platform
roadmap:

- 16 ModelOps schemas (`FineTuneRequest`, `TrainingJob`,
  `GpuMetricSummary`, `ComputePlan`, `DatasetAuditReport`, etc.)
- 16 ModelOps templates (`fine-tune-readiness`, `dataset-audit`,
  `training-runner`, `cost-report`, etc.)
- 30 ModelOps-specific replay event types (`training.checkpoint.saved`,
  `dataset.audit.completed`, etc.) — these *use* C8's typed envelope
- All MCP integrations (RunPod, Modal, Hugging Face, Unsloth, PEFT,
  TRL, Axolotl, MLflow, W&B, Presidio, TruffleHog, Promptfoo,
  DeepEval) — these are the §24.13 pattern, one integration per
  customer demand
- GPU-specific metric collection + workflow signals (uses C9 bridge
  but the *semantics* of `gpu_underutilized` etc. are ModelOps)
- Prometheus + Grafana as required deployment components (ClickStack
  OTLP covers MVP; Prometheus is a deployment choice)
- MLflow / W&B as required experiment trackers (one valid choice among
  many; pack-level)
- Bifrost as required MCP gateway (per §24.13 staged plan; direct MCP
  for MVP)
- ClickHouse as required separate analytics tier (Postgres covers MVP)

This is the same separation §24.13 makes for integrations: the platform
ships seams; packs ship domain content + provider choice.

#### 24.14.5 Mapping to existing phased plan (§24.6)

The C-features distribute across existing phases without creating a new
phase. Total roadmap grows by **~21–26 d** (Tier 1 + Tier 2 baseline).
Tier 3 only when the consuming pack is committed.

| Phase | Existing scope | C-features added | Phase effort delta |
|---|---|---|---|
| **P3** | §24.2 additive Temporal + Bus Tier 1 + template lifecycle + MCP integration | **+C4 (~2–3d), +C8 (~2–3d), +C3-basic (~1d)** — Tier 1 primitives ride alongside Temporal handler work since they share the durable-execution seam | **+5–7 d** (P3: ~13.5d → ~19d) |
| **P4** | §24.4 Storage Phase 1 + few-shot library + MCP catalog | **+C6 (~5–7d), +C7 (~3d), +C1 + C10 (~6–9d)** — artifact lineage + object storage ride alongside storage Phase 1; External Job lives next to §24.10 Bus | **+14–19 d** (P4: ~6.5d → ~22d) |
| **P5 onward** | Storage Phase 2 + Bus Tier 2 + suggestion engine | Unchanged | — |
| **(Tier 3, deferred)** | When ModelOps / security / infra packs commit | C2 (~3d + 5d sandbox), C5 (~3–4d), C9 (~3–4d), C3-advanced (~5–6d) | ~14–18 d only when triggered |

**Revised totals**:

- **Total platform roadmap (Tier 1 + Tier 2)**: **~67–72 d** (was ~46d)
- **Total with all Tier 3 platform work**: **~81–90 d**
- **All ModelOps pack content (deferred)**: ~35–50 d separate effort
  when that pack is committed (see §24.14.4)

#### 24.14.6 What good looks like after Tier 1 + Tier 2 land

- Any pack can produce an artifact and the platform knows its lineage
  end-to-end (C6 + C7).
- Any pack's events show up in the same cross-pack analytics query
  with a standard taxonomy (C8).
- Any pack can gate a state-changing action with `type: approval_gate`
  at compile time, without embedding HITL in the action saga (C4).
- Any pack incurs cost and the platform tracks it (C3-basic) — full
  budget engine arrives when ModelOps / infra packs demand it.
- Any pack can spawn a long-running job, monitor it durably, cancel
  it from a workflow signal, and downstream subscribers see the
  lifecycle on the Bus (C1 + C10).

That's the "platform is ready for ModelOps, AIOps, security, infra,
data-pipeline use cases" milestone. The pack content for each domain
is the next investment, gated by real customer demand.

#### 24.14.7 What we deliberately reject from the brief

Same shape as the §24.2 anti-patterns table — call out what we will NOT
build, so future drift doesn't bring them back:

| Rejected feature | Why |
|---|---|
| **Prometheus + Grafana as required built-ins** | ClickStack OTLP covers MVP. Deployment choice, not platform. |
| **MLflow as required experiment tracker** | One choice among many. Pack-level. |
| **Bifrost as required built-in** | §24.13 staged plan: direct MCP for MVP, gateway adoption at Stage 2 with a fresh decision. |
| **ClickHouse as required analytics tier** | Postgres + ClickStack cover MVP. Add real ClickHouse tables only when Postgres queries hurt. |
| **Distributed training / FSDP / DeepSpeed / Ray / FullFT** | Pack-level, ModelOps-domain. Brief already defers these. |
| **Autonomous deployment** | Violates §24.12 (improvement loop is suggested-changes, not autonomous). |
| **A separate analytics-only data store from operational store** | Premature optimization. Single Postgres until the query mix breaks it. |

Future "should we add X" questions get the §24.14.3 matrix as the
test: if X doesn't have ≥3/8 hard-need votes against realistic packs,
X belongs at pack level.
