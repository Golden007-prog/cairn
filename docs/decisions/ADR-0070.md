# ADR-0070 — Config scoping & ownership: governance vs operational, layered across env / workflow / run

Status: Proposed (2026-07-13)
Extends: ADR-0068 (operator config surface — the `config_schema` contract,
`[profile.config]`, precedence, doctor + run-submit preflight).
Relates to: ADR-0053 (policy scoping — the environment is the wiring hub;
config-locks compose with it), the workflow/bundle model (ADR-0069), and the
console Environments/Workflows surfaces.

## Context

ADR-0068 gave every tunable knob one home: `[profile.config."<op>"]`, keyed by
operator, scoped to an **environment**. That is correct for *some* knobs and wrong
for others, because it treats config as monolithic. Two problems:

1. **Config is not one kind of thing.** A gate's `format_min_conformant_pct` /
   `max_usd` / `max_eval_loss` is a **governance** decision — the whole point of
   the gate. A `sample_size` / `batch_size` / judge `model` / `serve.gpu_memory_
   utilization` is **operational** tuning. If a run or a workflow can *lower* a
   gate threshold, the gate is theater; but forcing operational tuning to be set
   environment-wide is clumsy.
2. **Users think in workflows, not operators-across-an-environment.** Setting
   `[profile.config."dataset/gate"]` in a profile changes that gate for **every**
   workflow in the environment. An author who wants "the finetune workflow tuned
   like *this*" has no place to say it, and no single screen that shows all the
   knobs their workflow actually exposes.

The user's question (verbatim intent): *"we also need a way for the user to set
these config parameters. Should it happen in profile/env? Or a custom config per
workflow, composed from all its operators? Think carefully."*

## Decision

**Config has a `scope` (governance | operational). Scope decides the owner and
the layer; the layers compose as a precedence stack. A per-workflow config is a
*composed view* over the workflow's reachable operators, not a competitor to the
profile.**

### 1. Every knob is tagged `governance` or `operational`

A `config_schema` field carries `json_schema_extra={"scope": "governance"}` (or
`"operational"`, the default). One marker, read by the resolver and every UI:

```python
max_usd: float = Field(0.0, json_schema_extra={"scope": "governance"})     # gate → env, lockable
sample_size: int = Field(1000, json_schema_extra={"scope": "operational"}) # tuning → workflow/run
```

Unmarked ⇒ operational (existing knobs stay freely tunable; guardrails opt into
governance explicitly). The three training-pipeline gates' thresholds are tagged
**governance**.

### 2. Three layers, three owners

| Layer | Owner | Holds | Where it lives |
|---|---|---|---|
| **Environment** | platform / governance | **governance** knobs (lockable) + env-wide operational defaults | `[profile.config]` (ADR-0068) |
| **Workflow** | workflow author | **operational** knobs, composed from the workflow's reachable operators | a stored `WorkflowConfig` (named, selectable) |
| **Run** | the person launching | ad-hoc **operational** overrides | `config_overrides` (ADR-0068) |

### 3. Precedence — split by scope (this is the governance guarantee)

- **Operational** knobs: `run > workflow > env > operator default` (most-specific
  context wins). Freely set at any layer.
- **Governance** knobs: **environment only**. A workflow or run that tries to set a
  governance knob is **rejected by the run-submit preflight** (#744). They render
  **read-only** in the workflow/run forms ("format floor: 99% — set by env: prod").
  A gate can therefore never be *weakened* below the environment's value by a
  workflow or a run — the guarantee the whole config-gating epic exists to make.
  *(Per-workflow **tightening** of a governance knob — a stricter-than-env floor —
  is a deliberate future extension via a monotonic merge; v1 is env-only for
  simplicity + safety.)*

### 4. The per-workflow config = a composed view + a stored object

Not new storage fighting the profile — a **projection** plus a named object:

- **Composition**: resolve the workflow's **reachable operators** (walk the
  template's behavior tree + `subgraph_node` children → each `OperationBTNode`'s
  operator; the same reachability the preflight/Guardrails form need), **union
  their `config_schema`s** into one surface, grouped by operator/stage, each field
  carrying its `scope`. The author opens `finetune-remote` and sees **one**
  Configuration screen spanning dataset-gate → cost-gate → train → model-gate →
  serve — operational knobs editable, governance knobs read-only (env-owned).
- **Storage**: a named, versioned **`WorkflowConfig`** (a `WorkflowConfigStore`,
  memory/sqlite/postgres, mirroring the runs/pipelines stores). Attach as the
  workflow's default, or select one at run time (like choosing a preset). Only
  the **operational** deltas persist; governance is always resolved from env.
- **Resolution**: at run submit, the selected `WorkflowConfig`'s operational
  values enter the precedence stack (below run override, above env operational
  default); governance values come from env regardless.

### 5. Discovery / authoring surfaces (all from the composed schema)

- `cairn config workflow <template>` — print the composed surface, grouped by
  operator, governance vs operational, with defaults.
- Console **Workflow → Configuration** tab — the composed form (the Guardrails
  form scoped to one workflow), governance fields read-only.
- The environment **Guardrails** form (ADR-0068) keeps owning governance knobs.

## Consequences

- **The gate stays a gate.** Governance knobs are env-only + preflight-enforced +
  (with the ADR-0053 lock) non-weakenable — a workflow/run can never lower a
  guardrail. Operational tuning is convenient exactly where the user wants it.
- **One question answered per knob, not globally.** "Can this be set per run?" is
  now answered by the knob's `scope`, declared once by the operator author.
- **Reuses reachability + the composed-form renderer.** The workflow config form
  is the Guardrails form scoped to a template; no new UI paradigm.
- **Back-compat.** Unmarked knobs are operational; no `WorkflowConfig` selected ⇒
  today's behavior byte-for-byte. Governance tagging changes nothing until a
  workflow/run *tries* to set a governance knob (then it's correctly rejected).
- **Storage add.** A `WorkflowConfigStore` (like the pipelines store, ADR-0069) —
  a named-config CRUD, not a change to the run/profile model.

## Alternatives considered

- **Everything in the profile (ADR-0068 as-is).** Can't express per-workflow
  presets; forces operational tuning env-wide; no single per-workflow surface.
  Rejected — it's the gap this ADR fills.
- **Everything per-workflow/per-run.** Lets a run weaken a gate → governance
  theater. Rejected outright.
- **Bake per-workflow config into the pack/template (data).** That's *pack
  defaults*, not user-owned deployment config; not editable per deployment without
  forking the pack. Kept as the operator/template default layer only.
- **A fourth "tighten-only" governance merge for workflows now.** Useful but adds
  a monotonic-merge concept; deferred — v1 governance is env-only.

## Build order (multi-slice)

1. **Scope tagging + partition helper** + tag the 3 training gates (foundation).
2. **Composed workflow config** — reachability → union → `cairn config workflow`.
3. **`WorkflowConfig` store + run-time selection** + precedence wiring.
4. **Preflight rejects governance-at-workflow/run**; env **lock** (ties ADR-0053).
5. **Console** — Workflow Configuration tab + run-form operational overrides.
