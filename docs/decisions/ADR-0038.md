# Long-running job control loop — operator-runner + bidirectional channel

## Context

cairn's governance model is the `invoke_operator` chokepoint: every operation
passes through it, the bounded `OperationContext` (§24.20.13) keeps replay
honest, and policy / redaction / audit / HITL / cost apply per operation.

A **remote GPU training job** (RunPod/Vast/AWS/Kube/Modal, #121–#124) breaks that
model: it is a **black box** to cairn — `submit → poll → adapter URI`. Nothing
that happens inside the container passes through `invoke_operator`:

- **checkpointing** the model/optimizer/adapter to S3 (for spot/preemption resume),
- **mid-training eval** every N steps (steer / early-stop / decide promotion),
- **per-step metrics** (loss, lr, throughput, GPU util),
- and any **control decision** we'd want to make from them (abort on regression,
  pause for a human to approve promoting a checkpoint, stop on budget).

The naive fix — model each of those as its own cairn operator — is **wrong and
already forbidden**:

- `OperationContext` explicitly **locks out "spawning other operators"** — operators
  do not compose at runtime.
- These concerns share the **model in GPU memory**, the optimizer state, and the
  step counter. They are **trainer callbacks** (HF `TrainerCallback`: `on_save` /
  `on_evaluate` / `on_log`), not graph nodes that pass data through state.

So the real question is not "how many operators" but: **how does cairn observe
and control work that runs inside a single long-running, remote operator?**

cairn already half-answered this. `OperationContext` ships two no-op primitives
designed exactly for it, with docstrings naming the future home:

- `emit_heartbeat(status)` — *"the external-execution runtime (operator-runner,
  #197) overrides this to call the Temporal heartbeat API."* → **events up**.
- `check_cancelled()` — *"…overrides to consult the Temporal cancel API."* →
  **control down**.

## Decision

A long-running operator stays **one coarse node** (no decomposition), but opens a
**bidirectional control channel** to cairn — *events flow up, control flows down* —
via the **operator-runner** pattern. This dissolves the black-box boundary without
violating "operators don't compose."

Three parts:

1. **In-job: trainer callbacks → a local operator-runner agent.** cairn ships a
   small **operator-runner agent** inside the training image. The trainer's
   callbacks never talk to cairn directly — they talk to the local agent
   (`agent.emit(event)`, `decision = agent.gate(payload)`), which owns the cairn
   channel (transport, retries, OTLP export, auth). Keeps training code clean and
   the cairn plumbing in one place.

2. **Channel: events-up / control-down, per run.** Two logical streams keyed by
   `run_id`: `train.{run_id}.events` (job → cairn) and `train.{run_id}.control`
   (cairn → job). Substrate is one of cairn's existing durable mechanisms
   (see *Substrate*).

3. **Cairn-side: a separate, generic job-control worker — NOT a graph node.** The
   controller is **execution machinery**, not workflow logic: a standalone cairn
   worker (a sibling to the scheduler / dispatcher), **generic across any remote
   job, any run, any provider.** It consumes the event streams of *all* in-flight
   jobs, applies governance (eval gate, budget, policy, HITL), issues control, and
   **resumes the paused run** on a terminal state or a gate decision.

   The workflow graph only declares *"run on remote compute"*: the operator node
   **submits** the job (records a `JobHandle` + control policy) and the run then
   **pauses — exactly like a HITL `interrupt()`** (it does not hold a node
   "running" for the hours of training). The control worker resumes it. So one
   worker drives every remote-job operator; nothing is baked into a specific
   workflow.

   On **Temporal** this worker is realized as a worker running a long heartbeating
   activity (the durable idiom) — conceptually still separate machinery, not graph
   logic. This is the "small worker that controls the job."

### Provisioning / handoff — operator and worker decoupled by a durable store

The operator never holds a reference to the control worker; they are wired only
through a durable **remote-job registry** — the same shape as the trigger inbox
(#115), mirrored for *outbound* jobs:

1. **`submit()` registers the job.** The remote-job operator writes a
   `RemoteJobRecord` to the **`RemoteJobStore`** (sqlite default / postgres / NATS —
   the inbox's tiering): `{run_id, node_name, provider, job_handle, compute_target,
   control_policy, channel_subjects, status: submitted}`, then the run **pauses**
   (`interrupt()`). The operator is done; it does not know the worker exists.
2. **The control worker claims + drives.** A claim/drain loop (the shape of
   `run_drain_loop`) claims `submitted`/`running` records, attaches by `job_handle`
   (re-poll, never re-dispatch → crash-safe), drives the event/control channel,
   applies gates/budget/HITL, and on a terminal state calls
   **`RunDispatcher.resume_run(run_id, result)`** — the *same* path that resumes a
   HITL-paused run, now resuming with the job result instead of an approval.

So the handoff is **enqueue (operator) → discover (worker) → resume (worker)** —
symmetric with inbound triggers, reusing the inbox + resume machinery. The worker
is generic: one instance drives every remote job across all runs/providers.

**Worker deployment:** single-box = a server lifespan task (sibling to the inbox
drain + schedulers); scale = a standalone `cairn-job-controller` claiming from a
shared postgres/NATS store; Temporal = a worker running a heartbeating activity
per job.

### The API (extends the bounded context — does not widen graph access)

- `ctx.emit_heartbeat(event)` — **events up**: `step`, `checkpoint_written{uri}`,
  `eval_completed{metrics}`, `heartbeat`, `finished{adapter_uri}`, `failed{error}`.
  Recorded by cairn as run events + OTel spans + cost — *observability into the loop*.
- `ctx.check_cancelled() -> bool` — **coarse control down**: cairn aborts (signal /
  budget breach / eval regression).
- `ctx.gate(payload) -> Decision` *(new)* — **governance control down**: the loop
  **blocks** at a decision point (e.g. after a mid-train eval) until cairn returns
  `continue | abort | promote`. This is a real in-loop gate (the #125 eval gate, run
  *during* training; or a HITL "promote this checkpoint").

These remain deployment-resolved, bounded primitives — they do **not** grant the
operator graph-state access; they only open a channel to the run's controller.

### Two deployment models (pick by control depth)

- **Model A — worker-side controller (lean; observe + abort).** The poll loop runs
  on a cairn worker under Temporal; it launches the GPU job, reads its events,
  `emit_heartbeat`s to Temporal, and can `cancel` the provider job. The container
  stays dumb (trains; writes checkpoints→S3, metrics→OTLP). No in-container agent.
  *Limit:* control is "abort," not "block-for-approval" (the container isn't waiting).
- **Model B — in-container agent (full L3).** The operator-runner agent in the image
  lets the loop **block on `gate()`** — true mid-train eval gate / HITL checkpoint
  promotion. More powerful, more moving parts.

### Levels (incremental)

| Level | Capability | Model |
|---|---|---|
| L0 | black box (`submit→poll→URI`) — today | — |
| **L1 Observe** | checkpoints/eval/metrics → run events + OTel + cost | A |
| **L2 Control-coarse** | abort on signal / budget / eval-regression | A |
| **L3 Govern-loop** | block for mid-train eval-gate / HITL checkpoint-promote | B |

### Substrate

- **Events channel:** **NATS JetStream** (cairn already runs it for the durable
  trigger inbox, #115) — durable, at-least-once, replayable. The simple fallback is
  S3/HTTP polling (no broker) for L1/L2.
- **Durable controller / coarse control:** **Temporal** (cairn's durable runtime,
  ADR-0036) — the poll is a heartbeating activity; the workflow receives **signals**
  (abort/approve) and crash-resumes by re-attaching to the `JobHandle`.
- **`gate()` (L3):** a request/reply over the control channel, backed by a cairn
  governance gate (deterministic eval thresholds and/or HITL via the existing
  approval machinery, ADR-0034).

### Governance boundary (what this does and does NOT do)

cairn governs the **edges** (input-data gate, output-model gate #125, promote HITL,
artifact provenance, audit of submit+result) **plus** — via this channel —
**selected in-loop decision points** (a mid-train eval gate, a checkpoint-promotion
gate). It does **not** route every training step through the graph (no graph-state
per step, no per-step `invoke_operator`). The channel carries **events + a few gate
points**, not the whole loop. That is the intended, replay-honest boundary.

### Two checkpointers — do not conflate

- **LangGraph checkpointer** (`runtime/checkpointer.py`) — resumes the *workflow*
  (which node / what state) across crashes + HITL. Not model weights.
- **Trainer checkpointer** — writes model/optimizer/adapter to **S3** inside the
  container so a preempted GPU job resumes from the last step. cairn's role: the
  `JobHandle` resume (re-poll, never re-dispatch) + the S3 artifact store. A trainer
  callback, **not** an operator.

## Consequences

**Positive**
- In-loop **observability, audit, cost, and control** without decomposing operators
  or widening the bounded context.
- Reuses what cairn already has: `emit_heartbeat`/`check_cancelled` + operator-runner
  (#197) + NATS JetStream + Temporal signals/heartbeat + the approval machinery.
- Incremental: L1 (observe) is cheap and high-value; L3 is opt-in for high-governance
  training.

**Negative / costs**
- **L3 adds latency** (the loop blocks for a decision) and a **control-decision
  durability** requirement (the reply must survive a controller restart).
- **Model B adds an in-container agent dependency** (shipped in the image) and
  requires the container to reach the channel (network egress / broker creds).
- The per-run channel is **ephemeral plumbing** to provision + tear down per job.

## Alternatives considered

- **Decompose into operators (checkpoint/eval/log as nodes).** Rejected — operators
  can't spawn operators; the concerns share GPU memory + the step loop; nothing to
  pass through state.
- **Govern the edges only (the prior stance).** Rejected as too conservative — it
  forecloses mid-train control (stop-on-regression, HITL checkpoint promotion), which
  is a core governance value for expensive fine-tuning.
- **Job-as-Temporal-worker.** Rejected — a one-shot GPU container is not a Temporal
  worker; Temporal lives on the cairn side as the controller.
- **HTTP callback + control-poll / S3 polling.** Accepted as the **L1/L2 fallback**
  when a broker isn't available; JetStream is the durable default.

## Slice plan

1. **L1 — Observe.** Wire `emit_heartbeat` → run events + OTel (folds into the
   remote-job observability issue + ADR-0036/#79); training callbacks emit
   `checkpoint/eval/metric` events; the controller records them. Model A.
2. **L2 — Coarse control.** Temporal-signal abort + budget/eval-regression abort via
   `check_cancelled`; provider `cancel`. Model A.
3. **L3 — In-loop gate.** The operator-runner agent in the image + `ctx.gate()` +
   the request/reply control channel; the #125 eval gate runs mid-training; HITL
   checkpoint promotion. Model B.
