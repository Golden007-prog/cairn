### 24.16 Decision: read-only graph visualization for developer mental model

> **Provenance.** Surfaced June 2026 by the developer-experience
> question: "it's hard to build a mental model of how a workflow
> composes across multiple templates and packs." Particularly acute
> for workflows that involve `subgraph_node` references to other
> templates, which in turn may have their own subgraphs.

**Status before:** A developer reading a multi-template workflow has
to read YAML / Markdown frontmatter and trace `subgraph_node`
references manually. There's no rendered view of:

  - The compiled graph of a single template (LangGraph could render
    this, but we don't expose it on the CLI today).
  - The **flattened cross-template composition** when one template's
    `subgraph_node` points at another template that has its own
    subgraphs (recursive walk).
  - The **pack composition** — what a pack provides / requires and
    where each requirement resolves (doctor's `[packs]` category
    shows status text, but no graph).
  - The **end-to-end execution shape** — trigger → skill → template
    → capabilities → providers — from a single starting point.

LangGraph's `.draw_mermaid()` / `.draw_png()`, LangGraph Studio,
LangSmith, Restate UI, Temporal UI, and `cairn replay` collectively
cover rendering, live-execution traces, and per-run trace inspection —
but none of them cover the **cross-template / cross-pack composition
view** because that's specific to our architecture, not theirs.

**Decision: build a thin read-only CLI visualization command that
composes LangGraph's native rendering with our pack registry +
subgraph resolver. Defer richer interactive viewers to upstream tools
(LangGraph Studio, LangSmith). Do NOT build a custom web UI.**

#### 24.16.1 What we use upstream, unchanged

| Tool | What it covers | Status |
|---|---|---|
| LangGraph `.draw_mermaid()` / `.draw_png()` | Single-graph rendering primitive | Free — we use as the renderer underneath the CLI |
| LangGraph Studio | Interactive desktop visualizer + debugger | Verify it works with our compiled templates (~1 hr); document as the interactive option if yes |
| LangSmith | Live execution trace visualization | Existing recommended option for production trace inspection |
| Restate UI / Temporal UI | Workflow/saga execution state | Already in our reference stack; no change |
| `cairn replay <run-id>` | Per-run JSONL trace inspection | Already shipped |

The gap is *not* rendering — it's exposing the composition story for our
specific architecture. The CLI below fills that.

#### 24.16.2 The CLI command

```bash
# Single template — uses LangGraph's draw_mermaid() directly
cairn visualize template <name>
  → Mermaid to stdout (or --output file.md)

# Flattened cross-template composition — walks subgraph_node refs
# recursively and inlines the children into one diagram
cairn visualize template <name> --flatten

# Pack composition view — provides/requires + where each requirement
# resolves (uses our §24.3 contribution registry + composition report)
cairn visualize pack <name>

# End-to-end trigger view — what executes when this skill fires
cairn visualize skill <name> --depth=full
```

Output is **Mermaid text by default**, with optional `--output`
(`.md`, `.svg` via `mermaid-cli`, `.png` via LangGraph). Mermaid is
rendered inline by GitHub, GitLab, Notion, Slack message previews,
Obsidian, and most modern markdown tools — engineers paste output
into PR descriptions, design docs, chat without any installer.

#### 24.16.3 What we build vs reuse

| Piece | Source |
|---|---|
| Graph-to-Mermaid renderer | **LangGraph** `.get_graph().draw_mermaid()` |
| Compiled `StateGraph` for each template | **Existing** compiler output |
| Subgraph resolution registry | **Existing** §24.3 (P2.e cross-pack template refs) |
| Pack composition registry | **Existing** §24.3 contribution registry + composition report |
| Recursive subgraph walker | **New** — small helper (~50 LoC) that walks `subgraph_node` refs and merges sub-graphs |
| CLI command + Typer subcommands | **New** — adds `visualize` to `cairn/cli/main.py` |

**Effort: ~1–2 d.** LangGraph does the rendering; we provide the
composition walker + CLI wiring. The ~50 LoC subgraph walker is the
only real new code.

#### 24.16.4 LangGraph Studio fit-check (~1 hr)

Before the CLI build, verify LangGraph Studio works against our
compiled templates:

1. Add a `langgraph.json` project config pointing at our compiled
   graphs.
2. Open Studio; confirm at least one of our templates renders correctly
   and can be stepped through.

If yes → document Studio as the **recommended interactive option** for
deep debugging; the CLI handles share-able / paste-able Mermaid output.
If no → document the limitation; CLI remains the primary tool.

#### 24.16.5 What we explicitly REJECT

| Rejected | Why |
|---|---|
| Build our own renderer engine | LangGraph + Mermaid + Graphviz cover rendering. Don't reinvent. |
| Custom web UI for graph viewing | LangGraph Studio + LangSmith already do this. Verify fit before building. |
| Add visualization to `cairn doctor` | Wrong place — doctor is preflight, visualize is its own verb. |
| Replace `cairn replay` with a UI | Different need (per-run trace inspection ≠ understand the graph structure). Keep both. |
| Heavy interactive features (live edit, hot-reload) | Not the goal. Read-only is the entire decision. Authoring lives in YAML + Markdown. |

#### 24.16.6 Effort + placement

- ~1 hr — LangGraph Studio fit-check
- ~1–2 d — `cairn visualize` CLI command (single + flatten + pack + skill modes)
- ~½ d — docs: when to use Mermaid CLI vs Studio vs LangSmith vs `replay`

**Total: ~2–3 d.** Lands post-demo (not in D-task budget). Natural fit
for late P3 or early P4 once the substrate work stabilizes.

What good looks like: a developer joins the team, runs
`cairn visualize skill db-pool-exhaustion --depth=full`, gets a
Mermaid diagram of trigger → skill → template (with subgraphs inlined)
→ capabilities → resolved providers, and understands in 30 seconds
what the workflow actually does. No code reading required.
