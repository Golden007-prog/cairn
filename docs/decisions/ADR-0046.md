# ADR-0046 — Stateful infra capabilities (memory · RAG · storage) as enable-a-backend

Status: Proposed (2026-06-29)
Relates to: ADR-0026 (locked architecture — declarative composition + the `invoke_operator` chokepoint), ADR-0020 (pack contract), ADR-0042 (operator granularity — one verb per operator, breadth behind `invoke_operator`, no new kinds), ADR-0023 (profile-owned RAG build config), ADR-0033 (credentials are references, never values), #68/#70 (two-axis connections: access / compute), #50 (Bus Protocol — outbound KV), #218 (unified Library surface).

## Context

Packs increasingly need **stateful backends** — a vector store (RAG), an episodic memory store, a relational / object / kv store. The pieces already exist, but the seam is in the wrong place:

- The capability **verbs** exist: `rag.search` / `rag.fetch` / `rag.embeddings`, `memory.write` / `memory.search` / `memory.store`, `store.*`, `storage.put` / `storage.get`.
- The backend **impls** exist behind store abstractions: `cairn/services/rag/stores/{base,pgvector,sqlite_vec}.py` and `cairn/core/storage/{episodic.py, postgres/, memory/}`.
- But the backend is selected by **profile config** (ADR-0023), invisible to the user. A pack that "needs RAG" is implicitly tied to whatever the profile happened to wire, there is no first-class *"enable Qdrant for this deployment and let any pack that needs vector search use it,"* and swapping a backend means editing config the pack author never sees.

The pressure surfaced in the console IA work (#218): a user wants to **enable a backend once at the deployment level** — Postgres / Qdrant / pgvector / S3 / Redis — and have packs that *declare* a storage/memory/RAG need draw from it, without each pack hard-coding a backend, and without a swap forcing pack edits.

## Decision

Model memory / RAG / storage as **stateful infra capabilities**: a small canonical class of capabilities satisfied by **user-enabled backends**, bound per environment. No new executor kind; no fat "infra operator" (ADR-0042 holds).

1. **A canonical infra-capability vocabulary.** A fixed set the platform recognises as backend-backed — `vector.search` / `vector.upsert`, `memory.read` / `memory.write`, `relational`, `object.put` / `object.get`, `kv.get` / `kv.set`. This ADR **classifies** the existing `rag.*` / `memory.*` / `store.*` verbs into that class; it does not rename them.

2. **Packs declare an *abstract* need, never a backend.** `requires = ["vector.search", "memory"]` in the manifest — the capability-level `requires` layer (today empty; CI-enriched by the cairn-loader). A pack never names Qdrant vs pgvector.

3. **A backend is enabled as a connection, behind the existing store abstraction.** Postgres / Qdrant / pgvector / S3 / Redis = a connection (creds as references, ADR-0033) resolved into `ctx` at dispatch — the same mechanism as `compute.*` / `mcp` / `tracking.*`. The backend impl sits behind `stores/base.py` (pgvector + sqlite-vec already do; Qdrant / Redis would be new **impls behind the same base**, not new operators and not a new executor).

4. **The environment binds capability → (thin operator + backend connection).** The same binding layer that maps capability → operator + policy + executor today. Swapping Qdrant → pgvector is a **rebind, zero pack changes**; different environments → different backends for the same workflow.

5. **The console surfaces it, does not own it.** The Library *Capabilities* lens (#218) marks the infra capabilities and shows their backing state (*backed by Qdrant* / *no backend — enable one*); the enable + bind actions live in Connectors / Environments.

## What this is NOT

- **Not** a new executor axis — the 7-value executor enum (ADR-0042 §4) is untouched.
- **Not** a fat infra operator — breadth stays behind `invoke_operator` via executor + connection.
- **Not** a rebuild of the stores — pgvector / sqlite-vec / episodic / postgres exist; new backends are impls behind `base.py`.
- **Not** control flow or a message bus — KV stays the Bus Protocol's outbound concern (#50), not a graph dependency.

## Consequences

- Packs become **backend-agnostic**; capability swapping is a binding concern, not a code edit.
- The genuinely new work per backend = one store impl behind `base.py` (e.g. Qdrant) + a connection. This gives the abstract-`requires` enrichment its **first real consumer**.
- The Library Capabilities lens is designed with a backed-by / enable column from the start, even while this ADR is unbuilt (the column reads "provided by ⟨pack⟩" until infra capabilities ship).

## Open questions (resolve before Accepted)

- **Connection-kind namespace.** Do backends get a `store.*` connection-kind namespace (precedent: `compute.*`, `tracking.*`), or do they reuse a generic connection + a profile-level backend selector? ADR-0042 forbids new *executor* kinds and new *axes*; a namespaced connection kind is consistent with precedent but should be confirmed, not assumed.
- **Vocabulary reconciliation.** `rag.search` vs `vector.search`, `storage.*` vs `object.*` — pick one set and alias the rest, so packs and the binding layer agree.
- **`relational` surface.** Does it expose raw SQL or only governed verbs? Raw SQL is an ungoverned escape hatch and likely belongs behind the MCP-bridge pattern, not a first-class infra capability.
- **Defaults / dev fallback.** sqlite-vec / sqlite / in-memory as the zero-config default so packs run hermetically before any backend is enabled (mirrors the "deterministic fallback" rule for optional deps).
