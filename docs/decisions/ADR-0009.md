### 24.9 What this section closes

After P1–P6, the engine has:

- **Complete CLI**: doctor / ls / validate / run / replay / init / eval.
- **One workflow engine**: Temporal (or in-process for dev/test).
- **One storage tier per environment**: SQLite+sqlite-vec (dev) /
  Postgres+pgvector (prod), with the eight stores all behind one
  `StorageBackend`.
- **Formal pack composition**: manifest-declared deps, version
  enforcement, soft capability namespacing, doctor visibility.
- **One async messaging mechanism**: `Bus` Protocol with three
  backends (in-process / Postgres / Redis), no separate operational
  concern in default deployments (see §24.10).
- **Real template lifecycle**: content-addressed identity, mutable
  tags, skill refs that resolve to specific hashes,
  `cairn eval --compare-against` for regression detection
  before merging prompt or model changes (see §24.11). Jinja
  deliberately deferred until a concrete need lands.
- **Improvement loop without autonomy**: memory accumulation +
  self-critique (shipped), few-shot library (P4), suggestion engine
  that surfaces candidate template/policy/binding changes through a
  human review queue (P5) — never autonomous self-modification.
  DSPy-style optimization and auto-fine-tuning are deliberately NOT
  engine features; they become packs if and when needed (see §24.12).
- **One integration substrate (MCP)**: pack manifest declares
  `requires.mcp_servers`; engine consumes MCP servers from the
  curated catalog (official + community) and from
  `integrations/custom/` (FastMCP-based wrappers for systems without
  upstream MCP). No raw external-API Python in packs.
  Activepieces / Pipedream explicitly NOT adopted as runtime
  substrates (workflow-engine conflict). See §24.13.
- **No unintended sprawl**: every "what store/engine/bus/integration
  do I run" question has one answer per tier.

This is the structural foundation the product features in Phase 9+ build
on top of.
