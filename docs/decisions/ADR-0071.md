# ADR-0071 — Config values: default sources, named presets, and how they flow through triggers

Status: Proposed (2026-07-13)
Extends: ADR-0068 (operator config surface — the `config_schema` contract,
precedence, doctor + run-submit preflight) and ADR-0070 (governance vs
operational scoping, layered across env / workflow / run).
Relates to: ADR-0047 (run provenance), ADR-0059/0060 (insights + suggestion
engine — the data-driven default source), ADR-0069 (workflow/bundle triggers),
the console Configuration + Run surfaces.

## Context

ADR-0068/0070 gave every tunable knob a home and a scope (governance vs
operational, layered env → workflow → run). What they did **not** answer:

1. **Where does a knob's *default* actually come from**, and can we do better
   than one static number?
2. **Can a user save a set of values under a name, reuse it, and mark one the
   default** — instead of re-typing the same tuning every run?
3. **What happens when the workflow is fired by a trigger / schedule / event**,
   where there is no human at the Run form to choose values?

Question (3) is the sharp one: a value system that only works when a human is
looking at a form is useless for the automated half of a control plane. This
ADR resolves all three with one layered model.

## Decision

### 1. Default sources — operator owns the knob, pack owns the input

Two distinct kinds of default, two owners; do not conflate them:

- **Operator** ships each **knob's** default via its `config_schema` field default
  (the *floor* — e.g. `dataset/pii_scan` declares `sample_size = 1000`). This is
  the guaranteed fallback and the governance safety baseline.
- **Template/pack** ships the **input** defaults (the Run-form input schema) and
  declares *which* operators compose the workflow.
- **Environment** layers governance overrides (ADR-0070); governance knobs are
  env-owned and never overridable below.

Hard rule (carried from ADR-0068): a template must **not** YAML-`$default`-pin a
config-managed knob — that clobbers the config layer. The safe default lives in
the operator's schema; the template wires operators, it does not freeze their
tunables.

### 2. Named presets — save value-sets, reuse, mark one default

Extend `WorkflowConfigStore` from "one current config per (workspace, workflow)"
to **N named presets** per (workspace, workflow), each versioned, one flaggable
as the workflow's **default preset**:

```
preset = { name, workflow_ref, workspace_id, values: {op: {knob: v}},
           version, is_default, created_at, created_by }
```

Constraints (cairn's governance differentiator):
- A preset may set **operational** knobs only. **Governance** knobs stay
  env-owned; a preset that tries to set one is rejected at save (reuse the
  ADR-0068 run-submit preflight, fail-closed).
- The selected preset + version is **stamped on the run's provenance** (ADR-0047),
  so the audit reads *"ran finetune with preset `cheap` v3."*

### 3. Layered resolution (highest wins) — the same for humans and machines

```
run override  >  selected preset  >  workflow config  >  environment  >  operator default
  (this run)      ("cheap" v3)        (persisted)         (governance)     (schema floor)
```

The two persisted layers (workflow config + default preset) live in the store and
are applied by the **dispatcher** on *every* run — verified single entry point
(`dispatcher.py` loads `default_workflow_config_store().get(...)` and injects
`__workflow_config__` into the compiled graph). This is what makes (3) work.

### 4. Triggers / schedules / events — the default preset is the mechanism

A triggered run has no Run form, so it resolves the **persisted** layers only:

```
event-normalized inputs  →  workflow DEFAULT preset  →  env  →  operator default
```

No human, no run-form. The Run-form preset picker is *only* an interactive,
per-run override; triggers correctly fall back to the marked-default preset.
Presets therefore MUST live in the persisted store (not run-form/UI state) — that
is the reason "mark as default" exists.

Optional refinement: a trigger/schedule definition may **pin a preset by name**
(schedules already persist their `inputs` the same way — a `config_preset` field
slots in identically). e.g. the nightly cron uses `nightly-cheap`, the PagerDuty
webhook uses `incident-fast`.

### 5. Suggested "optimal" values — suggest, never auto-apply

Two sources, both surfaced next to `Default` as an apply-in-one-click chip:
- **Author-declared `recommended`** in `config_schema` (deterministic, day-one).
- **Data-driven** — derived from the run/eval ledger via the existing suggestion
  engine (ADR-0059/0060): *"runs with `sample_size ≥ 1000` passed the gate 95%;
  below 200 failed 40% → suggest 1000,"* evidence attached. This is the ADR-0012
  "diagnose-auto, approve-human" pattern applied to knob values — never silent
  auto-tuning.

### 6. Inputs get the same model

Workflow **input** defaults are the same problem one layer up. The "Try with
sample data" demos are already author-shipped input presets; generalize them into
**user-savable input presets** so both knobs and inputs share one mental model:
*schema default → recommended → saved preset → run override*.

## Consequences

- Config becomes reusable and named, not re-typed per run; triggered runs inherit
  governed values automatically via the default preset.
- The audit gains a new, valuable line: which preset (+ version) produced a run.
- Governance is preserved end-to-end: presets can't touch governance knobs, and
  the run-submit preflight stays fail-closed.
- New surface area: preset CRUD (store + API + console), default-preset resolution
  in the dispatcher, provenance stamping, and (follow-up) the data-driven suggester.

## Rollout (see epic + slices)

MVP: named presets (operational-only, provenance-stamped, mark-default) + the
default-preset resolution for triggers + author-declared `recommended` on both the
Config tab and the Run form. Defer: per-trigger preset pin, portable
cross-workflow profiles, data-driven suggestions, full version-tree UI.
