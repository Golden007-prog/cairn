# Trust + safety layer (P2 / Cluster B)

## Context

The roadmap's "Trust + safety (core)" (ADR-0025 P2) is four items: **PII
redaction, secrets handling, audit logging, per-client tool allowlist.** This
is distinct from the action-governance trio (policy gate + budget cap +
approval gate), which is already built (ADR-0014; approval finished in
ADR-0024 RM3). Constraint: **no vendor-specific code in core** — core provides
only interfaces + the absolutely-necessary enforcement.

## Decision: a three-layer split per item

For every item the line is drawn in the same place:

| CORE (interface + necessary feature) | OPERATOR (service_provider, ADR-0027) |
|---|---|
| The Protocol (`Redactor`, `SecretStore`, `AuditSink`, `Authorizer`) | Every concrete impl — **including the zero-dep default** |
| **The enforcement chokepoint** — where it's applied (LLM gateway / MCP boundary / action handler). Always present; inert when unbound. | The detection/storage logic + any vendor SDK |
| Data models + the `services.<x>.provider` binding | — |
| Audit only: the *emission* at seams (core owns the seams) | The audit *sink* (where it lands) |

**Optional to turn ON, not optional to ESCAPE.** These services are NOT
mandatory for every deployment (correcting an earlier framing). Two controls:

| Actor | Controls | How |
|---|---|---|
| **Deployment (profile)** | whether the service runs at all | bind `redact.text` → a provider, or leave unbound → the chokepoint is a **pass-through no-op** (zero cost, no behavior change) |
| **Pack** | can *request* it (signal "I touch sensitive data") | declare `[requires].services` / `[optional]`; composition/doctor fails loud if a *requiring* pack is deployed with no provider bound |
| **Core** | the chokepoint is always there + can't be bypassed once bound | gateway always calls the bound provider; a pack cannot disable a redactor the deployment turned on |

So the chokepoint *call* is core and non-bypassable; what's optional is whether
a provider is *bound behind it*. A pack is never forced to redact and pays
nothing when redaction is off — but it also cannot switch off redaction a
deployment activated. The data owner (deployment) controls it, not the pack.

**Default:** `local-dev.toml` leaves `redact.text` **unbound** (dev data is
usually synthetic; zero surprise). The regex builtin ships and is one binding
line away; a `secure`/prod profile binds it. Packs that handle sensitive data
(e.g. `incident`, reading prod logs) declare `redact` in `[requires]`/`[optional]`.

### Per-item mapping

| Item | Core interface | Core chokepoint | Builtin (zero-dep) | Vendor operators (opt-in) |
|---|---|---|---|---|
| PII redaction | `Redactor` | LLM gateway send path (the data-to-vendor egress). NOTE: `obs/redact.py` is a *dead* no-op wired nowhere (old `src/mcp/hub.py` site is legacy) — slice 1 *establishes* the chokepoint, doesn't just swap a body. MCP-boundary is defense-in-depth, deferred. | `operator-redact-regex` | `operator-redact-presidio` |
| Secret **blocking** | *(reuses `Redactor`)* | same chokepoint, secret recognizers | `operator-redact-regex` (token/entropy) | `operator-secretscan-detectsecrets` |
| Secret **provisioning** | `SecretStore` | `OperationContext.secrets` (operators get only declared names) | `operator-secrets-env`, `-file` | `operator-secrets-openbao`, `-aws`, `-sops` |
| Audit logging | `AuditSink` + `AuditEvent` + emission (core) | gateway / MCP / action handler emit | `operator-audit-store` (reuse run/event store + sha256 hash-chain) | `operator-audit-otel`, `-immudb`, `-siem` |
| Per-client allowlist | `Authorizer` + `ClientIdentity` | MCP gateway resolves caps→tools *through* it | `operator-authz-static` (YAML via existing policy engine) | `operator-authz-cerbos`, `-opa` |

### Two collapses (don't build twice)

- **Secret-blocking IS redaction** — a secret recognizer in the same chokepoint.
  Only *secret provisioning* (`SecretStore`) is a separate concern.
- **Audit is mostly reuse** — we are OTel-native (ADR-0015) and have a run/event
  store. Audit = instrument the seams to emit `audit.*` events + an
  append-only/hash-chained shape. Do NOT build a new audit store.

## Licensing (permissive-only — the Restate lesson, ADR-0024)

Clean (core may declare as optional extras / official operators):
Presidio **MIT**, detect-secrets **Apache-2.0**, OpenBao **MPL-2.0**, SOPS
**MPL-2.0**, Cerbos **Apache-2.0**, OPA **Apache-2.0**, OpenTelemetry
**Apache-2.0**, immudb **Apache-2.0**.

**Landmine:** HashiCorp **Vault is BSL 1.1** since 2023 — operator-only, never
core (structurally impossible anyway). The permissive replacement is
**OpenBao** (MPL-2.0). OPA finally earns a place — not as the policy engine
(custom YAML stays, ADR-0020 §policy) but as the documented escape hatch for
per-client authz too complex for YAML.

## Build order

The redaction chokepoint is the spine (carries PII *and* secret-blocking; the
one with real data-egress exposure). Order: (1) `Redactor` interface + regex
builtin + wire the existing `redact.py` chokepoint → (2) fold secret
recognizers in → (3) audit emission over the existing store → (4) per-client
allowlist at the MCP gateway. Presidio/detect-secrets/OpenBao/Cerbos land later
as operators, never blockers.

## Status (updated 2026-06-12)

- **Slice 1 — redaction spine: DONE** (2026-06-11). `Redactor` + LLM-gateway
  chokepoint (`obs/redact.py`) + builtin `operator-redact-regex`. Optional via
  `redact.text` binding.
- **Slice 2 — secret recognizers: DONE** — folded into slice 1. The regex
  builtin's `_RECOGNIZERS` already carry private-key/JWT/AWS/OpenAI/GitHub
  tokens in the same chokepoint ("secret-blocking IS redaction", above). Secret
  *provisioning* (`SecretStore`) is a separate concern: the interface +
  `OperationContext.secrets` already exist; concrete `operator-secrets-env/-file`
  providers remain backlog, not part of this cluster's spine.
- **Slice 3 — audit logging: DONE** (2026-06-12). Core `AuditSink` + `AuditEvent`
  + `audit_emit` seams (LLM gateway / MCP boundary / durable action handler) +
  builtin `operator-audit-store` (zero-dep, sha256 hash-chained append-only
  JSONL). Optional via `audit.sink` binding.
- **Slice 4 — per-client tool allowlist: PARKED** (decided 2026-06-12). A
  *per-client* allowlist presumes multiple authenticated, differently-privileged
  callers — i.e. **multi-tenancy + authn, both parked** (`vision.md` north-star;
  ADR-0025 §3). cairn is single-tenant today; callers at the triggers/HTTP
  boundary are neither authenticated nor differentiated, so "client identity"
  has no real subject. The "per-client" wording here was north-star framing that
  leaked into near-term planning. Two consequences:
    - The `Authorizer`/`ClientIdentity` core interface is **not built** — it
      would solve for a world not on the roadmap, and would have forced caller
      identity through the deliberately caller-free, LOCKED `OperationContext`
      (§24.20.13).
    - A *deployment-scoped* tool allowlist (no identity: `(server, tool)` vs a
      profile-pinned allowed set, enforcing the today-dead
      `McpServerSpec.tool_allow_list_strict`) is a legitimate single-tenant
      blast-radius control and was considered, but was initially deferred.
      **UPDATE 2026-06-13 (housekeeping wave item 5): built.** The MCP client
      now enforces `tool_allow_list_strict`: when the active profile sets it
      for a server, `call_tool` denies any tool outside the union of installed
      packs' declared `[requires.mcp].tools` for that server
      (`McpToolNotAllowed`). Identity-free — the *per-client* `Authorizer`
      remains parked with multi-tenancy as decided above.
  When multi-tenancy is unparked, the natural home is `Authorizer` +
  `operator-authz-static` (YAML via the policy engine) with `-cerbos`/`-opa`
  (Apache-2.0) as documented swap-ins. Until then: not a blocker.

**Net: the trust + safety cluster is complete for the near term at slices 1–3.**

## Related backlog — notify service_provider (vendor-in-core debt, noted 2026-06-13)

The same `service_provider` + binding pattern this ADR uses for `redact.text` and
`audit.sink` has **not** been applied to notifications. `SlackNotifier`
(`core/notifier.py`), `slack_post` (`core/clients/mcp_client.py`), and the
`slack_executor`/`slack_approver` (`core/actions/builtin/`) are **vendor impls
living in core**, and `default_notifiers()` auto-wires Slack instead of resolving
a binding. The seam (`Notifier` Protocol + registry + neutral Stdout/File + a
no-op default) is correctly in core; the Slack impl should move to
`operator-notify-slack` (builtin `service_provider`) bound via a `notify.sink`
profile binding — mirroring redaction/audit exactly. **Pull it behind the first
real consumer** (the dataset-readiness gate's notify/approve step,
`docs/ideas/dataset-readiness-pack.md`), not as a standalone refactor of working
code. The `slack_approver` HITL channel is the approval half (ADR-0024).

## Tie-in

PII/secrets/audit here are the **substrate for ModelOps dataset auditing** (the
committed platform direction, `vision.md`) — "audit a training dataset for PII
before spend" reuses the same redaction + audit primitives.
